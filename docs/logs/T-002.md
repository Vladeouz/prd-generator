# T-002 Spike job berdurasi panjang di proses server Next.js

## Status

Selesai. Branch `chore/t-002-spike-jobs`.

## Ringkasan

Route handler `POST /api/spike/jobs` memulai proses anak Node palsu (`spikes/jobs/fake-worker.mjs`) yang berjalan 3 menit dan menulis progres setiap detik ke stdout (dibaca server) dan ke file log di folder sementara OS (tetap terisi walau server mati). State job disimpan di memori proses lewat `globalThis` (`Symbol.for`), dengan salinan di `%TEMP%\prd-generator-spike-jobs\jobs.json`. Saat store dibuat pertama kali di sebuah proses server, job yang tercatat `running` ditandai `interrupted`, beserta apakah proses anaknya masih hidup. Setiap respons menyertakan `serverPid` dan `moduleId` (acak per evaluasi modul), sehingga restart server dan evaluasi ulang modul terlihat.

Halaman `/spike/jobs` (tombol mulai) dan `/spike/jobs/status` (halaman lain) mem-polling `GET /api/spike/jobs` setiap detik. Navigasi diuji di Chrome headless sungguhan dengan `spikes/jobs/browser-check.mjs` (Chrome DevTools Protocol lewat WebSocket bawaan Node 24, tanpa dependency baru).

## Keputusan yang diambil sendiri

1. **State di `globalThis` dengan `Symbol.for`, plus salinan JSON di folder sementara OS.** `globalThis` dipakai agar evaluasi ulang modul tidak menghapus state. Salinan JSON di `%TEMP%` (bukan di repo, jadi tidak perlu mengubah `.gitignore`) menggantikan SQLite, yang baru tersedia di T-003.
2. **Navigasi diuji di Chrome sungguhan lewat DevTools Protocol** tanpa memasang Playwright, yang baru masuk di T-017.
3. **Ctrl+C ditiru dengan `GenerateConsoleCtrlEvent`** ke console server, karena `process.kill(pid, 'SIGINT')` di Windows sama dengan kill paksa dan tidak mewakili Ctrl+C.
4. **Worker palsu mengabaikan error stdout** dan terus berjalan, meniru `claude -p --output-format json` yang baru menulis ke stdout di akhir. Dengan begitu, yang mematikannya hanyalah sistem operasi, bukan pipe yang putus.

## Hasil spike

**Berhasil. Rekomendasi: tetap memakai D-03** (job di proses server Next.js, satu job dalam satu waktu). Proses worker terpisah tidak diperlukan. Temuan dan konsekuensinya untuk T-004/T-005:

1. **Job tidak terikat ke request.** Route mengembalikan `202` segera, dan navigasi (klien maupun penuh) tidak memengaruhi job.
2. **Modul bisa dievaluasi ulang tanpa restart proses** (hot reload di `pnpm dev`). State yang harus bertahan selama proses hidup, seperti handle `ChildProcess` job aktif, disimpan di `globalThis` dengan `Symbol.for`, bukan di variabel modul. Variabel modul biasa akan hilang, sehingga job kedua bisa dimulai dan job yang masih berjalan tidak bisa diselesaikan. Di build produksi, kedua route memakai satu instance modul yang sama.
3. **Proses server bisa berganti**: restart `next dev` karena `next.config.ts` berubah (kemungkinan juga `.env`, karena Next menampilkan "Environments: .env"; belum diuji karena agent tidak boleh mengubah `.env`), Ctrl+C, atau crash. Di Windows, proses anak yang tidak `detached` selalu ikut mati, karena libuv memasukkannya ke job object yang ditutup saat Node keluar. Ini berlaku untuk seluruh pohon proses `shell: true`. Tidak ada proses yatim, jadi tidak ada `claude` yang terus memakai kuota setelah server mati. **Jangan pakai `detached: true`.**
4. **Status `interrupted` saat startup dibutuhkan dan cukup.** Sumber kebenaran sebaiknya SQLite (T-003). T-005 menandai semua job `running` sebagai `interrupted` sekali saat server start, misalnya di `register()` pada `src/instrumentation.ts`. Spike ini melakukannya secara lazy pada request pertama, yang juga bekerja tetapi membuat status salah sampai ada request.
5. **Satu job dalam satu waktu terbukti** dengan cek-dan-set sinkron di satu event loop (tanpa `await` di antaranya). Di T-005, insert job lewat `better-sqlite3` (sinkron) ditambah partial unique index di PRD bagian 4 memberi jaminan yang sama di tingkat database.
6. **Untuk T-004 (batas waktu runner):** di Windows dengan `shell: true`, `child.kill()` tidak mematikan `claude`. Gunakan `taskkill /PID <pid> /T /F`. Jangan mematikan proses berdasarkan pid yang disimpan dari proses server sebelumnya, karena pid bisa dipakai ulang oleh proses lain. Ini terjadi di sesi ini: saat membersihkan probe, pid yang dicatat sudah dipakai `conhost.exe` lain dan ikut ter-kill. Lagi pula, poin 3 membuat langkah itu tidak perlu.

Tidak diuji: perilaku di Linux/macOS, karena di sana proses anak tidak otomatis mati bersama induknya. Di luar cakupan, karena pengguna memakai Windows.

## Kendala

- Ctrl+C pada `pnpm start` di CMD memunculkan "Terminate batch job (Y/N)?" dari shim `pnpm.cmd`. Ini hanya kosmetik, karena server dan job sudah berhenti.
- Saat membersihkan proses probe, satu `conhost.exe` yang tidak terkait ikut dimatikan karena pid-nya sama dengan pid probe yang sudah mati (lihat Hasil spike poin 6).
