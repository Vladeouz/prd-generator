- **`spikes/conflict-review/run.mjs`:**
  - membaca salinan database utama (sumber dibuka `readonly`, lalu `backup` ke folder sementara);
  - mengambil dokumen `tasks` dan `prd` terbaru proyek "Reservasi Massage 3" (`47f90fbc-…`, TASKS versi 2 hasil verifikasi T-043, PRD versi 2), output 7a yang berlaku, dan bagian konvensi `stage7b` dari `TEMPLATE_DIR`;
  - menyusun prompt percobaan 7c (`spikes/conflict-review/prompt-7c.md`).
- **Pengambilan catatan:** setiap entri `` `path` (keterangan) `` di baris `files:` dipindai. Satu keterangan bisa memuat lebih dari satu "Catatan pertentangan:", jadi dipecah per awalan. Setiap catatan mendapat id `C-01`…, beserta task dan path-nya (`results/notes.json`). Script berhenti bila jumlah catatan yang terbaca berbeda dengan jumlah awalan di seluruh dokumen.

  - `id`, `topic`, `note_ids`;
  - `source` (`prd`, `template`, `generator`, `pilihan_bebas`);
  - `question`;
  - `options` (2–3 opsi, masing-masing `label` dan `impact`);
  - `recommended` dan `recommendation_reason`;
  - `affected_tasks` dan `answered_by` (`{task, explanation}` atau `null`).
- **Validasi bentuk** (tanpa menilai isi) memeriksa:
  - setiap catatan masuk tepat satu pertentangan;
  - `source` dikenal;
  - 2–3 opsi dengan id unik, dan `recommended` adalah salah satunya;
  - `affected_tasks` dan `answered_by.task` ada di daftar 7a.
- **Metrik per run:** jumlah pertentangan, jumlah per sumber, apakah catatan role ada di satu pertentangan, catatan yang tidak terpetakan atau ganda, token, biaya, dan durasi.
- **Pemanggilan:**
  - lewat `CliClaudeRunner`, dengan bentuk perintah runner saat ini; `--model`/`--effort` diberikan per pemanggilan (`ClaudeRunOptions`);
  - urutan run: Sonnet `low` 1, Opus `medium` 1, Sonnet `low` 2, Opus `medium` 2;
  - satu percobaan per run, tanpa percobaan ulang;
  - batas biaya $3;
  - run yang sudah tercatat dilewati bila script dijalankan ulang.

### Catatan role: dipisah dua, konsisten di keempat run

Tidak ada run yang menggabungkan keenam catatan role menjadi satu. **Keempat run memisahkannya dengan cara yang sama**, dan menurut penilaian saya pemisahan itu benar:

- **API (C-05 T-005, C-08 T-010):** "konvensi tidak mengenal role admin". Keempat run mengisi `answered_by: T-001`. Judul T-001 di 7a memang "kolom role di tabel users, middleware otorisasi admin, dan penetapan admin lewat konfigurasi", dan T-002 mengembalikan `role` di `GET /v1/users/me`. Catatan ini muncul karena 7b fase 1 hanya melihat task fasenya sendiri, bukan karena template kurang. Pertanyaan ini seharusnya tidak sampai ke user.
- **Flutter (C-04 T-003, C-06, C-11, C-12):** bagaimana aplikasi tahu peran dan memilih layar. Ini celah konvensi template yang nyata: bagian Autentikasi hanya mengenal status login. Ini satu-satunya pertanyaan role yang perlu dijawab user, dan ketiga opsinya konsisten di keempat run: peran dimuat bersama sesi, cubit terpisah, atau tanpa pemisahan di client.

Artinya, metrik "6 catatan role menjadi satu" terlalu ketat. Hasil yang diinginkan adalah satu pertanyaan role untuk user, ditambah satu pertentangan yang ditandai sudah dijawab. Hasil itu tercapai di keempat run.
