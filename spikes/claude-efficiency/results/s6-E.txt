# Aplikasi Membership Gym

## 1. Context & Goal

**Masalah.** Pencatatan member dan masa aktif di sebuah gym masih manual atau berantakan. Admin sulit tahu siapa yang masih aktif, kapan masa aktif habis, dan siapa yang sudah bayar.

**Pengguna.** Dua peran memakai aplikasi yang sama:
- **Admin** mengelola paket, member, pembayaran, check-in (scan QR di web), dan jadwal kelas.
- **Member** melihat status masa aktif, menampilkan QR check-in, membayar perpanjangan secara online, dan mem-booking kelas.

**Tujuan.** Versi pertama untuk operasional satu gym. Aksi pertama admin adalah menambahkan member baru beserta paketnya. Nilai utamanya adalah merapikan pengelolaan member, masa aktif, pembayaran, kehadiran, dan kelas dalam satu sistem dengan satu sumber kebenaran di server.

**Platform.** Android, iOS, dan web dari satu codebase Flutter. Halaman admin, termasuk scan QR dengan kamera, dipakai lewat web. Aplikasi selalu online. Tidak ada fitur realtime: data diambil saat halaman dibuka atau di-refresh, dan validasi penting (kuota, masa aktif) selalu dicek di server.

**Keputusan produk yang berlaku di seluruh dokumen** (nilai bisa diubah admin lewat pengaturan gym di FR-03):
- Zona waktu dan "hari ini" selalu memakai zona waktu gym (default `Asia/Jakarta`).
- Member aktif sampai akhir hari `expires_on`. Tidak ada masa tenggang (RV-07).
- "Hampir habis" berarti sisa 0 sampai 7 hari. Booking boleh dibatalkan paling lambat 2 jam sebelum kelas. QR berganti tiap 30 detik (RV-09).
- Payment gateway adalah **Midtrans (Snap)** dengan metode QRIS, virtual account bank (BCA, BNI, BRI, Mandiri), dan GoPay. Gateway dibungkus interface `PaymentGateway` supaya mudah diganti (RV-08).

## 2. Scope

### In scope

Urutan fase mengikuti dependensi fitur:

- **Fase 0, Fondasi**
  - F-01 Akun dan login: login/logout, pembuatan user otomatis saat request pertama, halaman profil. Penautan akun ke data member tidak ada di fase ini (RV-03).
  - F-02 Gym dan peran: profil gym dan pengaturan, peran admin/member, pembatasan akses, cabut admin, seed admin pertama lewat CLI (RV-06).
- **Fase 1, Member dan paket**
  - F-03 Paket membership.
  - F-04 Data member, termasuk undangan satu kali pakai dan penautan akun ke member (RV-02, RV-03), foto lewat signed URL (RV-05), dan permintaan hapus akun di profil (RV-10; bagian dari F-01, dikerjakan di fase ini karena butuh data member).
  - F-05 Status masa aktif dan tanggal kedaluwarsa.
- **Fase 2, Pembayaran dan perpanjangan**
  - F-06 Pembayaran manual oleh admin dan perpanjangan.
  - R-06 Ekspor laporan member dan pembayaran (setelah F-06; RV-01).
  - F-07 Pembayaran online lewat Midtrans.
- **Fase 3, Check-in QR**
  - F-08 QR dinamis, scan admin, dan riwayat check-in.
- **Fase 4, Kelas dan booking**
  - F-09 Jadwal kelas (satu kali dan mingguan berulang).
  - F-10 Booking kelas dengan kuota atomik.
- **Fase 5, Notifikasi** (RV-01, RV-04)
  - Infrastruktur push: token perangkat FCM, setup APNs, job pg-boss idempoten.
  - R-01 Pengingat masa aktif hampir habis (setelah F-05 dan F-07).
  - R-03 Pengingat jadwal kelas (setelah F-10).

### Non-goals

- Banyak gym atau cabang dalam satu aplikasi. Skema sudah memakai `gym_id`, tetapi fiturnya belum dibuat.
- Mode offline. Check-in, booking, dan pembayaran selalu butuh koneksi.
- Pembaruan data realtime.
- Instruktur atau personal trainer sebagai pengguna dengan login sendiri.
- Penjualan produk atau kasir.
- Absensi dan penggajian staf.
- Check-in mandiri lewat perangkat atau kios tanpa admin.
- Refund otomatis lewat payment gateway.
- Dashboard ringkasan admin, daftar tunggu kelas, cuti/bekukan membership, kode promo dan diskon.
- Impor data member lama dari spreadsheet.
- Notifikasi lewat email, SMS, atau WhatsApp (hanya push FCM).
- Booking kelas otomatis dihitung sebagai check-in. Check-in tetap lewat scan QR.

## 3. Tech Constraints

- Monorepo pnpm: `apps/app` (Flutter web/Android/iOS), `apps/api` (Hono + TypeScript), `packages/contract` (OpenAPI + client Dart hasil generate).
- Database PostgreSQL + Drizzle. Auth Firebase Auth (backend memverifikasi ID token). Peran dan keanggotaan di PostgreSQL.
- File di Cloud Storage for Firebase, **dikunci penuh dari client**: `storage.rules` menolak semua baca/tulis. Akses hanya lewat API (RV-05).
- Push lewat FCM. Job terjadwal memakai pg-boss di dalam container API dengan `RUN_WORKER=true` (RV-04).
- Deploy: API sebagai container yang selalu hidup, web di hosting statis, mobile lewat store.
- Detail konvensi (struktur repo, job, autentikasi, port, pagination, database, format error, Clean Architecture, tenancy) ada di `docs/conventions.md`. Ikuti file itu, jangan diulang di sini.

Keputusan khusus produk ini:
- **Tenancy.** Pola bagian "Organisasi dan tenancy" di conventions dipakai dengan `gyms` sebagai pengganti `organizations` dan `gym_accounts` sebagai pengganti `memberships`. Nama `memberships` dihindari karena bentrok dengan istilah produk. Path bersarang `/v1/gyms/{gymId}/...`. Bukan anggota gym → `404`. Peran kurang → `403`.
- **Kode error baru** ditambahkan ke `error-codes.ts` lalu dipetakan di `failureCodeOf` dan `failure_messages.dart` (lihat bagian Format error di conventions):

| Kode | HTTP | Kapan |
| --- | --- | --- |
| `MEMBERSHIP_INACTIVE` | 409 | Member kedaluwarsa saat check-in atau booking |
| `QR_INVALID` | 422 | QR rusak, kedaluwarsa, atau sudah dipakai |
| `CLASS_FULL` | 409 | Kuota kelas penuh |
| `BOOKING_CLOSED` | 409 | Booking atau pembatalan di luar batas waktu |
| `LAST_ADMIN` | 409 | Aksi akan membuat gym tanpa admin |
| `INVITE_INVALID` | 422 | Kode undangan salah, kedaluwarsa, sudah dipakai, atau dicabut |
| `RATE_LIMITED` | 429 | Terlalu banyak percobaan kode undangan |

- **Port baru** mengikuti pola port di conventions (adapter `none` / `fake` / sungguhan, dipilih lewat env):
  - `PaymentGateway` (`PAYMENT_ADAPTER=midtrans|fake`) dengan `createTransaction`, `verifyWebhook`, dan `getStatus`.
  - `FileStorage` diperluas dengan `getSignedUrl(path, ttlSeconds)` di adapter `fake` dan `firebase-storage` (RV-05).
  - `PushSender` sudah ada. Produksi memakai `PUSH_ADAPTER=fcm`.
- **Setup APNs.** Kunci APNs (.p8) diunggah di Firebase Console agar FCM bisa mengirim ke iOS. Ini langkah manual sekali saat rilis (RV-04).
- **Admin pertama** dibuat lewat skrip CLI `pnpm --filter api seed:first-admin --email <email> [--gym-name <nama>] [--timezone <IANA>]`, dijalankan saat deploy (RV-06). Skrip idempoten:
  - Membuat gym bila belum ada.
  - Jika user dengan email itu sudah pernah login, ia diberi peran admin.
  - Jika belum, skrip mencetak satu kali kode undangan admin (berlaku 48 jam) yang ditebus setelah login.
- **Hitung tanggal.** `addDuration(date, value, unit)` memakai kalender dan dipakai di satu tempat (`computeRenewalPeriod`). Untuk `month` dan `year`, hari dipotong ke akhir bulan (31 Jan + 1 bulan = 28/29 Feb).
- **Pengaturan gym** disimpan di tabel `gyms` (lihat bagian 4).

Constraint penting. Penamaan mengikuti bagian Database di conventions: enum sebagai `text` + CHECK, FK bernama eksplisit, timestamp lewat helper `schema/columns.ts`.

- **Pengguna dan peran**
  - `users`: UNIQUE `firebase_uid`. CHECK email lowercase. User baru tidak punya baris `gym_accounts`, jadi tanpa peran (RV-06).
  - `gym_accounts`: UNIQUE `(gym_id, user_id)`. CHECK `role IN ('admin','member')`. Seorang user yang ditautkan ke member memiliki `gym_accounts` dengan role `member`.
  - `gyms`: CHECK `expiring_soon_days` 1–30, `cancel_cutoff_minutes` 0–1440, `qr_rotation_seconds` 10–120, `class_reminder_minutes` 15–1440. `timezone` divalidasi sebagai IANA di Zod.
- **Undangan**
  - `invitations`: UNIQUE `code_hash` (SHA-256 dari kode). Kode tidak pernah disimpan polos. CHECK `(type='member') = (member_id IS NOT NULL)`.
  - Index parsial `invitations_member_id_active_index` pada `member_id` untuk undangan yang belum dipakai dan belum dicabut.
- **Paket dan member**
  - `plans`: CHECK `duration_value > 0`, `duration_unit IN ('day','week','month','year')`, `price_amount > 0`, `char_length(name)` 1–80. UNIQUE `(gym_id, lower(name))`.
  - `members`: UNIQUE `(gym_id, user_id)` bila `user_id` tidak null, sehingga satu akun hanya satu member. UNIQUE parsial `(gym_id, phone)` `WHERE deleted_at IS NULL`.
  - `members`: CHECK `start_on <= expires_on`. FK `user_id` `ON DELETE SET NULL`. Index pagination `(gym_id, created_at DESC, id DESC)`. Index `(gym_id, expires_on)` untuk filter status.
- **Pembayaran**
  - `payments`: kolom `plan_duration_value` dan `plan_duration_unit` NOT NULL dengan CHECK yang sama seperti `plans` (RV2-01). Keduanya diisi saat pembayaran dibuat, dan `computeRenewalPeriod` hanya membaca snapshot ini, tidak pernah `plans`.
  - `payments`: CHECK `status IN ('pending','paid','failed','expired','needs_review')`, `method IN ('cash','transfer','online')`, `amount > 0`. CHECK `(applied_at IS NULL) = (period_end_on IS NULL)`.
  - `payments`: CHECK `method='online'` mensyaratkan `expires_at` tidak null. Index `(gym_id, created_at DESC, id DESC)` dan `(member_id, created_at DESC, id DESC)`. Index parsial `(created_at)` `WHERE status='pending' AND method='online'` untuk rekonsiliasi.
  - `payment_webhook_events`: UNIQUE `event_key` (SHA-256 dari `order_id|transaction_status|status_code|gross_amount`).
  - FK `payments.member_id` `ON DELETE RESTRICT` agar riwayat pembukuan tidak hilang. `recorded_by_user_id` `ON DELETE SET NULL`.
- **Check-in**
  - `check_ins`: UNIQUE `qr_jti`, jadi satu QR hanya bisa dipakai sekali. Index `(gym_id, checked_in_at DESC, id DESC)` dan `(member_id, checked_in_at DESC)`.
- **Kelas dan booking**
  - `class_series`: CHECK `weekday` 0–6, `start_time ~ '^([01][0-9]|2[0-3]):[0-5][0-9]$'`, `capacity` 1–500, `duration_minutes` 5–480, `ends_on IS NULL OR ends_on >= starts_on`.
  - `class_sessions`: UNIQUE parsial `(series_id, local_date)` `WHERE series_id IS NOT NULL` (`class_sessions_series_id_local_date_unique`). Ini membuat generator idempoten.
  - `class_sessions`: CHECK `capacity` 1–500, `status IN ('scheduled','cancelled')`. Index `(gym_id, starts_at)`.
  - `local_date` selalu dihitung server dari `starts_at` dengan zona gym, tidak pernah dari input client.
  - `bookings`: UNIQUE parsial `(session_id, member_id)` `WHERE status='booked'` (`bookings_session_id_member_id_booked_unique`). Index `(member_id, created_at DESC, id DESC)`.
- **Notifikasi**
  - `device_tokens`: UNIQUE `token`. FK `user_id` `ON DELETE CASCADE`.
  - `notification_log`: UNIQUE `dedupe_key` untuk mencegah notifikasi terkirim dua kali (RV-04).
- **Aturan integritas lintas tabel**
  - Setiap tabel utama punya `gym_id`, dan semua query repository difilter `gym_id`.
  - Perubahan admin (cabut admin, hapus akun admin, tebus undangan admin) berjalan dalam transaksi yang diawali `SELECT ... FROM gyms WHERE id=$1 FOR UPDATE` (RV2-02).
  - Perpanjangan mengunci baris `members` dengan `FOR UPDATE`. Booking mengunci baris `class_sessions` dengan `FOR UPDATE` sebelum menghitung peserta `booked`.

## 5. API Contract

**Aturan umum.** Semua route `/v1/*` terautentikasi (bagian Autentikasi di conventions). Format error dan pagination mengikuti bagian Format error dan Pagination. Route `/v1/gyms/{gymId}/*` melewati middleware keanggotaan: `gymId` bukan UUID → `422 details.gymId`, bukan anggota gym → `404`, peran kurang → `403`. Error `401`, `404` (gym), dan `422` (path/query/body) berlaku di semua endpoint, dan daftar error per endpoint hanya menyebut tambahannya. Semua tanggal `date` berformat `YYYY-MM-DD`, semua timestamp berformat ISO 8601 UTC. Jumlah uang berupa integer rupiah.

Tipe bersama:
- `Member` = `{ id, name, phone, email, photoUrl, plan: { id, name }, startOn, expiresOn, status, daysRemaining, linked }`. `status` ∈ `active | expiring_soon | expired`, dihitung server (FR-12). `photoUrl` adalah signed URL berumur 5 menit atau `null`. `MemberSummary` sama tanpa `photoUrl` dan memuat `hasPhoto`.
- `Payment` = `{ id, memberId, memberName, planName, planDuration: { value, unit }, amount, method, status, expiresAt, paidAt, periodStartOn, periodEndOn, createdAt }`.
- `ClassSession` = `{ id, seriesId, name, instructorName, startsAt, localDate, durationMinutes, capacity, bookedCount, remaining, status, myBookingId }`. `myBookingId` hanya terisi untuk member.

### Akun dan undangan

**GET /v1/me**
- Akses: user login mana pun.
- Response `200`: `{ id, email, displayName, accounts: [{ gymId, role, memberId }] }`. `accounts` kosong untuk user baru, dan UI menampilkan layar "Masukkan kode undangan".

**DELETE /v1/me**
- Akses: user login. Menjalankan penghapusan akun (FR-11). Response `204`.
- Error: `409 LAST_ADMIN` bila user admin terakhir sebuah gym.

**POST /v1/invitations/redeem**
- Akses: user login tanpa syarat peran.
- Request: `{ code }` (trim, huruf besar, 8 karakter dari alfabet tanpa karakter ambigu).
- Response `200`: `{ gymId, role, memberId }`.
- Error: `422 INVITE_INVALID`, `409 CONFLICT` (user sudah punya akun di gym itu), `429 RATE_LIMITED`.

**POST /v1/me/device-tokens** (fase 5)
- Akses: user login. Request: `{ token, platform }`. Upsert berdasarkan `token`: bila token sudah ada milik user lain, kepemilikan dipindah ke user ini.
- Response `204`.

**POST /v1/me/device-tokens/remove**
- Request: `{ token }`. Dipanggil saat logout. Response `204` (idempoten, `204` juga bila token tidak ada).

**POST /v1/gyms/{gymId}/invitations**
- Akses: admin.
- Request: `{ type: 'member', memberId }` atau `{ type: 'admin' }`.
- Response `201`: `{ id, type, memberId, code, expiresAt }`. `code` hanya muncul di respons ini. Berlaku 48 jam.
- Error: `404` (member tidak ada), `409 CONFLICT` (member sudah ditautkan ke akun).
- Menerbitkan undangan baru untuk member yang sama mencabut undangan aktif sebelumnya.

**GET /v1/gyms/{gymId}/invitations**
- Akses: admin. Daftar undangan yang belum dipakai, belum dicabut, dan belum kedaluwarsa, tanpa `code`. Response: `{ items }`.

**DELETE /v1/gyms/{gymId}/invitations/{invitationId}**
- Akses: admin. Mencabut undangan. Response `204`.

### Gym dan admin

**GET /v1/gyms/{gymId}**
- Akses: admin dan member.
- Response `200`: `{ id, name, address, timezone, expiringSoonDays, cancelCutoffMinutes, qrRotationSeconds, classReminderMinutes }`.

**PATCH /v1/gyms/{gymId}**
- Akses: admin. Body: semua field opsional, minimal satu (`details._root`). Response `200` gym.
- Error: `422` (zona waktu bukan IANA, nilai di luar rentang).

**GET /v1/gyms/{gymId}/admins**
- Akses: admin. Response: `{ items: [{ userId, displayName, email, createdAt }] }`.

**DELETE /v1/gyms/{gymId}/admins/{userId}**
- Akses: admin. Mencabut peran admin (baris `gym_accounts` dihapus). Boleh mencabut diri sendiri. Response `204`.
- Error: `404` (bukan admin gym ini), `409 LAST_ADMIN`.

### Paket

**GET /v1/gyms/{gymId}/plans?activeOnly=true**
- Akses: admin dan member. Member hanya mendapat paket aktif. Response: `{ items: [Plan] }`. `Plan` = `{ id, name, durationValue, durationUnit, priceAmount, isActive }`. Tidak dipaginasi (jumlah kecil).

**POST /v1/gyms/{gymId}/plans**
- Akses: admin. Request: `{ name, durationValue, durationUnit, priceAmount }`. Response `201` Plan.
- Error: `409 CONFLICT` (nama kembar).

**PATCH /v1/gyms/{gymId}/plans/{planId}**
- Akses: admin. Body opsional minimal satu: `name`, `durationValue`, `durationUnit`, `priceAmount`, `isActive`. Response `200`.
- Error: `404`, `409 CONFLICT`. Perubahan tidak memengaruhi pembayaran yang sudah dibuat (snapshot).

### Member

**POST /v1/gyms/{gymId}/members**
- Akses: admin.
- Request: `{ name, phone, email?, planId, startOn, paymentMethod? }`.
  - `startOn` hari ini sampai 30 hari ke belakang (RV2-04).
  - `paymentMethod` ∈ `cash | transfer`. Bila diisi, dibuat pembayaran `paid` sebesar harga paket.
- Response `201` Member.
- Error: `422 details.startOn` (di masa depan atau lebih dari 30 hari lalu), `422` (planId nonaktif atau bukan milik gym, `details.planId`), `409 CONFLICT` (nomor HP sudah dipakai).

**GET /v1/gyms/{gymId}/members?status=&q=&limit=&cursor=**
- Akses: admin. `status` ∈ `active | expiring_soon | expired`. `q` mencari nama (prefix, tanpa membedakan huruf besar-kecil) atau nomor HP (substring). Urutan `created_at DESC, id DESC`.
- Response: `MemberPage` berisi `MemberSummary`.

**GET /v1/gyms/{gymId}/members/{memberId}**
- Akses: admin. Response: Member dengan `photoUrl`. Error: `404`.

**PATCH /v1/gyms/{gymId}/members/{memberId}**
- Akses: admin. Body opsional minimal satu: `name`, `phone`, `email`. Masa aktif hanya berubah lewat pembayaran. Response `200`.
- Error: `404`, `409 CONFLICT`.

**PUT /v1/gyms/{gymId}/members/{memberId}/photo**
- Akses: admin. Request `multipart/form-data` dengan field `file` (JPEG, PNG, atau WebP, maks 2 MB). Response `200`: `{ photoUrl }`.
- Error: `404`, `422 details.file` (tipe atau ukuran).
- File disimpan di path `gyms/<gymId>/members/<memberId>/photo`, menimpa file lama.

**GET /v1/gyms/{gymId}/me/member**
- Akses: member (yang akunnya ditautkan). Response: Member milik sendiri, termasuk `photoUrl`.
- Error: `404` bila akun admin tanpa data member.

### Pembayaran

**POST /v1/gyms/{gymId}/members/{memberId}/payments**
- Akses: admin. Request: `{ planId, method }` dengan `method` ∈ `cash | transfer`.
- Response `201` Payment berstatus `paid` dengan `periodStartOn` dan `periodEndOn` terisi. Masa aktif member ikut diperpanjang.
- Error: `404`, `422` (paket nonaktif).

**GET /v1/gyms/{gymId}/payments?from=&to=&status=&memberId=&limit=&cursor=**
- Akses: admin. `from` dan `to` adalah tanggal di zona gym (inklusif). Response `PaymentPage`.
- `status` menerima semua nilai, termasuk `needs_review` untuk tindak lanjut manual admin.

**GET /v1/gyms/{gymId}/members/{memberId}/payments?limit=&cursor=**
- Akses: admin. Response `PaymentPage`. Error: `404`.

**GET /v1/gyms/{gymId}/me/payments?limit=&cursor=**
- Akses: member. Riwayat pembayaran milik sendiri.

**GET /v1/gyms/{gymId}/me/payments/{paymentId}**
- Akses: member. Pembayaran milik sendiri. Dipakai untuk memuat ulang status setelah kembali dari halaman bayar. Error: `404`.

**POST /v1/gyms/{gymId}/me/payments/online**
- Akses: member. Request: `{ planId }`.
- Response `201`: `{ payment, redirectUrl }`. Pembayaran berstatus `pending` dan berlaku 60 menit.
- Error: `422` (paket nonaktif), `404` (akun tanpa data member), `502`-setara dilaporkan sebagai `500 INTERNAL_ERROR` bila gateway gagal. Pembayaran yang gagal dibuat di gateway tidak disimpan.

**POST /webhooks/midtrans** (publik, di luar `/v1`)
- Didaftarkan di `PUBLIC_ROUTES` pada `all-routes-require-auth.int.test.ts`.
- Request: payload notifikasi Midtrans. Tanda tangan diverifikasi lewat `PaymentGateway.verifyWebhook`.
- Response: `200 {}` bila diterima (termasuk duplikat atau diabaikan), `401 UNAUTHENTICATED` bila tanda tangan salah, `404` bila `order_id` tidak dikenal. Perilaku detail di FR-18.

### Ekspor (R-06)

**GET /v1/gyms/{gymId}/exports/members?status=**
- Akses: admin. Response `200` `text/csv; charset=utf-8` dengan BOM dan `Content-Disposition: attachment; filename="members-<tanggal>.csv"`.
- Kolom: `nama, nomor_hp, email, paket, tanggal_kedaluwarsa, status`.

**GET /v1/gyms/{gymId}/exports/payments?from=&to=&status=**
- Akses: admin. `from` dan `to` wajib, rentang maks 366 hari. Response `text/csv`.
- Kolom: `tanggal_bayar, nama_member, paket, jumlah, metode, status`.
- Error: `422 details.from` / `details.to` (rentang terlalu besar, atau lebih dari 50.000 baris).

### Check-in

**GET /v1/gyms/{gymId}/me/qr-token**
- Akses: member aktif. Response `200`: `{ token, expiresAt, rotateInSeconds }`. Error: `409 MEMBERSHIP_INACTIVE`, `404` (tanpa data member).

**POST /v1/gyms/{gymId}/check-ins**
- Akses: admin. Request: `{ token }`.
- Response `201`: `{ id, checkedInAt, member: { id, name, photoUrl, expiresOn, status } }`.
- Error: `422 QR_INVALID`, `409 MEMBERSHIP_INACTIVE`.

**GET /v1/gyms/{gymId}/check-ins?memberId=&from=&to=&limit=&cursor=**
- Akses: admin. Order `checked_in_at DESC, id DESC`. Response `CheckInPage` berisi `{ id, memberId, memberName, checkedInAt }`.

**GET /v1/gyms/{gymId}/me/check-ins?limit=&cursor=**
- Akses: member. Riwayat sendiri.

### Kelas dan booking

**POST /v1/gyms/{gymId}/class-sessions**
- Akses: admin. Kelas satu kali. Request: `{ name, instructorName, startsAt, durationMinutes, capacity }`. Response `201` ClassSession.
- Error: `422` (`startsAt` di masa lalu).

**POST /v1/gyms/{gymId}/class-series**
- Akses: admin. Kelas mingguan berulang. Request: `{ name, instructorName, weekday, startTime, durationMinutes, capacity, startsOn, endsOn? }`. Response `201` ClassSeries = `{ id, name, instructorName, weekday, startTime, durationMinutes, capacity, startsOn, endsOn, isActive }`.
- Sesi untuk 28 hari ke depan langsung dibuat.
- Error: `422` (`weekday` tidak cocok dengan `startsOn` dihitung di zona gym, `details.weekday`).

**GET /v1/gyms/{gymId}/class-series**
- Akses: admin. Response `{ items: [ClassSeries] }`.

**GET /v1/gyms/{gymId}/class-series/{seriesId}** (RV2-05)
- Akses: admin. Response ClassSeries. Error: `404`.

**PATCH /v1/gyms/{gymId}/class-series/{seriesId}**
- Akses: admin. Body opsional minimal satu: `name`, `instructorName`, `startTime`, `durationMinutes`, `capacity`, `endsOn`. Perubahan berlaku untuk sesi `scheduled` yang belum dimulai.
- Response `200`.
- Error: `404`, `409 CONFLICT` (kapasitas baru kurang dari jumlah booking `booked` di salah satu sesi).

**POST /v1/gyms/{gymId}/class-series/{seriesId}/cancel**
- Akses: admin. Menonaktifkan seri dan membatalkan sesi mendatangnya. Booking terkait menjadi `session_cancelled`. Response `200` ClassSeries. Idempoten.

**GET /v1/gyms/{gymId}/class-sessions?from=&to=**
- Akses: admin (semua status) dan member (hanya `scheduled`). `from` dan `to` adalah tanggal `local_date`, inklusif, rentang maks 31 hari.
- Response `{ items: [ClassSession] }` urut `starts_at ASC`. Daftar tidak dipaginasi karena rentang dibatasi.

**GET /v1/gyms/{gymId}/class-sessions/{sessionId}** (RV2-05)
- Akses: admin dan member. Member hanya untuk sesi `scheduled`, selain itu `404`. Response ClassSession.

**PATCH /v1/gyms/{gymId}/class-sessions/{sessionId}**
- Akses: admin. Body opsional minimal satu: `name`, `instructorName`, `startsAt`, `durationMinutes`, `capacity`. Response `200`.
- Error: `404`, `409 CONFLICT` (kapasitas di bawah jumlah peserta, atau sesi sudah `cancelled`), `422 details.startsAt` (RV2-03).
- Sesi dengan `series_id`: `startsAt` baru wajib jatuh di `local_date` yang sama. Sesi satu kali bebas digeser dan `local_date` dihitung ulang.

**POST /v1/gyms/{gymId}/class-sessions/{sessionId}/cancel**
- Akses: admin. Status menjadi `cancelled`, booking `booked` menjadi `session_cancelled`. Response `200`. Idempoten.

**POST /v1/gyms/{gymId}/class-sessions/{sessionId}/bookings**
- Akses: member. Tanpa body. Response `201`: `{ id, sessionId, status, createdAt }`.
- Error: `404` (sesi tidak ada atau bukan `scheduled`), `409 MEMBERSHIP_INACTIVE`, `409 CLASS_FULL`, `409 BOOKING_CLOSED` (kelas sudah dimulai), `409 CONFLICT` (sudah booking).

**DELETE /v1/gyms/{gymId}/bookings/{bookingId}**
- Akses: member pemilik booking. Response `204`.
- Error: `404`, `409 BOOKING_CLOSED` (lewat batas pembatalan), `409 CONFLICT` (sudah dibatalkan).

**GET /v1/gyms/{gymId}/me/bookings?upcoming=&limit=&cursor=**
- Akses: member. `upcoming=true` hanya sesi mendatang dengan status `booked`. Response `BookingPage` berisi `{ id, status, session: ClassSession }`.

**GET /v1/gyms/{gymId}/class-sessions/{sessionId}/bookings**
- Akses: admin. Response `{ items: [{ bookingId, memberId, memberName, createdAt }] }` hanya status `booked`, bersama `session: ClassSession` supaya halaman detail mendapat "N / kapasitas". Error: `404`.

## 6. Functional Requirements

### FR-01: Login dan pembuatan user otomatis
Admin dan member login dengan Firebase Auth. Server memverifikasi token dan membuat baris `users` pada request pertama (`syncUser` di conventions). User baru tidak punya peran sampai menebus undangan atau diberi peran lewat CLI (RV-06). Fase 0 hanya berisi login, pembuatan user, dan peran. Penautan ke member ada di FR-10 (RV-03).
Fitur: F-01
Acceptance criteria:
- [ ] Given user belum ada di database, When ia memanggil `GET /v1/me` dengan token valid, Then baris `users` dibuat dan `accounts` berisi array kosong.
- [ ] Given token tidak valid atau tidak ada, When memanggil endpoint `/v1/*`, Then respons `401`.
- [ ] Given user baru login, When memanggil endpoint gym mana pun, Then `404` (tanpa peran, tanpa akses).
- [ ] Given user login di app, When akun belum punya peran, Then app menampilkan layar memasukkan kode undangan, bukan beranda.
- [ ] Given user menekan logout, When sesi berakhir, Then token perangkat push dihapus (fase 5) dan app kembali ke layar login.
Edge cases:
- Email berubah di Firebase, sehingga baris `users` ikut diperbarui oleh `syncUser`.
- Dua request pertama bersamaan, dan upsert tetap menghasilkan satu baris.

### FR-02: Admin pertama lewat CLI
Admin pertama dibuat lewat skrip `seed:first-admin`, bukan lewat API (RV-06).
Fitur: F-02
Acceptance criteria:
- [ ] Given database kosong, When skrip dijalankan dengan `--email`, Then baris `gyms` dibuat (zona `Asia/Jakarta` bila tidak diberi) dan pengaturan memakai nilai default.
- [ ] Given user dengan email itu sudah pernah login, When skrip dijalankan, Then ia mendapat `gym_accounts` role `admin`.
- [ ] Given user belum pernah login, When skrip dijalankan, Then skrip mencetak satu kode undangan admin dan tidak membuat `users`.
- [ ] Given skrip dijalankan dua kali dengan argumen sama, Then tidak ada baris ganda dan tidak error.
- [ ] Given user baru mana pun login, Then tidak pernah otomatis mendapat peran admin.
Edge cases:
- Email berbeda huruf besar-kecil diperlakukan sama.
- Gym sudah ada, sehingga skrip tidak membuat gym kedua.

### FR-03: Profil gym dan pengaturan
Admin mengelola nama, alamat, zona waktu, dan pengaturan operasional gym (`expiringSoonDays`, `cancelCutoffMinutes`, `qrRotationSeconds`, `classReminderMinutes`) (RV-09).
Fitur: F-02
Acceptance criteria:
- [ ] Given admin, When `PATCH /gyms/{gymId}` dengan `timezone` valid, Then gym diperbarui dan status/tanggal berikutnya memakai zona baru.
- [ ] Given zona waktu bukan IANA, When PATCH, Then `422 details.timezone`.
- [ ] Given member, When PATCH, Then `403`.
- [ ] Given gym baru, Then default 7 hari, 120 menit, 30 detik, dan 60 menit.
Edge cases:
- Body kosong → `422 details._root`.
- `expiringSoonDays` 0 atau 31 → `422`.

### FR-04: Peran dan pembatasan akses
Admin mengelola semua data gym. Member hanya mengakses datanya sendiri lewat endpoint `/me/*` dan membaca paket, jadwal, dan sesi.
Fitur: F-02
Acceptance criteria:
- [ ] Given member, When memanggil endpoint admin (misalnya `GET /members`), Then `403`.
- [ ] Given user yang bukan anggota gym, When memanggil endpoint gym, Then `404`.
- [ ] Given member A, When mengakses `GET /me/payments`, Then hanya pembayaran miliknya yang tampil.
- [ ] Given member, When membuka detail sesi kelas yang `cancelled`, Then `404`.
- [ ] Given route baru, Then `all-routes-require-auth.int.test.ts` lulus dan hanya `/webhooks/midtrans` di `PUBLIC_ROUTES`.
Edge cases:
- `gymId` bukan UUID → `422 details.gymId`.
- Peran dicek di use case dan teruji unit test (lihat bagian Organisasi dan tenancy di conventions).

### FR-05: Kelola admin (cabut dan jaga admin terakhir)
Admin baru hanya lewat undangan admin atau CLI. Admin dapat dicabut asalkan gym tetap punya minimal satu admin. Operasi dikunci di baris `gyms` (RV2-02).
Fitur: F-02
Acceptance criteria:
- [ ] Given dua admin, When salah satu mencabut yang lain, Then `204` dan tersisa satu admin.
- [ ] Given satu admin, When ia mencabut dirinya, Then `409 LAST_ADMIN` dan perannya tetap.
- [ ] Given admin A dan B, When A mencabut B dan B mencabut A bersamaan, Then tepat satu berhasil dan satu mendapat `409 LAST_ADMIN`, dan gym tetap punya satu admin.
- [ ] Given pencabutan atau penghapusan akun admin, Then transaksi menjalankan `SELECT ... FROM gyms WHERE id=$1 FOR UPDATE` sebelum menghitung admin.
- [ ] Given integration test, Then tersedia test cabut-silang bersamaan, dan test dua admin terakhir menghapus akun bersamaan.
Edge cases:
- Mencabut user yang bukan admin → `404`.
- Admin yang dicabut tetap bisa menjadi member bila punya akun member terpisah.

### FR-06: Paket membership
Admin menambah, mengubah, dan menonaktifkan paket. Paket tidak dihapus supaya riwayat tetap utuh.
Fitur: F-03
Acceptance criteria:
- [ ] Given admin, When membuat paket "Bulanan" 1 month Rp150.000, Then `201` dan paket muncul di daftar aktif.
- [ ] Given nama "bulanan" sudah ada, When membuat "Bulanan", Then `409 CONFLICT`.
- [ ] Given paket dinonaktifkan, When admin menambah member dengan paket itu, Then `422 details.planId`.
- [ ] Given member, When `GET /plans`, Then hanya paket aktif yang dikembalikan.
- [ ] Given admin mengubah durasi paket, Then member dan pembayaran yang sudah ada tidak berubah.
Edge cases:
- `durationValue` 0 atau negatif → `422`.
- Harga 0 → `422`.

### FR-07: Tambah member baru beserta paket
Aksi pertama admin: membuat member dengan paket awal. Masa aktif awal dihitung dari `startOn` ditambah durasi paket. Tidak boleh di masa depan (RV2-04).
Fitur: F-04
Acceptance criteria:
- [ ] Given admin, When `POST /members` dengan `startOn` hari ini, paket 1 month, Then `201` dengan `expiresOn` = `addDuration(startOn, 1 month)` dan status `active`.
- [ ] Given `startOn` besok, Then `422 details.startOn`.
- [ ] Given `startOn` 31 hari lalu, Then `422 details.startOn`.
- [ ] Given `startOn` 10 hari lalu dan paket 1 week, Then `expiresOn` sudah lewat dan status `expired`.
- [ ] Given `paymentMethod: 'cash'`, Then dibuat pembayaran `paid` dengan snapshot paket (nama, durasi, harga) dan periode terisi, sehingga tidak ada perpanjangan ganda.
- [ ] Given nomor HP sudah dipakai member lain yang belum terhapus, Then `409 CONFLICT`.
Edge cases:
- Nomor HP dinormalisasi (spasi dan tanda hubung dibuang).
- `startOn` 31 Jan + paket 1 month → `expiresOn` 28/29 Feb.
- Tanpa `paymentMethod`, tidak ada baris pembayaran.

### FR-08: Ubah data member dan foto
Admin mengubah nama, nomor HP, email, dan foto. Foto hanya lewat API, dan Storage tidak bisa diakses langsung dari client (RV-05).
Fitur: F-04
Acceptance criteria:
- [ ] Given admin, When PATCH nama, Then `200` dan detail menampilkan nama baru.
- [ ] Given file JPEG 1 MB, When `PUT /members/{id}/photo`, Then `200` dengan `photoUrl` signed URL yang kedaluwarsa dalam 5 menit.
- [ ] Given file 3 MB atau bertipe GIF, Then `422 details.file`.
- [ ] Given `storage.rules`, Then semua baca dan tulis dari client ditolak.
- [ ] Given member lain mencoba mengambil foto, Then tidak ada endpoint yang memberikan signed URL milik member lain (hanya admin dan pemilik via `/me/member`).
Edge cases:
- Unggah ulang menimpa foto lama.
- Foto gagal disimpan, sehingga `photo_path` tidak berubah.

### FR-09: Daftar dan detail member
Admin mencari dan memfilter member, lalu melihat detail beserta riwayat pembayaran dan check-in.
Fitur: F-04
Acceptance criteria:
- [ ] Given 25 member, When `GET /members?limit=20`, Then 20 item dan `nextCursor` terisi, halaman kedua berisi 5 item dan `nextCursor: null`.
- [ ] Given `status=expiring_soon`, Then hanya member dengan sisa 0–7 hari yang tampil.
- [ ] Given `q=budi`, Then member dengan nama diawali "Budi" (tanpa membedakan huruf besar-kecil) tampil.
- [ ] Given detail member, Then app menampilkan paket, status, riwayat pembayaran (FR-15), dan riwayat check-in (FR-22).
- [ ] Given member yang akunnya sudah dihapus (FR-11), Then tidak tampil di daftar.
Edge cases:
- Cursor rusak → `422 details.cursor`.
- Halaman detail bisa di-deep-link dan di-refresh karena memakai `GET /members/{memberId}`.

### FR-10: Undangan dan penautan akun ke member
Penautan hanya lewat kode undangan sekali pakai dari admin, tidak lewat kecocokan email atau nomor HP yang belum terverifikasi (RV-02, RV-03). Undangan admin memakai alur yang sama.
Fitur: F-04
Acceptance criteria:
- [ ] Given admin, When membuat undangan untuk member yang belum ditautkan, Then `201` dengan `code` yang hanya tampil sekali dan `expiresAt` 48 jam.
- [ ] Given user login tanpa peran, When menebus kode valid, Then dibuat `gym_accounts` role `member`, `members.user_id` terisi, dan undangan bertanda `used_at`, semuanya dalam satu transaksi.
- [ ] Given kode sudah dipakai, kedaluwarsa, dicabut, atau salah, When ditebus, Then `422 INVITE_INVALID` dengan pesan yang sama untuk semua kasus (tidak membocorkan alasan).
- [ ] Given dua user menebus kode yang sama bersamaan, Then tepat satu berhasil.
- [ ] Given 10 percobaan kode salah dalam 15 menit oleh satu user, When percobaan berikutnya, Then `429 RATE_LIMITED`.
- [ ] Given member sudah ditautkan, When admin membuat undangan lagi, Then `409 CONFLICT`.
- [ ] Given undangan admin ditebus, Then user mendapat `gym_accounts` role `admin` dalam transaksi yang mengunci baris `gyms` (RV2-02).
Edge cases:
- User yang sudah punya akun di gym itu menebus kode → `409 CONFLICT`.
- Admin membuat undangan baru untuk member yang sama, sehingga undangan lama dicabut otomatis.
- Kode tidak pernah muncul di log atau disimpan polos.

### FR-11: Hapus akun dari halaman profil
Aplikasi menyediakan tombol hapus akun di halaman profil dengan konfirmasi (syarat App Store dan Google Play) (RV-10).
Fitur: F-01 (dikerjakan di fase 1, setelah F-04)
Acceptance criteria:
- [ ] Given member, When `DELETE /v1/me`, Then baris `users`, `gym_accounts`, dan `device_tokens` dihapus.
- [ ] Given member terhapus, Then data member dianonimkan: `name` menjadi "Member Terhapus", `phone` dan `email` dikosongkan, foto dihapus dari Storage, `deleted_at` terisi.
- [ ] Given member terhapus, Then riwayat pembayaran dan check-in tetap tersimpan untuk pembukuan.
- [ ] Given member punya booking mendatang, Then booking itu menjadi `cancelled`.
- [ ] Given pembayaran online `pending` milik member terhapus, Then statusnya menjadi `expired`.
- [ ] Given admin terakhir, When hapus akun, Then `409 LAST_ADMIN` dan tidak ada yang berubah.
- [ ] Given dua admin terakhir menghapus akun bersamaan, Then tepat satu berhasil (kunci `gyms ... FOR UPDATE`, RV2-02).
- [ ] Given API sukses, Then app menghapus akun Firebase (dengan login ulang bila diminta) lalu kembali ke layar login.
Edge cases:
- Pembayaran online yang lunas setelah member dihapus tidak memperpanjang apa pun dan masuk `needs_review` (FR-18).
- Gagal menghapus akun Firebase tidak mengembalikan data. Login ulang membuat user baru tanpa peran.
- Sebuah akun yang juga admin dan bukan yang terakhir boleh dihapus.

### FR-12: Status masa aktif
Status dihitung di server dari `expires_on` dan "hari ini" di zona gym. Member aktif sampai akhir hari `expires_on`, tanpa masa tenggang (RV-07, RV-09).
Fitur: F-05
Acceptance criteria:
- [ ] Given `expires_on` = hari ini, Then status `expiring_soon` dan `daysRemaining` 0 (masih bisa check-in).
- [ ] Given `expires_on` = kemarin, Then status `expired` dan `daysRemaining` negatif atau 0, serta check-in ditolak.
- [ ] Given `expires_on` = hari ini + 7, Then `expiring_soon`. Given hari ini + 8, Then `active`.
- [ ] Given pukul 23:30 WIB (16:30 UTC) dengan `expires_on` hari itu, Then tetap aktif. Pukul 00:01 WIB hari berikutnya, Then `expired`.
- [ ] Given admin mengubah `expiringSoonDays` menjadi 14, Then ambang berlaku untuk semua tampilan berikutnya.
- [ ] Given app, Then admin dapat memfilter daftar member "hampir habis" dan "kedaluwarsa" (FR-09).
Edge cases:
- Gym mengubah zona waktu, dan status mengikuti zona terbaru.
- Server tidak pernah memakai zona waktu perangkat client.

### FR-13: Member melihat status dan tanggal kedaluwarsa
Member melihat paket, status, tanggal kedaluwarsa, dan tombol perpanjang.
Fitur: F-05
Acceptance criteria:
- [ ] Given member tertaut, When membuka beranda, Then app memanggil `GET /me/member` dan menampilkan status serta tanggal.
- [ ] Given status `expired`, Then app menampilkan "Kedaluwarsa" dan tombol perpanjang (aktif setelah F-07).
- [ ] Given akun admin tanpa data member, Then `GET /me/member` `404` dan app tidak menampilkan layar member.
Edge cases:
- Pull-to-refresh memuat ulang data (tidak ada realtime).

### FR-14: Pembayaran manual dan aturan perpanjangan
Admin mencatat pembayaran tunai atau transfer. Pembayaran `paid` memperpanjang masa aktif. Aturan ada di satu fungsi `computeRenewalPeriod`, dipakai juga oleh F-07 (RV-07, RV2-01).
Fitur: F-06
Acceptance criteria:
- [ ] Given member dengan `expires_on` 20 hari lagi, When pembayaran paket 1 month dicatat, Then `expires_on` baru = `addDuration(expires_on lama, 1 month)` (lanjut dari tanggal kedaluwarsa).
- [ ] Given `expires_on` kemarin, When pembayaran dicatat hari ini, Then `expires_on` baru = `addDuration(hari ini, durasi)` (dari tanggal bayar), tanpa masa tenggang.
- [ ] Given `expires_on` = hari ini, Then dihitung dari `expires_on` (masih aktif).
- [ ] Given pembayaran dibuat, Then baris `payments` menyimpan `plan_name`, `amount`, `plan_duration_value`, dan `plan_duration_unit`, dan `computeRenewalPeriod` membaca durasi dari snapshot ini.
- [ ] Given pembayaran online berstatus `pending` dengan snapshot 1 month, When admin mengubah durasi paket menjadi 3 month lalu pembayaran lunas, Then perpanjangan tetap 1 month (RV2-01).
- [ ] Given dua pembayaran dicatat bersamaan untuk member yang sama, Then keduanya berurutan (kunci `members FOR UPDATE`) dan masa aktif bertambah dua kali durasi.
- [ ] Given pembayaran sukses, Then `members.plan_id` menjadi paket yang dibayar dan `payments.period_start_on`/`period_end_on`/`applied_at` terisi.
Edge cases:
- Paket nonaktif → `422`.
- 31 Jan + 1 month → 28/29 Feb.
- Member terhapus → `404`.

### FR-15: Riwayat dan daftar pembayaran
Admin melihat daftar pembayaran dengan filter, dan member melihat riwayat sendiri.
Fitur: F-06
Acceptance criteria:
- [ ] Given `from` dan `to`, When `GET /payments`, Then hanya pembayaran dengan tanggal `created_at` di zona gym dalam rentang itu.
- [ ] Given `status=needs_review`, Then hanya pembayaran yang perlu ditindaklanjuti tampil, dan UI admin menyediakan filter status tersebut.
- [ ] Given member, When `GET /me/payments`, Then hanya miliknya.
- [ ] Given status `needs_review`, Then member melihat teks "Pembayaran sedang ditinjau admin", status `pending` melihat "Menunggu pembayaran".
Edge cases:
- Pagination `created_at DESC, id DESC`, tanpa duplikat saat milidetik sama.

### FR-16: Ekspor laporan member dan pembayaran
Admin mengunduh CSV member dan pembayaran untuk pembukuan.
Fitur: R-06
Acceptance criteria:
- [ ] Given admin, When `GET /exports/members`, Then CSV UTF-8 dengan BOM dan header `nama,nomor_hp,email,paket,tanggal_kedaluwarsa,status`.
- [ ] Given `GET /exports/payments?from=2026-01-01&to=2026-01-31`, Then semua pembayaran dalam rentang (zona gym) ikut, termasuk status `needs_review`.
- [ ] Given rentang lebih dari 366 hari atau `from` kosong, Then `422`.
- [ ] Given nama berawalan `=`, `+`, `-`, atau `@`, Then sel diawali `'` untuk mencegah formula injection, dan koma/kutip di-escape.
- [ ] Given member, When mengakses ekspor, Then `403`.
- [ ] Given member terhapus, Then CSV member tidak memuatnya, sedangkan CSV pembayaran memuat nama "Member Terhapus".
Edge cases:
- Hasil kosong tetap berisi baris header.
- Di web, app mengunduh dengan header Authorization lalu menyimpan sebagai file.

### FR-17: Mulai pembayaran online
Member memilih paket dan membayar lewat Midtrans Snap. Pembayaran berlaku 60 menit (RV-08).
Fitur: F-07
Acceptance criteria:
- [ ] Given member dan paket aktif, When `POST /me/payments/online`, Then baris `payments` `pending` dibuat dengan snapshot nama, durasi, dan harga, `expires_at` = sekarang + 60 menit, dan `redirectUrl` dikembalikan.
- [ ] Given `PaymentGateway` memakai adapter `fake`, Then alur lengkap teruji tanpa jaringan.
- [ ] Given gateway gagal membuat transaksi, Then `500 INTERNAL_ERROR` dan tidak ada baris `payments` tersisa.
- [ ] Given app, When member kembali dari halaman bayar, Then app memanggil `GET /me/payments/{id}` dan menampilkan status terbaru.
- [ ] Given order_id gateway, Then sama dengan `payments.id`.
Edge cases:
- Member mulai dua pembayaran online untuk paket sama, dan keduanya `pending` independen. Bila keduanya lunas, keduanya memperpanjang.
- Kartu kredit tidak diaktifkan, hanya QRIS, VA (BCA, BNI, BRI, Mandiri), dan GoPay.

### FR-18: Webhook pembayaran
Perpanjangan dari pembayaran online hanya diproses dari webhook yang tanda tangannya valid, aman dari pemrosesan ganda.
Fitur: F-07
Acceptance criteria:
- [ ] Given tanda tangan salah, When webhook diterima, Then `401` dan tidak ada perubahan data.
- [ ] Given notifikasi `settlement` dengan `gross_amount` sama dengan `payments.amount`, When diproses, Then status `paid`, `paid_at` terisi, dan masa aktif diperpanjang sesuai FR-14.
- [ ] Given notifikasi yang sama dikirim dua kali atau bersamaan, Then perpanjangan terjadi satu kali (`event_key` unik dan `applied_at`).
- [ ] Given `gross_amount` tidak sama dengan `payments.amount`, Then status menjadi `needs_review`, masa aktif tidak diperpanjang, dan kejadian dicatat di log tanpa data sensitif (RV2-06).
- [ ] Given status `expired` dan notifikasi `settlement` datang kemudian, Then pembayaran menjadi `paid` dan diperpanjang (uang sudah masuk).
- [ ] Given notifikasi `deny` atau `cancel`, Then `failed`. Notifikasi `expire`, Then `expired`. Notifikasi `pending`, Then tidak ada perubahan.
- [ ] Given pembayaran sudah `paid` atau `needs_review`, Then notifikasi lanjutan diabaikan dengan `200`.
- [ ] Given member sudah terhapus (FR-11), When `settlement` diterima, Then status `needs_review`.
Edge cases:
- `order_id` tidak dikenal → `404`.
- Transisi `failed` ke `paid` tidak diizinkan, dan transisi dikunci dengan `payments FOR UPDATE`.
- Tanda tangan diverifikasi dari body mentah sebelum JSON diparse.

### FR-19: Rekonsiliasi pembayaran online
Job `payments.reconcile` memeriksa pembayaran `pending` ke gateway bila webhook terlambat atau hilang (cron `*/10 * * * *`, di `features/payments/jobs/`).
Fitur: F-07
Acceptance criteria:
- [ ] Given pembayaran `pending` berumur lebih dari 5 menit dan gateway menjawab lunas, When job berjalan, Then diproses lewat use case yang sama dengan webhook (FR-18).
- [ ] Given pembayaran `pending` melewati `expires_at` dan gateway menjawab `expire`, Then status `expired`.
- [ ] Given pembayaran `needs_review`, Then tidak diperiksa job (dikecualikan dari kueri).
- [ ] Given job berjalan dua kali, Then hasil sama dan tidak ada perpanjangan ganda.
- [ ] Given gateway error untuk satu pembayaran, Then error dicatat dan pembayaran lain tetap diproses.
Edge cases:
- Job berjalan hanya bila `RUN_WORKER=true`.
- Pembayaran yang sudah `expired` tidak diperiksa lagi. Pelunasan setelahnya masuk lewat webhook.

### FR-20: QR dinamis di aplikasi member
Member menampilkan QR berisi token bertanda tangan server yang berganti tiap 30 detik (RV-09).
Fitur: F-08
Acceptance criteria:
- [ ] Given member aktif, When `GET /me/qr-token`, Then token HMAC dengan `memberId`, `jti` acak, dan `exp` = sekarang + `qrRotationSeconds` (+ toleransi 5 detik saat verifikasi).
- [ ] Given layar QR terbuka, Then app memuat token baru otomatis tiap `rotateInSeconds`.
- [ ] Given member `expired`, Then `409 MEMBERSHIP_INACTIVE` dan app menampilkan ajakan perpanjang.
- [ ] Given dua panggilan berurutan, Then `jti` berbeda.
Edge cases:
- Kunci penandatangan berasal dari env dan tidak pernah dicatat di log.
- Perangkat dengan jam salah tidak berpengaruh karena `exp` diverifikasi dengan jam server.

### FR-21: Admin memindai QR untuk check-in
Admin memindai QR dengan kamera di web, lalu server memvalidasi dan mencatat check-in.
Fitur: F-08
Acceptance criteria:
- [ ] Given QR valid dan member aktif, When `POST /check-ins`, Then `201` dengan nama, foto (signed URL), dan tanggal kedaluwarsa untuk diverifikasi visual oleh admin.
- [ ] Given QR yang sama dipindai dua kali, Then yang kedua `422 QR_INVALID` (`jti` unik).
- [ ] Given QR lebih dari 30 detik (+5 detik toleransi), Then `422 QR_INVALID`.
- [ ] Given tanda tangan diubah, Then `422 QR_INVALID`.
- [ ] Given member `expired` (kemarin), Then `409 MEMBERSHIP_INACTIVE` dan tidak ada baris `check_ins`.
- [ ] Given member terhapus atau tidak ada, Then `422 QR_INVALID`.
- [ ] Given akun member, When memanggil endpoint ini, Then `403`.
Edge cases:
- Izin kamera ditolak, dan app menyediakan input token manual.
- Screenshot QR lama tidak berguna karena umur pendek dan sekali pakai.

### FR-22: Riwayat check-in
Member dan admin melihat riwayat kehadiran.
Fitur: F-08
Acceptance criteria:
- [ ] Given member, When `GET /me/check-ins`, Then hanya check-in miliknya, urut terbaru dulu.
- [ ] Given admin, When `GET /check-ins?memberId=&from=&to=`, Then difilter sesuai parameter.
- [ ] Given detail member (FR-09), Then riwayat check-in tampil.

### FR-23: Jadwal kelas satu kali
Admin membuat, mengubah, dan membatalkan kelas satu kali.
Fitur: F-09
Acceptance criteria:
- [ ] Given admin, When `POST /class-sessions` dengan `startsAt` masa depan, Then `201`, `local_date` dihitung server di zona gym, dan `status` `scheduled`.
- [ ] Given `startsAt` masa lalu, Then `422 details.startsAt`.
- [ ] Given PATCH `startsAt` ke tanggal lain pada kelas satu kali, Then diterima dan `local_date` dihitung ulang (RV2-03).
- [ ] Given kapasitas diubah di bawah jumlah peserta `booked`, Then `409 CONFLICT`.
- [ ] Given pembatalan, Then status `cancelled` dan booking menjadi `session_cancelled`.
Edge cases:
- Membatalkan dua kali, idempoten (`200`).
- Mengubah sesi `cancelled` → `409 CONFLICT`.

### FR-24: Seri kelas mingguan dan generator sesi
Seri mingguan menghasilkan sesi per minggu lewat job harian dan saat seri dibuat.
Fitur: F-09
Acceptance criteria:
- [ ] Given seri Senin 18:00 mulai `startsOn` hari Senin, When dibuat, Then sesi 28 hari ke depan langsung ada, masing-masing `starts_at` 18:00 waktu gym dan `local_date` yang sesuai.
- [ ] Given `startsOn` bukan hari `weekday`, Then `422 details.weekday`.
- [ ] Given job `classes.generate-sessions` (cron `0 20 * * *` UTC) berjalan dua kali, Then tidak ada sesi ganda (UNIQUE `(series_id, local_date)` dan `ON CONFLICT DO NOTHING`).
- [ ] Given sesi seri dibatalkan atau digeser (FR-25), When job berjalan, Then tidak dibuat ulang di tanggal yang sama.
- [ ] Given `endsOn` terlewati atau seri nonaktif, Then job berhenti membuat sesi.
- [ ] Given pergantian jam musim di zona gym, Then `starts_at` tetap menunjukkan jam lokal yang sama.
Edge cases:
- Seri berakhir di tengah horizon, dan sesi setelah `endsOn` tidak dibuat.
- Job hanya aktif bila `RUN_WORKER=true`.

### FR-25: Ubah dan batalkan sesi atau seri
Admin mengubah sesi individual atau seluruh seri (RV2-03, RV2-05).
Fitur: F-09
Acceptance criteria:
- [ ] Given sesi dengan `series_id` pada tanggal lokal 2026-11-02, When PATCH `startsAt` ke 2026-11-02 19:00 waktu gym, Then `200` dan `local_date` tetap 2026-11-02.
- [ ] Given sesi seri yang sama, When PATCH `startsAt` ke 2026-11-03, Then `422 details.startsAt` dan data tidak berubah.
- [ ] Given PATCH seri `capacity` atau `startTime`, Then sesi `scheduled` yang belum mulai ikut berubah, dan sesi lampau tidak.
- [ ] Given `POST /class-series/{id}/cancel`, Then `is_active=false`, sesi mendatang `cancelled`, booking `session_cancelled`.
- [ ] Given halaman form edit dibuka lewat URL langsung, Then data diisi dari `GET /class-sessions/{sessionId}` atau `GET /class-series/{seriesId}`.
Edge cases:
- Mengubah `startTime` seri tidak menggeser `local_date`.
- Mengubah sesi yang sudah dimulai ditolak dengan `409 CONFLICT`.

### FR-26: Lihat jadwal dan detail sesi
Member melihat jadwal dengan sisa kuota. Admin melihat detail sesi dengan peserta (RV2-05).

- [ ] Given admin, Then semua status ikut tampil.
- [ ] Given rentang lebih dari 31 hari, Then `422`.
- [ ] Given admin membuka halaman detail sesi lewat URL langsung atau refresh, Then app memanggil `GET /class-sessions/{sessionId}` dan `GET /class-sessions/{sessionId}/bookings`, dan menampilkan daftar peserta serta "N / kapasitas".

### FR-27: Booking kelas dengan kuota atomik
Member aktif memesan slot. Kuota dan pembuatan booking atomik di server.
Fitur: F-10
Acceptance criteria:
- [ ] Given sisa 1 slot dan 2 member booking bersamaan, Then satu `201` dan satu `409 CLASS_FULL`.
- [ ] Given integration test 50 permintaan paralel dari 50 member pada kapasitas 10, Then tepat 10 booking `booked`.
- [ ] Given member sudah punya booking `booked` di sesi itu, Then `409 CONFLICT`.
- [ ] Given `expires_on` member lebih awal dari `local_date` sesi, Then `409 MEMBERSHIP_INACTIVE` (aktif pada hari kelas, bukan hanya hari ini).
- [ ] Given member `expired` hari ini, Then `409 MEMBERSHIP_INACTIVE`.

### FR-28: Pembatalan booking

### FR-30: Registrasi token perangkat dan infrastruktur push
Aplikasi mendaftarkan token FCM per perangkat, dan server mengirim push lewat port `PushSender` (RV-04).
Fitur: R-01 (infrastruktur bersama dengan R-03)
Acceptance criteria:
- [ ] Given user login di Android atau iOS, When app memperoleh token FCM, Then `POST /me/device-tokens` meng-upsert token.
- [ ] Given token sama didaftarkan oleh akun lain, Then kepemilikan pindah ke akun terbaru.
- [ ] Given `PushSender` mengembalikan `invalid-token`, Then baris token dihapus.
- [ ] Given logout, Then `POST /me/device-tokens/remove` dipanggil.
- [ ] Given produksi, Then `PUSH_ADAPTER=fcm`. Given `fake`, Then `loadEnv()` menolak di `NODE_ENV=production`.
- [ ] Given iOS, Then kunci APNs terpasang di Firebase sebelum rilis.

### FR-31: Pengingat masa aktif hampir habis
Job harian mengirim push ke member yang masa aktifnya hampir habis.
Fitur: R-01
Acceptance criteria:
- [ ] Given member `expires_on` = hari ini + 7 (sama dengan `expiringSoonDays`) dan punya token, When job `notifications.expiry-reminder` (cron `0 2 * * *` UTC) berjalan, Then satu push dikirim dan `notification_log` mencatat `dedupe_key = expiry:<memberId>:<expiresOn>:7`.
- [ ] Given `expires_on` = hari ini + 1, Then satu push lagi dengan kunci `...:1`.
- [ ] Given job berjalan dua kali di hari yang sama, Then tidak ada push ganda (UNIQUE `dedupe_key`).
- [ ] Given member sudah memperpanjang sehingga `expires_on` berubah, Then pengingat memakai tanggal baru.
- [ ] Given member tanpa akun atau tanpa token, Then dilewati tanpa error.
- [ ] Given member terhapus, Then dilewati.
- [ ] Given satu pengiriman gagal, Then pengiriman lain tetap berjalan dan error dicatat.
Edge cases:
- Teks notifikasi menyebut tanggal kedaluwarsa dalam format lokal.
- Dikirim ke semua token user (banyak perangkat).

### FR-32: Pengingat jadwal kelas
Job berkala mengirim push ke member yang sudah booking sebelum kelas dimulai.
Fitur: R-03

- [ ] Given booking `booked` untuk sesi `scheduled` yang mulai dalam ≤ 60 menit (`classReminderMinutes`), When job `notifications.class-reminder` (cron `*/5 * * * *`) berjalan, Then satu push dikirim dengan `dedupe_key = class:<bookingId>`.
- [ ] Given job berjalan berulang dalam jendela waktu, Then tidak ada push ganda.
- [ ] Given booking dibatalkan atau sesi dibatalkan, Then tidak ada push.
- [ ] Given booking dibuat kurang dari 60 menit sebelum mulai, Then tidak ada pengingat.
- [ ] Given admin mengubah `classReminderMinutes`, Then jendela baru dipakai.

- Jam sesi digeser admin setelah pengingat terkirim, sehingga tidak ada pengingat kedua.

## 7. Non-Functional Requirements

- **NFR-01 (Kinerja):** `GET /members` dengan 5.000 member dan `GET /payments` dengan 50.000 baris memiliki p95 kurang dari 300 ms, dan `EXPLAIN` memakai index pagination tanpa `Sort`.
- **NFR-02 (Konkurensi booking):** Test integrasi 50 booking paralel pada kapasitas 10 selalu menghasilkan tepat 10 booking `booked`, tanpa deadlock, dalam 20 kali pengulangan.
- **NFR-03 (Idempotensi pembayaran):** Webhook yang sama dikirim 10 kali paralel menghasilkan satu perpanjangan dan satu baris `payment_webhook_events`. Job `payments.reconcile`, `classes.generate-sessions`, `notifications.expiry-reminder`, dan `notifications.class-reminder` hasilnya sama bila dijalankan dua kali berturut-turut (dijaga test integrasi).
- **NFR-04 (Konsistensi waktu):** Semua penentuan status, `local_date`, dan "hari ini" memakai zona gym dan jam database. Ada test unit dan integrasi untuk batas 23:59 dan 00:00 lokal, dan untuk zona dengan offset berbeda dari UTC.
- **NFR-05 (Keamanan data):** Semua trafik HTTPS. Setiap query repository memfilter `gym_id` dan, bila relevan, `member_id` pemilik. Test integrasi memastikan member A tidak bisa membaca pembayaran, QR, check-in, atau booking member B.
- **NFR-06 (Foto):** Storage dikunci penuh (`storage.rules` menolak semuanya). Signed URL berumur maksimal 5 menit. Tidak ada URL publik permanen.
- **NFR-07 (Privasi log):** Log tidak pernah memuat ID token, kode undangan, token QR, token perangkat, payload kartu, atau nomor HP. Test memeriksa log pada skenario kode undangan salah dan webhook tanda tangan salah.
- **NFR-08 (Ketahanan webhook):** Verifikasi tanda tangan memakai perbandingan waktu-konstan. Webhook dijawab dalam kurang dari 2 detik pada p95 supaya gateway tidak mengulang.
- **NFR-09 (Undangan):** Kode undangan memiliki entropi minimal 40 bit, berlaku 48 jam, dan hanya hash SHA-256 yang disimpan. Percobaan tebus dibatasi 10 per 15 menit per user.
- **NFR-10 (Ekspor):** Ekspor 50.000 baris selesai dalam kurang dari 10 detik dan memakai streaming tanpa memuat semua baris di memori. Sel CSV dilindungi dari formula injection.
- **NFR-11 (Kontrak dan kualitas):** `pnpm check` lulus: lint, `contract:check` (OpenAPI dan client Dart sinkron), Vitest API, dan flutter_test. Setiap use case punya unit test dengan repository palsu, dan setiap endpoint punya integration test untuk kasus sukses, `401`, `403`/`404`, dan `422`.
- **NFR-12 (Operasional job):** pg-boss hanya berjalan bila `RUN_WORKER=true` dan berhenti rapi saat `SIGTERM` (lihat bagian Job dan Shutdown di conventions). Kegagalan satu item dalam job tidak menghentikan item lain.
- **NFR-13 (Kepatuhan store):** Halaman profil menyediakan hapus akun yang selesai dalam satu alur kurang dari 3 langkah, dan penghapusan data selesai dalam satu transaksi database. Data yang dipertahankan (pembayaran, check-in) sudah tanpa data pribadi.
- **NFR-14 (Penggantian gateway):** Seluruh kode Midtrans berada di adapter `PaymentGateway`. Use case dan route tidak mengimpor SDK atau tipe Midtrans, dan test use case memakai adapter `fake`.
