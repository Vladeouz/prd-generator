# Aplikasi Membership Gym

## 1. Context & Goal

Pencatatan member dan masa aktif di sebuah gym masih manual dan berantakan. Aplikasi ini merapikannya untuk **satu gym** (versi pertama). Admin dan member sama-sama memakainya.

- **Admin** (dipakai terutama lewat web) mengelola paket membership, data member, pembayaran, jadwal kelas, dan memindai QR check-in.
- **Member** (HP Android/iOS, atau web) melihat status dan tanggal kedaluwarsa, menampilkan QR check-in, membayar perpanjangan lewat payment gateway, dan membooking kelas.

**Aksi pertama pengguna:** admin menambahkan member baru beserta paketnya.

**Tujuan MVP**
1. Admin menambah member beserta paket dalam kurang dari 1 menit.
2. Status masa aktif konsisten di semua layar dan saat check-in (dihitung di server dengan zona waktu gym).
3. Perpanjangan selalu benar, baik dari pembayaran manual maupun online, dan tidak pernah diproses dua kali.
4. Check-in QR tidak bisa dipakai ulang atau dari screenshot lama.
5. Booking kelas tidak pernah melebihi kuota.

**Risiko yang ditangani**
- Overbooking: kuota dicek dan booking dibuat secara atomik di server.
- Zona waktu dan batas akhir hari: tanggal kedaluwarsa disimpan sebagai tanggal dan dihitung dengan zona waktu gym.
- QR statis: QR dinamis, berumur 30 detik, sekali pakai, dan admin melihat foto member.
- Pengambilalihan data: akun login ditautkan ke member hanya lewat kode undangan sekali pakai (RV-02).

**Keputusan produk yang diterapkan**
- RV-01: pengingat masa aktif (R-01), pengingat jadwal kelas (R-03), dan ekspor laporan (R-06) menjadi bagian MVP, ditempatkan sesuai dependensinya.
- RV-07: aturan perpanjangan dan masa tenggang ditetapkan sebagai default (lihat FR-13).
- RV-08: payment gateway adalah **Midtrans** (Snap). Metode bayar: transfer bank virtual account, QRIS, dan GoPay. Semuanya di balik interface `PaymentGateway`.
- RV-09: "hampir habis" = 7 hari, batal booking paling lambat 2 jam sebelum kelas, QR berganti tiap 30 detik. Ketiganya disimpan sebagai pengaturan gym.

**Pengguna dan peran**
- User baru yang login pertama kali **tidak punya peran apa pun** (RV-06).
- Peran `admin` diberikan lewat skrip CLI saat deploy atau lewat undangan admin.
- User yang tertaut ke data member berperan `member`.
- Satu user bisa admin sekaligus member.

## 2. Scope

### In scope

Urutan fase (setiap fase selesai dan teruji sebelum fase berikutnya):

**Fase 0: Fondasi**
- F-01 Akun dan login: login/logout, pembuatan user otomatis, halaman profil, hapus akun.
- F-02 Pengelolaan gym dan peran: profil dan pengaturan gym, peran admin, admin pertama lewat CLI, undangan admin, cabut admin.
- Penautan akun ke data member **tidak** ada di fase ini (RV-03).

**Fase 1: Member dan paket**
- F-03 Paket membership.
- F-04 Data member: tambah/ubah/daftar/detail, foto lewat API, dan penautan akun lewat kode undangan sekali pakai (RV-02, RV-03).
- F-05 Status masa aktif dan tanggal kedaluwarsa.
- Pelengkap hapus akun untuk member (anonimisasi data member).

**Fase 2: Pembayaran, ekspor, dan pengingat masa aktif**
- F-06 Pencatatan pembayaran manual dan perpanjangan.
- R-06 Ekspor laporan member dan pembayaran (setelah F-06).
- F-07 Pembayaran online lewat Midtrans: webhook, rekonsiliasi, status `needs_review`.
- R-01 Pengingat masa aktif hampir habis (setelah F-05 dan F-07). Fase ini juga membangun infrastruktur notifikasi: token perangkat, FCM, dan job pg-boss.

**Fase 3: Check-in QR**
- F-08 Check-in kehadiran dengan QR dinamis.

**Fase 4: Kelas dan booking**
- F-09 Jadwal kelas (sesi satu kali, seri mingguan, generator sesi).
- F-10 Booking kelas.
- R-03 Pengingat jadwal kelas (setelah F-10).
- Pelengkap hapus akun: pembatalan booking mendatang.

**Lintas fitur**
- Teks UI Bahasa Indonesia.
- Platform: web, Android, iOS dari satu codebase Flutter.
- Hapus akun dari halaman profil (RV-10).
- Pengaturan gym (RV-09).

### Non-goals

- Dukungan banyak gym atau cabang dalam satu aplikasi. Skema sudah memakai `gym_id`, tetapi fiturnya belum dibuat.
- Mode offline: check-in, booking, dan pembayaran selalu butuh koneksi internet.
- Pembaruan data realtime: data diambil saat halaman dibuka atau di-refresh.
- Instruktur atau personal trainer sebagai pengguna dengan login sendiri.
- Penjualan produk atau kasir (suplemen, minuman, merchandise).
- Absensi dan penggajian staf.
- Check-in mandiri lewat perangkat atau kios tanpa admin.
- Refund otomatis lewat payment gateway.
- Dashboard ringkasan untuk admin.
- Daftar tunggu kelas.
- Cuti atau bekukan membership.
- Kode promo dan diskon paket.
- Push notification di web (push hanya Android dan iOS).
- Impor data member lama dari spreadsheet.
- Pembatasan paket per kelas atau kuota kelas per bulan.
- Sanksi no-show.
- Booking otomatis dianggap check-in.
- Satu member punya lebih dari satu paket aktif.

## 3. Tech Constraints

Konvensi proyek di `docs/conventions.md` adalah sumber kebenaran. Ringkasan untuk proyek ini:

**Monorepo (pnpm workspaces, tanpa Turborepo)**
- `apps/app`: Flutter untuk web, Android, iOS.
- `apps/api`: Hono + TypeScript.
- `packages/contract`: `openapi.json` dan client Dart `api_client` hasil generate. Keduanya di-commit dan tidak diedit manual. Jalankan `pnpm contract:generate` setiap route atau skema berubah.
- `pnpm check` harus hijau sebelum task dicentang.

**Backend**
- Clean Architecture per fitur: `domain`, `usecases`, `infrastructure/drizzle-*`, `http/*.route.ts`.
- Route memakai `@hono/zod-openapi` dengan `operationId` dan skema bernama.
- Dependency luar masuk lewat `AppDeps` (composition root di `createApp`).
- Prefix `/v1` untuk semua endpoint kecuali `/health` dan `/webhooks/*` (publik, wajib didaftarkan di `PUBLIC_ROUTES` pada test keamanan).
- JSON camelCase, timestamp ISO 8601 UTC berakhiran `Z`, tanggal `YYYY-MM-DD`.
- Format error baku `{ error: { code, message, details? } }`.
- Kode error baru ditambahkan ke `error-codes.ts`, dipetakan di Flutter pada `failureCodeOf` dan `failure_messages.dart`:

| ErrorCode baru | HTTP |
| --- | --- |
| `MEMBERSHIP_INACTIVE` | 409 |
| `CLASS_FULL` | 409 |
| `ALREADY_BOOKED` | 409 |
| `BOOKING_CLOSED` | 409 |
| `LAST_ADMIN` | 409 |
| `QR_INVALID` | 400 |
| `INVITE_INVALID` | 400 |
| `TOO_MANY_ATTEMPTS` | 429 |
| `PAYMENT_PROVIDER_ERROR` | 502 |

**Database**
- PostgreSQL 17 + Drizzle + drizzle-kit, lokal lewat Docker Compose.
- Tabel snake_case jamak. Constraint dan index diberi nama eksplisit `<tabel>_<kolom>_<jenis>`. Enum ditulis sebagai `text` + CHECK.
- Semua timestamp `timestamptz(3)` lewat helper `schema/columns.ts`. Nilai yang ditulis server memakai `now()` database.
- Uang disimpan sebagai integer rupiah.
- Migrasi tidak mengedit migrasi yang sudah di-commit. Tabel dan kolom ditambahkan per fase, jadi satu tabel boleh muncul di migrasi fase yang berbeda dengan versi akhirnya seperti di bagian 4.

**Multi-gym (pola tenancy)**
- Pola "Organisasi dan tenancy" dari konvensi dipakai dengan `organizations` diganti `gyms`.
- Path bersarang `/v1/gyms/{gymId}/...`. Middleware akses gym membaca peran user dan menaruhnya di `c.var.gymAccess` (`isAdmin`, `memberId`).
- User yang bukan admin dan bukan member gym itu mendapat `404 NOT_FOUND`. Peran kurang mendapat `403 FORBIDDEN`.
- Pemeriksaan peran ada di use case.
- Repository memfilter `gym_id` di query yang sama.

**Auth**
- Firebase Auth email/password di client. API memverifikasi ID token di middleware `authenticate`.
- Tabel `users` tanpa password, dibuat saat request pertama lewat `syncUser`.
- Peran ada di PostgreSQL. Auth Emulator dipakai lokal dan di test.
- User baru tanpa peran (RV-06). Admin pertama dibuat lewat skrip CLI `node dist/scripts/seed-admin.js --email <email> [--gym-name <nama>] [--timezone <IANA>]`. Perilaku skrip:
  - Mencari user Firebase berdasarkan email. Bila belum terdaftar, skrip gagal dengan pesan jelas.
  - Membuat gym bila belum ada (zona waktu default `Asia/Jakarta`).
  - Upsert `users` dan membuat baris `gym_admins`.
  - Idempoten, dan menolak membuat gym kedua.
- Versi dev: `pnpm --filter api seed:admin -- --email <email>`.

**Port (D-06) dan adapter** di `core/ports/`, masing-masing dengan adapter `none` (default), `fake` (ditolak di produksi), dan adapter sungguhan:

| Port | Env | Adapter sungguhan | Catatan |
| --- | --- | --- | --- |
| `PushSender` | `PUSH_ADAPTER` | `fcm` | |
| `FileStorage` | `STORAGE_ADAPTER` | `firebase` | Ditambah metode `getSignedUrl(path, { expiresInSeconds })` |
| `PaymentGateway` | `PAYMENT_ADAPTER` | `midtrans` | Baru |

- `FileStorage`: `getSignedUrl` ditambahkan di port, adapter fake, dan adapter firebase. Di produksi butuh Application Default Credentials dengan izin menandatangani URL.
- `PaymentGateway`:
  - `createCharge({ orderId, amount, customer, itemName, expiresInMinutes, returnUrl })` mengembalikan `{ redirectUrl, providerRef }`.
  - `getStatus(orderId)` mengembalikan `{ status, grossAmount, settledAt }`.
  - `verifyNotification(rawBody)` memverifikasi signature dan mengembalikan notifikasi ter-parse.
  - Adapter Midtrans memakai Snap dengan `enabled_payments` transfer bank (VA), QRIS, dan GoPay, serta masa berlaku 60 menit.
  - Verifikasi webhook: `SHA512(order_id + status_code + gross_amount + serverKey)`.
- Env baru (ditambahkan sekaligus ke `env.ts`, `.env.example`, dan `test/setup/env.ts`):
  - `PAYMENT_ADAPTER`
  - `MIDTRANS_SERVER_KEY`
  - `MIDTRANS_ENV` (`sandbox`/`production`)
  - `PAYMENT_RETURN_URL`
  - `QR_SIGNING_SECRET` (minimal 32 karakter, wajib)
- Produksi: `RUN_WORKER=true`, `PUSH_ADAPTER=fcm`, `STORAGE_ADAPTER=firebase`, `PAYMENT_ADAPTER=midtrans`.

**Foto member (RV-05)**
- Storage dikunci penuh dari client (`storage.rules` menolak semua akses).
- Upload lewat `PUT` ke API, baca lewat signed URL berumur 300 detik yang dibuat API.
- Otorisasi tetap di server.

**Notifikasi dan job (RV-04)**
- FCM untuk push. Tabel `device_tokens` per user.
- Job pg-boss berjalan di dalam container API (`RUN_WORKER=true`):

| Job | Jadwal (UTC) | Fungsi |
| --- | --- | --- |
| `payments.reconcile` | `*/10 * * * *` | Rekonsiliasi pembayaran pending |
| `classes.generate-sessions` | `0 * * * *` | Membuat sesi dari seri berulang |
| `notifications.membership-expiring` | `0 * * * *` | Pengingat masa aktif |
| `notifications.class-reminders` | `*/5 * * * *` | Pengingat jadwal kelas |

- Semua job idempoten. Pengiriman push dicegah ganda lewat tabel `notification_logs` dengan `dedupe_key` unik: baris diklaim dulu dengan `INSERT ... ON CONFLICT DO NOTHING`, push dikirim hanya bila baris baru berhasil dibuat, dan bila pengiriman gagal baris dihapus agar bisa dicoba ulang.
- Token yang dijawab `invalid-token` dihapus.
- Setup APNs untuk iOS: kunci APNs (.p8) diunggah di konsol Firebase dan dicatat di README deploy. IOS belum terverifikasi di template, jadi verifikasi iOS (build dan push di perangkat nyata) dicatat saat pertama dikerjakan.

**Flutter**
- Clean Architecture per fitur: `domain` (entity, interface repository, use case, Dart murni), `data` (data source dari client OpenAPI, DTO + mapper, repository impl), `presentation` (Bloc/Cubit dengan state sealed + widget).
- go_router (rute terlindungi default, rute anak untuk form, deep link untuk halaman detail), get_it dengan registrasi manual per fitur, `Result` sealed `Ok`/`Err`.
- Teks kegagalan hanya dari `failure_messages.dart` (D-03). Aturan bisnis ada di API, client tidak boleh lebih ketat.
- Package baru (dipin versi pasti saat dipasang dan dicatat di tabel versi `docs/conventions.md`):
  - `qr_flutter` (tampilkan QR)
  - `mobile_scanner` (scan QR di web, butuh HTTPS)
  - `url_launcher` (membuka halaman bayar Midtrans)
  - `image_picker`
  - `firebase_messaging`
- Aplikasi tidak memakai `firebase_storage` di client.
- Helper tanggal zona gym di API (`core/time`) memakai `Intl` tanpa library tambahan, diuji unit.

**Deploy**
- API sebagai container selalu hidup (`apps/api/Dockerfile`). Migrasi dijalankan terpisah (`node dist/db/migrate.js`) sebelum server.
- Flutter web di hosting statis (HTTPS wajib untuk kamera).
- Mobile lewat store.
- Testing: Vitest (unit + integration) dan flutter_test + bloc_test + mocktail.

**Constraint dan aturan integritas** (nama mengikuti pola `<tabel>_<kolom>_<jenis>`):

*Gym dan akun*
- `gyms`:
  - CHECK `near_expiry_days` 1–60 (default 7).
  - CHECK `cancel_cutoff_minutes` 0–1440 (default 120).
  - CHECK `qr_rotation_seconds` 10–120 (default 30).
  - CHECK `expiry_reminder_days` 1–30 (default 3).
  - CHECK `class_reminder_minutes` 15–1440 (default 60).
  - `timezone` divalidasi sebagai zona IANA di API.
  - Versi pertama hanya punya satu baris, dijaga skrip seed dan bukan constraint.
- `users`: `users_firebase_uid_unique`; email disimpan lowercase (`users_email_lowercase_check`).
- `gym_admins`: `gym_admins_gym_id_user_id_unique`; FK `ON DELETE CASCADE`.
- `invites`:
  - `kind` IN (`member_link`,`admin`). `invites_kind_member_check`: `member_link` wajib `member_id`, `admin` wajib `member_id` null.
  - Kode disimpan sebagai hash SHA-256 (`invites_code_hash_unique`). Kode asli hanya muncul sekali di respons pembuatan.
  - Undangan valid bila `used_at`, `revoked_at` null dan `expires_at > now()`.
  - Kolom `member_id` dan CHECK ditambahkan di migrasi fase 1 (member belum ada di fase 0).
- `invite_redeem_attempts`: append-only; index `(user_id, created_at)`.

*Paket dan member*
- `plans`:
  - `plans_gym_id_name_lower_unique` pada `(gym_id, lower(name))`.
  - `plans_duration_value_check` (> 0).
  - `plans_duration_unit_check` IN (`day`,`week`,`month`,`year`).
  - `plans_price_idr_check` (> 0).
- `members`:
  - `members_user_id_unique` (satu user tertaut ke paling banyak satu member). FK `user_id` ke `users` `ON DELETE SET NULL`.
  - `members_expires_on_check`: `expires_on >= started_on`.
  - Index pagination `(gym_id, created_at DESC, id DESC)`.
  - Index `(gym_id, expires_on)` untuk filter status.
  - Anggota yang dianonimkan: `full_name`='Member terhapus', `phone`, `email`, dan `photo_path` null, `anonymized_at` terisi.

*Pembayaran*
- `payments`:
  - **Snapshot** `plan_name`, `plan_duration_value`, `plan_duration_unit`, dan `amount` diisi saat pembayaran dibuat dan tidak pernah berubah (RV2-01).
  - `payments_plan_duration_value_check` (> 0) dan `payments_plan_duration_unit_check` (nilai sama seperti `plans`); keduanya NOT NULL.
  - `payments_amount_check` (> 0).
  - `payments_method_check` IN (`cash`,`transfer`,`online`).
  - `payments_status_check` IN (`pending`,`paid`,`failed`,`expired`,`needs_review`).
  - `payments_provider_order_id_unique`.
  - `payments_manual_online_check`: method `cash`/`transfer` wajib status `paid` dan provider null; method `online` wajib `provider` dan `provider_order_id`.
  - `period_start`/`period_end` diisi saat status menjadi `paid` (periode perpanjangan yang diterapkan).
  - FK `recorded_by_user_id` `ON DELETE SET NULL`.
  - Index pagination `(gym_id, created_at DESC, id DESC)`, index `(member_id, created_at DESC, id DESC)`, dan index `(status, created_at)` untuk rekonsiliasi.
  - Riwayat pembayaran tidak ikut terhapus saat akun dihapus (pembukuan).
- `payment_webhook_events`: `payment_webhook_events_event_key_unique` (idempotensi webhook), append-only.

*Check-in*
- `checkins`: `checkins_qr_jti_unique` (QR sekali pakai); index `(member_id, created_at DESC, id DESC)` dan `(gym_id, created_at DESC, id DESC)`.

*Kelas dan booking*
- `class_series`:
  - `weekday` 1–7 (ISO, 1 = Senin).
  - `start_time` format `HH:mm` waktu lokal gym.
  - `duration_minutes` 5–480.
  - `capacity` 1–500.
- `class_sessions`:
  - `class_sessions_series_id_local_date_unique`: unique parsial `(series_id, local_date)` `WHERE series_id IS NOT NULL` (generator idempoten).
  - `class_sessions_booked_count_check`: `0 <= booked_count <= capacity`.
  - `status` IN (`scheduled`,`cancelled`).
  - `local_date` selalu = tanggal lokal gym dari `starts_at`.
  - Index `(gym_id, starts_at)`.
- `bookings`:
  - `bookings_session_id_member_id_active_unique`: unique parsial `(session_id, member_id) WHERE status = 'booked'`.
  - `status` IN (`booked`,`cancelled`).
  - `cancelled_by` IN (`member`,`session`,`account_deleted`).
  - Index `(member_id, created_at DESC, id DESC)`.

*Notifikasi*
- `device_tokens`: `device_tokens_token_unique`; `platform` IN (`android`,`ios`); FK `ON DELETE CASCADE`.
- `notification_logs`: `notification_logs_dedupe_key_unique`; `kind` IN (`membership_expiring`,`class_reminder`).

## 5. API Contract

**Aturan umum**
- Semua endpoint `/v1/*` memakai `Authorization: Bearer <ID token>`. Tanpa token atau token salah memberi `401 UNAUTHENTICATED`.
- Path `{gymId}`, `{memberId}`, dan sejenisnya divalidasi `z.uuid()`; yang bukan UUID memberi `422 details.<param>`.
- Pada endpoint `/v1/gyms/{gymId}/*`, user yang bukan admin dan bukan member gym itu mendapat `404 NOT_FOUND`. Resource milik member lain juga `404`.
- Peran kurang memberi `403 FORBIDDEN`.
- Daftar berpagination memakai `?limit=20&cursor=` dan respons `{ items, nextCursor }` (`pageSchema`).
- Body kosong yang wajib → `422`. Teks wajib memakai `.trim()` sebelum `.min()`.
- Di tiap endpoint di bawah, "Error" hanya menyebut error khusus selain `401` dan `422`.

**Status masa aktif** (`MembershipStatus`): `active`, `expiring_soon`, `expired`.

**Skema bersama** (nama skema OpenAPI = nama kelas Dart)
- `Me`: `{ user: { id, email, displayName }, gym: { id, name, timezone } | null, isAdmin, memberId | null }`
- `Gym`: `{ id, name, address, timezone, nearExpiryDays, cancelCutoffMinutes, qrRotationSeconds, expiryReminderDays, classReminderMinutes }`
- `Plan`: `{ id, name, durationValue, durationUnit, priceIdr, isActive }`
- `Member`: `{ id, fullName, phone | null, email | null, planId, planName, startedOn, expiresOn, status, daysUntilExpiry, photoUrl | null, hasAccount, createdAt }`
  - `photoUrl` adalah signed URL 300 detik.
  - `daysUntilExpiry` = `expiresOn − hari ini` (zona gym), bisa negatif.
- `Payment`: `{ id, memberId, memberName, planName, planDurationValue, planDurationUnit, amount, method, status, paidAt | null, periodStart | null, periodEnd | null, expiresAt | null, redirectUrl | null, note | null, createdAt }`
  - `redirectUrl` hanya untuk pembayaran online berstatus `pending` milik pemanggil.
- `Checkin`: `{ id, memberId, memberName, createdAt }`
- `ClassSeries`: `{ id, name, instructorName, weekday, startTime, durationMinutes, capacity, startsOn, endsOn | null, isActive }`
- `ClassSession`: `{ id, seriesId | null, name, instructorName, startsAt, localDate, durationMinutes, capacity, bookedCount, remainingSpots, status, myBookingId | null }`
- `Booking`: `{ id, sessionId, memberId, memberName, status, cancelledBy | null, createdAt, session: ClassSession | null }`

## 6. Functional Requirements

Aturan tanggal berlaku untuk semua FR: "hari ini" adalah tanggal kalender di zona waktu gym. `expires_on` adalah **hari terakhir member aktif** (aktif sampai akhir hari itu).

### FR-01: Login, logout, dan pembuatan user otomatis
Admin dan member masuk dengan email/password lewat Firebase Auth. API membuat baris `users` saat request pertama (RV-06: tanpa peran).

Fitur: F-01

Acceptance criteria:
- [ ] Given pengguna belum punya akun When mendaftar dan login di Flutter Then Firebase mengeluarkan ID token dan `GET /v1/me` mengembalikan `200` dengan `gym: null`, `isAdmin: false`, `memberId: null`.
- [ ] Given user baru sudah ada When `GET /v1/me` dipanggil dua kali Then hanya satu baris `users` untuk `firebase_uid` itu dan `last_seen_at` diperbarui.
- [ ] Given pengguna sudah login When menekan logout Then sesi hilang dan rute terlindungi mengarah ke `/login`.
- [ ] Given user tanpa peran sudah login When membuka aplikasi Then yang tampil hanya layar "Masukkan kode undangan" dan halaman profil, tanpa data gym.
- [ ] Given request ke `/v1/*` tanpa token valid When dipanggil Then `401 UNAUTHENTICATED` (dijaga `all-routes-require-auth.int.test.ts`).

Edge cases:
- Token kedaluwarsa dimuat ulang sekali oleh `AuthInterceptor`.
- Email di token memakai huruf besar, disimpan lowercase.
- Login bersamaan dari dua tab tidak membuat user ganda (`ON CONFLICT (firebase_uid)`).

### FR-02: Peran, akses per gym, dan admin pertama
Peran `admin` ada di `gym_admins`, peran `member` dari `members.user_id`. Admin pertama dibuat lewat CLI (RV-06).

Fitur: F-02

Acceptance criteria:
- [ ] Given database kosong When skrip `seed-admin --email a@x.id` dijalankan untuk email yang sudah terdaftar di Firebase Then gym dibuat, `gym_admins` berisi user itu, dan `GET /v1/me` untuknya memberi `isAdmin: true`.
- [ ] Given skrip sudah dijalankan When dijalankan lagi dengan email yang sama Then tidak ada baris ganda dan tidak ada gym kedua.
- [ ] Given email tidak terdaftar di Firebase When skrip dijalankan Then keluar dengan exit code 1 dan pesan "daftar dulu".
- [ ] Given user tanpa peran When memanggil `/v1/gyms/{gymId}/members` Then `404 NOT_FOUND`.
- [ ] Given member (bukan admin) When memanggil endpoint khusus admin Then `403 FORBIDDEN`.
- [ ] Given tidak ada kode yang menaikkan user biasa menjadi admin When user baru dibuat Then `gym_admins` tidak bertambah.

Edge cases:
- Skrip dijalankan dengan `NODE_ENV=production` memakai Application Default Credentials.
- Seed membuat gym baru dengan pengaturan default RV-09.

### FR-03: Profil dan pengaturan gym
Admin mengubah nama, alamat, zona waktu, dan pengaturan operasional (hampir habis, batas batal, interval QR, hari pengingat, menit pengingat kelas).

Fitur: F-02

Acceptance criteria:
- [ ] Given admin When `PATCH /gyms/{gymId}` dengan `{ nearExpiryDays: 10 }` Then `200` dan status "hampir habis" memakai 10 hari.
- [ ] Given zona waktu `Mars/Phobos` When dikirim Then `422 details.timezone`.
- [ ] Given member When `PATCH` Then `403`.
- [ ] Given body `{}` When `PATCH` Then `422 details._root`.
- [ ] Given nilai di luar rentang CHECK (misalnya `qrRotationSeconds: 5`) When dikirim Then `422`.

Edge cases:
- Mengubah zona waktu tidak mengubah `expires_on` yang tersimpan (tanggal murni).
- Mengubah `qrRotationSeconds` hanya berlaku untuk token berikutnya.

### FR-04: Undangan admin dan pencabutan admin
Admin menambah admin lain lewat undangan sekali pakai. Mencabut admin atau menghapus akun admin tidak boleh menyisakan gym tanpa admin, dijaga dengan penguncian baris `gyms` (RV2-02).

Fitur: F-02

Acceptance criteria:
- [ ] Given admin When `POST /invites { kind: "admin" }` Then `201` dengan `code` dan `expiresAt` = 48 jam, dan hanya hash kode yang tersimpan.
- [ ] Given user tanpa peran When `POST /invites/redeem` dengan kode valid Then ia menjadi admin dan undangan memiliki `used_at`.
- [ ] Given undangan sudah dipakai, dicabut, atau kedaluwarsa When ditebus Then `400 INVITE_INVALID`.
- [ ] Given 5 tebusan gagal dalam 15 menit When tebusan keenam Then `429 TOO_MANY_ATTEMPTS`, bahkan dengan kode benar, sampai jendela lewat.
- [ ] Given dua admin A dan B When A mencabut B dan B mencabut A bersamaan Then tepat satu berhasil dan satunya `409 LAST_ADMIN` (integration test cabut-silang bersamaan).
- [ ] Given hanya satu admin When ia mencabut dirinya Then `409 LAST_ADMIN`.
- [ ] Given pencabutan atau hapus akun admin When dijalankan Then transaksi memulai dengan `SELECT ... FROM gyms WHERE id=$1 FOR UPDATE` sebelum menghitung admin.

Edge cases:
- Admin yang dicabut tetap bisa menjadi member jika tertaut.
- Dua orang menebus kode yang sama bersamaan: hanya satu berhasil (`UPDATE ... WHERE used_at IS NULL`).
- Admin mencabut dirinya sendiri bila masih ada admin lain: diizinkan.

### FR-05: Halaman profil
Halaman profil menampilkan nama, email, peran, dan (bila member) paket serta masa aktif ringkas, dengan tombol logout dan "Hapus akun".

Fitur: F-01

Acceptance criteria:
- [ ] Given user login When membuka `/profile` Then email dan peran tampil sesuai `GET /v1/me`.
- [ ] Given user tanpa peran When membuka profil Then tombol "Hapus akun" dan "Keluar" tersedia.
- [ ] Given halaman dimuat ulang di web When URL `/profile` dibuka langsung Then data dimuat ulang dari API.
- [ ] Given pemuatan gagal When jaringan putus Then `FailureView` dengan tombol "Coba lagi".

Edge cases:
- Nama tampil dari klaim token; bila kosong tampil email.

### FR-06: Hapus akun dari aplikasi
Pengguna menghapus akun dari halaman profil lewat dialog konfirmasi (RV-10). Hapus akun menghapus data pribadi tetapi menyimpan riwayat pembayaran untuk pembukuan. Bagian anonimisasi member dikerjakan bersama F-04 (fase 1), dan pembatalan booking mendatang bersama F-10 (fase 4).

Fitur: F-01

Acceptance criteria:
- [ ] Given user tanpa peran When `DELETE /v1/me` Then `204`, baris `users` dan `device_tokens` terhapus, dan akun Firebase dihapus.
- [ ] Given member tertaut When `DELETE /v1/me` Then `members.user_id` menjadi null, `full_name` menjadi "Member terhapus", `phone`/`email`/`photo_path` null, foto dihapus dari Storage, `anonymized_at` terisi, dan baris `payments` dan `checkins` tetap ada.
- [ ] Given member punya booking `booked` untuk sesi mendatang When akun dihapus Then booking menjadi `cancelled` dengan `cancelled_by = account_deleted` dan `booked_count` sesi berkurang.
- [ ] Given admin terakhir When `DELETE /v1/me` Then `409 LAST_ADMIN` dan tidak ada yang terhapus.
- [ ] Given penghapusan akun Firebase gagal setelah transaksi database When endpoint dipanggil ulang Then selesai idempoten dengan `204`.

Edge cases:
- Dua admin terakhir menghapus akunnya bersamaan: satu berhasil, satu `409` (kunci `gyms`).
- Dialog konfirmasi menjelaskan data yang dihapus dan yang tetap disimpan.
- Setelah sukses, aplikasi logout dan mengarah ke `/login`.

### FR-07: Paket membership
Admin mengelola paket (nama, durasi, harga, status aktif).

Fitur: F-03

Acceptance criteria:
- [ ] Given admin When membuat paket "Bulanan" 1 `month` Rp150.000 Then `201` dan paket muncul di daftar.

### FR-13: Pembayaran manual dan aturan perpanjangan
Admin mencatat pembayaran tunai/transfer. Aturan perpanjangan (RV-07, berlaku untuk pembayaran manual maupun online) lewat `computeRenewalPeriod(expiresOn, paidOn, durasi snapshot payment)`:
- Bila `expires_on >= paidOn` (masih aktif): basis = `expires_on`.
- Bila `expires_on < paidOn` (sudah lewat): basis = `paidOn` (tanggal gym).
- Masa aktif baru = `addDuration(basis, durasi)`.
- `periodStart` = basis.
- **Tanpa masa tenggang:** check-in ditolak mulai hari setelah `expires_on`.

Fitur: F-06

Acceptance criteria:
- [ ] Given `expires_on` 2026-03-20, hari ini 2026-03-10, paket 1 bulan When pembayaran manual dicatat Then `expires_on` = 2026-04-20, `periodStart` = 2026-03-20, `periodEnd` = 2026-04-20.
- [ ] Given `expires_on` 2026-03-01, hari ini 2026-03-10, paket 1 bulan When pembayaran manual dicatat Then `expires_on` = 2026-04-10.
- [ ] Given `expires_on` = hari ini When pembayaran dicatat Then basis `expires_on` (belum dianggap lewat).
- [ ] Given pembayaran manual sukses When dilihat Then status `paid`, `plan_name`, `plan_duration_*`, dan `amount` adalah snapshot dari paket saat itu, dan `members.plan_id` berubah ke paket itu.
- [ ] Given member expired sejak kemarin When check-in dengan QR Then `accepted: false` dengan `membership_inactive` (tanpa masa tenggang).
- [ ] Given pencatatan pembayaran dan update member When salah satu gagal Then keduanya dibatalkan (satu transaksi, baris member dikunci `FOR UPDATE`).
- [ ] Given dua pembayaran manual bersamaan untuk member yang sama When keduanya selesai Then masa aktif bertambah dua kali berurutan, tanpa kehilangan satu pun.

Edge cases:
- Paket nonaktif tidak bisa dipakai (`422 details.planId`).
- Member anonim: `409`.
- `computeRenewalPeriod` adalah fungsi murni dengan unit test untuk akhir bulan dan tahun kabisat.
- Mengubah aturan (misalnya menambah masa tenggang) cukup mengubah satu use case ini.

Fitur: F-10

Acceptance criteria:
- [ ] Given kelas mulai 18:00 dan sekarang 15:59 When member membatalkan Then `200`, status `cancelled`, `cancelled_by = member`, dan `booked_count` berkurang 1.
- [ ] Given kelas mulai 18:00 dan sekarang 16:01 When member membatalkan Then `409 BOOKING_CLOSED`.
- [ ] Given tepat 16:00 When membatalkan Then diterima (batas inklusif).
- [ ] Given booking sudah `cancelled` When dibatalkan lagi Then `200` idempoten dan `booked_count` tidak berkurang lagi.
- [ ] Given member A When membatalkan booking member B Then `404`.
- [ ] Given admin When membuka halaman detail sesi Then tampil "N / kapasitas" dan daftar peserta (`status = booked`), dapat dibuka lewat URL langsung.
- [ ] Given member When membuka `/me/bookings` Then tampil yang mendatang (default) atau lampau (`scope=past`) dengan pagination.

Edge cases:
- Pembatalan dua kali bersamaan mengurangi `booked_count` sekali (baris booking dikunci).
- Batas waktu pembatalan membaca pengaturan gym saat itu.

### FR-27: Pengingat jadwal kelas
Member yang sudah booking menerima push sebelum kelas dimulai (R-03).

Fitur: R-03

Acceptance criteria:
- [ ] Given booking `booked` untuk sesi yang mulai dalam 60 menit (`classReminderMinutes`) When `notifications.class-reminders` berjalan (tiap 5 menit) Then satu push dikirim ke token member itu.
- [ ] Given job berjalan berulang When `dedupe_key = class:{bookingId}` sudah ada Then tidak ada push ganda.
- [ ] Given booking dibatalkan atau sesi dibatalkan sebelum job When job berjalan Then tidak ada push.
- [ ] Given sesi mulai lebih dari 60 menit lagi When job berjalan Then tidak ada push.
- [ ] Given member tidak punya token When job berjalan Then dilewati tanpa error.

Edge cases:
- Booking yang dibuat kurang dari 60 menit sebelum kelas dikirimi pengingat pada putaran job berikutnya (sekali).
- Sesi yang sudah dimulai tidak dikirimi pengingat.
- Kegagalan kirim menghapus klaim `notification_logs` agar dicoba ulang pada putaran berikutnya selama sesi belum mulai.

## 7. Non-Functional Requirements

- **NFR-01 (Keamanan akses):** Semua endpoint `/v1/*` mewajibkan token valid. Test `all-routes-require-auth.int.test.ts` memeriksa seluruh route. Hanya `/health` dan `/webhooks/midtrans` publik. Integration test per resource membuktikan: bukan anggota gym → `404`, peran kurang → `403`, member A tidak bisa membaca data member B (0 kebocoran di test).
- **NFR-02 (Penautan akun):** Penautan akun ke member hanya lewat kode undangan sekali pakai: 10 karakter Crockford base32 (kira-kira 50 bit), berlaku 48 jam, disimpan sebagai hash SHA-256, dan dibatasi 5 percobaan gagal per 15 menit per user.
- **NFR-03 (Privasi dan log):** Field `authorization`, `token`, `idToken`, `email`, `phone`, dan `code` diredaksi di log. Test log memastikan token, kode undangan, dan nomor HP tidak muncul di output `captureLogger().raw()`. Semua lalu lintas lewat HTTPS di produksi.
- **NFR-04 (Foto):** Bucket Storage tidak dapat diakses client (`storage.rules` menolak semua). Foto hanya dibaca lewat signed URL berumur 300 detik, ukuran maksimal 2 MB, dan tipe JPEG/PNG/WebP.
- **NFR-05 (Konkurensi booking):** Dengan 50 permintaan booking paralel pada sesi berkuota 10, hasilnya tepat 10 sukses dan `booked_count = 10`. Ada integration test yang memakai koneksi database nyata.
- **NFR-06 (Konkurensi admin dan pembayaran):** Test integrasi memastikan (a) cabut admin silang bersamaan tidak pernah menyisakan nol admin, (b) webhook ganda atau bersamaan memperpanjang tepat sekali, (c) dua pemindaian token yang sama bersamaan menghasilkan tepat satu check-in.
- **NFR-07 (Ketepatan tanggal):** Perhitungan status, perpanjangan, dan batas booking memakai jam yang disuntik dan zona waktu gym. Unit test mencakup pergantian hari UTC vs gym, akhir bulan, dan tahun kabisat (minimal 12 kasus pada `computeRenewalPeriod` dan `membershipStatus`).
- **NFR-08 (Performa API):** Dengan 5.000 member dan 50.000 pembayaran, p95 respons kurang dari 500 ms untuk endpoint daftar dan detail, serta p95 kurang dari 300 ms untuk `POST /checkins` dan `POST .../bookings`. Pagination memakai index `(gym_id, created_at DESC, id DESC)` (dicek `EXPLAIN` tanpa `Sort`).
- **NFR-09 (Ekspor):** Ekspor 10.000 baris selesai kurang dari 10 detik dengan memori API di bawah 256 MB (streaming per baris).
- **NFR-10 (Idempotensi job):** Setiap job (`payments.reconcile`, `classes.generate-sessions`, `notifications.*`) bila dijalankan dua kali berturut-turut tidak menghasilkan efek ganda (data atau push). Tiap job punya integration test dua kali jalan, dan job gagal di satu item tidak menghentikan item lain.
- **NFR-11 (Ketahanan webhook):** Webhook membalas dalam kurang dari 3 detik di p95 dan selalu `200` untuk event valid yang duplikat. Tidak ada perpanjangan dari redirect klien. Perubahan paket tidak mengubah hasil perpanjangan pembayaran lama (dijaga test snapshot).
- **NFR-12 (Kualitas dan kontrak):** `pnpm check` hijau (Biome, typecheck, unit + integration test API, `contract:check`, `flutter analyze`, `flutter test`). Setiap use case punya unit test, tiap repository Drizzle punya integration test, dan tiap Cubit punya `blocTest`. Nama komponen OpenAPI konsisten dengan kelas Dart, dan setiap `ErrorCode` baru dipetakan di Flutter (analyzer gagal bila belum).
- **NFR-13 (Penghapusan akun):** Hapus akun selesai dalam satu transaksi database kurang dari 2 detik. Setelah itu tidak ada baris `users`, `device_tokens`, atau data pribadi member (nama, telepon, email, foto), sementara 100% baris `payments` dan `checkins` terkait tetap ada. Dijaga integration test.
- **NFR-14 (Notifikasi):** Pengingat masa aktif dikirim dalam jam pertama setelah pukul 09:00 waktu gym. Pengingat kelas dikirim dalam 5 menit setelah memasuki jendela pengingat. Maksimal satu push per `dedupe_key`.
- **NFR-15 (UI dan platform):** Teks UI 100% Bahasa Indonesia (kegagalan hanya dari `failure_messages.dart`). Halaman admin nyaman di lebar ≥ 1024 px, halaman member di lebar ≥ 360 px. Setiap halaman daftar punya status memuat, kosong, dan gagal dengan "Coba lagi". Web dan Android terverifikasi manual, iOS tercatat sebagai verifikasi terpisah di perangkat atau runner macOS.
- **NFR-16 (Operasional):** Container API start dengan `RUN_WORKER=true`, berhenti bertahap lewat `SIGTERM` (server, lalu pg-boss graceful, lalu koneksi), dan tidak menjalankan migrasi sendiri. Env yang salah atau hilang (termasuk `QR_SIGNING_SECRET` kurang dari 32 karakter) membuat server keluar dengan exit code 1 dan pesan yang menyebut nama variabelnya.
