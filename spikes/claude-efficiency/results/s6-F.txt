# Aplikasi Membership Gym

## 1. Context & Goal

Pencatatan member dan masa aktif di sebuah gym masih manual dan berantakan. Aplikasi ini dipakai admin dan member lewat satu codebase Flutter (web, Android, iOS) dengan backend API terpisah. Admin memakai web, termasuk untuk scan QR. Member memakai HP.

Tujuan versi pertama:
- Admin menambahkan member beserta paketnya, lalu memantau masa aktif.
- Member melihat status, membayar perpanjangan di aplikasi, check-in dengan QR dinamis, dan booking kelas tanpa overbooking.
- Admin mencatat pembayaran manual dan mengekspor laporan.
- Member menerima pengingat masa aktif dan jadwal kelas lewat push.

Versi ini untuk satu gym. Semua tabel utama tetap memuat `gym_id` agar multi-gym bisa ditambahkan nanti.

Urutan fase (rekomendasi diterima ditempatkan sesuai dependensi, RV-01):

| Fase | Nama | Fitur |
| --- | --- | --- |
| 0 | Fondasi | F-01, F-02 |
| 1 | Member dan paket | F-03, F-04, F-05 |
| 2 | Pembayaran | F-06, R-06, F-07 |
| 3 | Check-in QR | F-08 |
| 4 | Kelas dan booking | F-09, F-10 |
| 5 | Notifikasi | R-01, R-03 |

## 2. Scope

### In scope

- F-01 Akun dan login: login/logout, pembuatan user otomatis, profil, hapus akun (RV-10). Penautan akun ke member dikerjakan di F-04 (RV-03).
- F-02 Gym dan peran: profil gym, pengaturan gym, peran admin/member, tambah dan cabut admin lewat undangan, admin pertama lewat CLI (RV-06).
- F-03 Paket membership.
- F-04 Data member, foto lewat signed URL (RV-05), undangan penautan akun sekali pakai (RV-02).
- F-05 Status masa aktif dan kedaluwarsa.
- F-06 Pembayaran manual dan perpanjangan.
- R-06 Ekspor laporan member dan pembayaran (CSV).
- F-07 Pembayaran online lewat Midtrans, dibungkus interface `PaymentGateway` (RV-08).
- F-08 Check-in QR dinamis.
- F-09 Jadwal kelas, termasuk kelas berulang mingguan.
- F-10 Booking kelas.
- R-01 Pengingat masa aktif hampir habis (push).
- R-03 Pengingat jadwal kelas (push).

### Non-goals

- Banyak gym atau cabang dalam satu aplikasi (skema sudah siap, fiturnya belum).
- Mode offline untuk check-in, booking, dan pembayaran.
- Pembaruan realtime. Data diambil saat halaman dibuka atau di-refresh.
- Instruktur atau personal trainer sebagai pengguna dengan login sendiri.
- Penjualan produk atau kasir.
- Absensi dan penggajian staf.
- Check-in mandiri tanpa admin.
- Refund otomatis lewat payment gateway.
- Dashboard ringkasan admin, daftar tunggu kelas, cuti/bekukan membership, kode promo dan diskon.
- Impor data member lama dari spreadsheet.

## 3. Tech Constraints

- Monorepo pnpm: `apps/app` (Flutter web/Android/iOS), `apps/api` (Hono + TypeScript, Zod OpenAPI), `packages/contract` (OpenAPI + client Dart hasil generate).
- PostgreSQL + Drizzle. Auth Firebase Auth (backend memverifikasi ID token). Foto di Cloud Storage for Firebase. Push lewat FCM. Job terjadwal pg-boss di dalam API container (`RUN_WORKER=true`). Deploy API sebagai container yang selalu hidup, web di hosting statis, mobile lewat store.
- Semua konvensi (struktur fitur, auth, error, pagination, port, job, database, migrasi) mengikuti docs/conventions.md. Bagian yang relevan: Autentikasi, Format error, Pagination, Database, Job (pg-boss), Port push dan storage, Organisasi dan tenancy.
- Keputusan khusus produk:
  - Tenancy: path `/v1/gyms/{gymId}/...` dengan middleware keanggotaan. Bukan anggota gym → `404`. Peran kurang → `403` dari use case. Tabel `memberships` dengan role `admin`/`member`.
  - Port `FileStorage` ditambah `signedUrl(path, ttlSeconds)`. Client tidak pernah mengakses Storage langsung dan `storage.rules` menolak semua akses client (RV-05).
  - Port baru `PaymentGateway` (`createCharge`, `verifyNotification`, `getStatus`) dengan adapter `none`/`fake`/`midtrans`, dipilih lewat `PAYMENT_ADAPTER` (RV-08).
  - `PUSH_ADAPTER=fcm` di produksi. Butuh setup APNs key di proyek Firebase untuk iOS (RV-04).
  - Kode error baru di `error-codes.ts`: `MEMBERSHIP_INACTIVE` 403, `QR_INVALID` 422, `INVITATION_INVALID` 422, `ALREADY_LINKED` 409, `LAST_ADMIN` 409, `CLASS_FULL` 409, `ALREADY_BOOKED` 409, `CANCEL_WINDOW_CLOSED` 409, `SESSION_NOT_BOOKABLE` 409.
  - Env tambahan: `QR_SIGNING_SECRET`, `MIDTRANS_SERVER_KEY`, `MIDTRANS_CLIENT_KEY`, `MIDTRANS_IS_PRODUCTION`.
  - Tanggal (`expires_on`, `local_date`) memakai kolom `date` dan dihitung dengan zona waktu gym (default `Asia/Jakarta`).

Constraint penting (nama mengikuti docs/conventions.md bagian Database):
- `memberships`: UNIQUE `(gym_id, user_id)`. `members`: UNIQUE `user_id` (parsial, bila tidak null). `users.email` lowercase CHECK.
- `plans`: CHECK `duration_value BETWEEN 1 AND 120`, `duration_unit IN ('day','week','month','year')`, `price_idr > 0`. `payments.plan_duration_value` dan `plan_duration_unit` NOT NULL dengan CHECK yang sama (RV2-01). Snapshot diisi saat pembayaran dibuat.
- `payments`: CHECK `status IN ('pending','paid','failed','expired','needs_review')` dan `method IN ('cash','transfer','online')`. Index `(gym_id, created_at DESC, id DESC)` dan `(member_id, created_at DESC, id DESC)`.
- `invitations`: CHECK `kind`. `member_id` wajib bila `kind='member'`. Hanya `code_hash` (SHA-256) yang disimpan.
- `class_sessions`: UNIQUE `(series_id, local_date)` (parsial). Index `(gym_id, starts_at)`. CHECK `capacity >= 1`.
- `bookings`: UNIQUE parsial `(session_id, member_id) WHERE status='booked'`.
- `checkins`: UNIQUE `qr_jti` agar QR hanya sekali pakai.
- `notification_log`: UNIQUE `dedupe_key` untuk mencegah notifikasi ganda.
- Semua FK ke `gyms` `ON DELETE CASCADE`. Data milik user `ON DELETE CASCADE`. `members.user_id` `ON DELETE SET NULL`.
- Gym tidak boleh tanpa admin. Cabut admin dan hapus akun admin menjalankan `SELECT ... FROM gyms WHERE id=$1 FOR UPDATE` sebelum menghitung admin, dalam transaksi yang sama (RV2-02).

## 6. Functional Requirements

### FR-01: Akun, login, profil, dan hapus akun
User login lewat Firebase Auth dan baris `users` dibuat otomatis (lihat docs/conventions.md bagian Autentikasi). User baru tidak punya peran sampai menukar kode undangan. Halaman profil menampilkan data akun dan tombol hapus akun (RV-10).
Fitur: F-01
Acceptance criteria:
- [ ] Given token Firebase valid untuk uid baru When request pertama dikirim Then baris `users` dibuat tanpa `memberships`.
- [ ] Given user tanpa peran When memanggil endpoint gym Then `404`.
- [ ] Given member tertaut When `DELETE /v1/me` Then `users`, `device_tokens`, dan `memberships` terhapus. Data member dianonimkan (nama "Member Terhapus", telepon, email, dan foto dihapus, `user_id` null). Booking mendatang dibatalkan. `payments` dan `checkins` tetap tersimpan.
- [ ] Given user terautentikasi When `DELETE /v1/me` sukses Then client menghapus akun Firebase lalu logout.
Edge cases:
- Hapus akun admin terakhir → `409 LAST_ADMIN`.
- Gagal menghapus akun Firebase: login ulang membuat user baru tanpa peran.

### FR-02: Gym, peran, dan pengelolaan admin
Satu gym dengan pengaturan (zona waktu, ambang "hampir habis" 7 hari, batas batal booking 120 menit, interval QR 30 detik; RV-09). Admin pertama dibuat lewat CLI `pnpm --filter api create-gym` saat deploy. CLI membuat gym bila belum ada dan mencetak kode undangan admin sekali pakai (RV-06). Admin lain ditambah lewat undangan dan dicabut lewat API.
Fitur: F-02
Acceptance criteria:
- [ ] Given deploy baru When CLI dijalankan Then ada satu gym dan satu kode admin berlaku 48 jam. Tidak ada user yang otomatis admin.
- [ ] Given kode admin valid When user login menukarnya Then `memberships.role='admin'` dibuat dan kode tidak bisa dipakai lagi.
- [ ] Given dua admin When keduanya mencabut satu sama lain bersamaan Then tepat satu berhasil dan satunya `409 LAST_ADMIN` (lock `gyms FOR UPDATE`, RV2-02).
- [ ] Given member When memanggil endpoint admin Then `403`.
Edge cases:
- Admin mencabut dirinya sendiri saat masih ada admin lain: boleh.
- Zona waktu bukan IANA valid → `422`.

### FR-03: Paket membership
Admin membuat, mengubah, dan menonaktifkan paket. Paket nonaktif tidak bisa dipilih untuk member baru atau pembayaran, tetapi riwayat tetap utuh.
Fitur: F-03
Acceptance criteria:
- [ ] Given admin When membuat paket valid Then paket aktif tersimpan dan muncul di daftar.
- [ ] Given `durationValue` 0 atau unit tak dikenal When submit Then `422` dengan `details` per field.
- [ ] Given paket dinonaktifkan When admin memilihnya untuk member baru Then `422 details.planId`.
- [ ] Given member When `GET /plans` Then hanya paket aktif.
Edge cases:
- Nama paket kembar diperbolehkan.
- Mengubah durasi paket tidak memengaruhi pembayaran yang sudah dibuat (snapshot).

### FR-04: Data member dan penautan akun
Admin menambah member beserta paketnya (aksi pertama admin). `startOn` default hari ini dan hanya boleh hari ini sampai 30 hari ke belakang (RV2-04). `expires_on` = `startOn` + durasi paket − 1 hari. Penautan ke akun login hanya lewat kode undangan sekali pakai berlaku 48 jam (RV-02, RV-03). Foto lewat API dan dibaca lewat signed URL (RV-05).
Fitur: F-04
Acceptance criteria:
- [ ] Given admin When `POST /members` dengan paket bulanan dan `startOn` 2026-01-10 Then `expires_on` 2026-02-09.
- [ ] Given `startOn` besok atau lebih dari 30 hari lalu When submit Then `422 details.startOn`.
- [ ] Given kode undangan valid When member login lalu `POST /invitations/redeem` Then `members.user_id` terisi, role `member` dibuat, dan kode tak bisa dipakai lagi.
- [ ] Given kode salah, kedaluwarsa, atau sudah dipakai When redeem Then `422 INVITATION_INVALID`. Membuat undangan baru membatalkan yang lama.
- [ ] Given foto diunggah When `GET photo-url` Then URL berlaku 5 menit. Member lain mendapat `404`.
Edge cases:
- Member sudah tertaut, undangan baru → `409 ALREADY_LINKED`.
- Pencarian `q` cocok sebagian nama atau telepon, tanpa beda huruf besar-kecil.
- Foto bukan jpeg/png/webp atau >2 MB → `422`.

### FR-05: Status masa aktif
Status dihitung di server dari `expires_on` dan tanggal hari ini di zona gym. `expired` bila hari ini > `expires_on`. `expiring_soon` bila sisa 0–7 hari. Selain itu `active`. Member aktif sampai akhir hari `expires_on`, tanpa masa tenggang (RV-07, RV-09).
Fitur: F-05
Acceptance criteria:
- [ ] Given `expires_on` = hari ini When status dihitung Then `expiring_soon`, bukan `expired`.
- [ ] Given `expires_on` kemarin Then `expired`. Given sisa 8 hari Then `active`.
- [ ] Given admin When filter `status=expiring_soon` atau `expired` Then daftar hanya berisi member tersebut.
- [ ] Given member When `GET /members/me` Then respons memuat status dan `expiresOn`.
Edge cases:
- Pukul 23:59 dan 00:01 zona gym diuji di sisi hari yang berbeda.
- Ambang diubah di pengaturan gym → status berikutnya mengikuti nilai baru.

### FR-06: Pembayaran manual dan perpanjangan
Admin mencatat pembayaran tunai atau transfer. Pembayaran `paid` memperpanjang masa aktif dalam satu transaksi dengan baris member terkunci. Aturan perpanjangan (RV-07) berlaku juga untuk F-07. Bila masih aktif (`expires_on` ≥ hari ini), mulai dari `expires_on` + 1 hari. Bila sudah lewat, mulai dari tanggal bayar (zona gym). `period_end` = mulai + durasi − 1 hari, dihitung dari snapshot durasi di `payments` (RV2-01). Tanggal akhir bulan di-clamp.
Fitur: F-06
Acceptance criteria:
- [ ] Given `expires_on` 2026-01-31 dan hari ini 2026-01-20 When bayar paket 1 bulan Then `period_start` 2026-02-01 dan `expires_on` 2026-02-28.
- [ ] Given `expires_on` 2026-01-31 dan dibayar 2026-03-10 When paket 1 bulan Then `period_start` 2026-03-10 dan `expires_on` 2026-04-09.
- [ ] Given paket diedit setelah pembayaran dibuat When perpanjangan dihitung Then memakai `plan_duration_*` dari payment.
- [ ] Given admin When `GET /payments?from&to` Then daftar sesuai rentang dan terurut terbaru.
Edge cases:
- Pembayaran gagal di tengah transaksi tidak mengubah `expires_on`.
- `amount` kosong → default harga paket saat itu.
- Perpanjangan mengubah `members.plan_id` ke paket yang dibayar.

### FR-07: Ekspor laporan member dan pembayaran
Admin mengunduh CSV daftar member (nama, telepon, email, paket, status, `expires_on`) dan pembayaran (tanggal, member, paket, jumlah, metode, status) untuk periode tertentu.
Fitur: R-06
Acceptance criteria:
- [ ] Given admin When `GET exports/members.csv` Then CSV UTF-8 berisi satu baris per member dan header kolom.
- [ ] Given `from`, `to`, dan `status` When ekspor pembayaran Then hanya baris yang cocok.
- [ ] Given member When memanggil ekspor Then `403`.
- [ ] Given sel diawali `=`, `+`, `-`, atau `@` When diekspor Then diawali tanda petik agar tidak dieksekusi sebagai formula.
Edge cases:
- Data kosong → hanya header.
- Data besar dialirkan per batch tanpa memuat semuanya ke memori.

### FR-08: Pembayaran online (Midtrans)
Member memilih paket dan membayar di aplikasi lewat Midtrans Snap (QRIS, virtual account bank, GoPay/ShopeePay), dibungkus port `PaymentGateway` (RV-08). Pembayaran dibuat `pending` dengan `expires_at` 60 menit dan snapshot plan. Perpanjangan hanya dari webhook yang terverifikasi.
Fitur: F-07
Acceptance criteria:
- [ ] Given member When `POST /payments/online` Then payment `pending` dengan snapshot nama, harga, dan durasi, serta `redirectUrl`.
- [ ] Given webhook `settlement` dengan `signature_key` benar dan `gross_amount` sama When diterima Then `pending` atau `expired` menjadi `paid` dan masa aktif diperpanjang sekali.
- [ ] Given webhook yang sama dikirim ulang atau paralel When diproses Then perpanjangan tetap sekali (`UPDATE ... WHERE status IN ('pending','expired')`).
- [ ] Given `gross_amount` berbeda dari `amount` When webhook diterima Then status `needs_review`, tidak diperpanjang, dicatat di log, dan dikecualikan dari `payments.reconcile` (RV2-06). Admin menindaklanjuti dari daftar pembayaran berfilter status.
- [ ] Given signature salah When webhook diterima Then `401` dan tidak ada perubahan.
Edge cases:
- Pembayaran lunas setelah `expired` tetap diperpanjang memakai snapshot.
- Job `payments.reconcile` (cron `*/10 * * * *`) menanyakan status gateway untuk `pending` dan menandai `expired` setelah lewat `expires_at`.
- Notifikasi `deny` atau `cancel` → status `failed`.

### FR-09: Check-in QR
Member menampilkan QR dinamis. Token ditandatangani server (HMAC dengan `QR_SIGNING_SECRET`), berisi `memberId`, `exp`, dan `jti`, berlaku selama interval gym (30 detik) dan otomatis diperbarui di aplikasi. Admin memindai di web. Server memvalidasi token dan status, lalu menampilkan nama dan foto untuk verifikasi visual.
Fitur: F-08
Acceptance criteria:
- [ ] Given token valid dan member `active` atau `expiring_soon` When admin scan Then check-in tercatat dan respons memuat nama dan `photoUrl`.
- [ ] Given token kedaluwarsa, tanda tangan salah, atau `jti` sudah dipakai When scan Then `422 QR_INVALID`, tidak ada check-in.
- [ ] Given member `expired` When scan atau meminta QR Then `403 MEMBERSHIP_INACTIVE`.
- [ ] Given admin atau member pemilik When membuka riwayat Then check-in terurut terbaru. Member lain `404`.
Edge cases:
- Dua scan paralel dengan token sama → hanya satu sukses (UNIQUE `qr_jti`).
- Kamera tidak diizinkan: tampilkan input token manual.

### FR-10: Jadwal kelas
Admin membuat kelas satu kali atau seri mingguan. Job `classes.generate-sessions` (harian) menjaga sesi 28 hari ke depan secara idempoten (`ON CONFLICT (series_id, local_date) DO NOTHING`). `starts_at` dihitung dari `start_time` dan zona gym. Member melihat sesi `scheduled` dengan sisa kuota.
Fitur: F-09
Acceptance criteria:
- [ ] Given seri Senin 18:00 When dibuat Then sesi Senin berikutnya dibuat segera dan `local_date` terisi.
- [ ] Given generator dijalankan dua kali When selesai Then tidak ada sesi ganda.
- [ ] Given sesi seri When `startsAt` digeser ke tanggal lokal lain Then `422 details.startsAt`. Di tanggal yang sama berhasil. Kelas satu kali bebas digeser dan `local_date` dihitung ulang (RV2-03).
- [ ] Given sesi atau seri dibatalkan When member melihat jadwal Then sesi tidak muncul dan booking aktifnya `canceled`.
- [ ] Given `GET /class-sessions/{id}` atau `GET /class-series/{id}` When dibuka langsung (deep link) Then data terisi tanpa rentang tanggal (RV2-05).
Edge cases:
- Kapasitas diturunkan di bawah jumlah booking aktif → `409`.
- Rentang `from`/`to` >62 hari → `422`.
- Mengubah seri hanya memengaruhi sesi `scheduled` yang belum mulai.

### FR-11: Booking kelas
Member dengan masa aktif yang mencakup tanggal sesi (`expires_on >= local_date`) dapat memesan. Transaksi mengunci baris sesi (`FOR UPDATE`), menghitung booking aktif, lalu memasukkan booking agar tidak overbooking. Pembatalan paling lambat 2 jam sebelum mulai (RV-09).
Fitur: F-10
Acceptance criteria:
- [ ] Given sisa 1 slot dan 5 member memesan bersamaan When selesai Then tepat 1 sukses dan 4 mendapat `409 CLASS_FULL`.
- [ ] Given member `expired` pada `local_date` sesi When booking Then `403 MEMBERSHIP_INACTIVE`.
- [ ] Given sudah booking When booking lagi Then `409 ALREADY_BOOKED`. Sesi `canceled` atau sudah mulai → `409 SESSION_NOT_BOOKABLE`.
- [ ] Given sesi mulai dalam >2 jam When member membatalkan Then booking `canceled` dan slot kembali. Dalam ≤2 jam → `409 CANCEL_WINDOW_CLOSED`.
- [ ] Given admin When membuka detail sesi Then melihat peserta dan "N / kapasitas".
Edge cases:
- Booking yang dibatalkan boleh dipesan ulang selama kuota tersedia.
- Booking tidak otomatis menjadi check-in.
- Member lain membatalkan booking orang lain → `404`.

### FR-12: Pengingat masa aktif
Push FCM kepada member yang tertaut ketika sisa masa aktif tepat sama dengan `expiring_soon_days`. Job `notifications.expiry-reminders` jalan harian (cron `0 1 * * *`, 08:00 WIB). Token perangkat didaftarkan klien setelah login (RV-04). Dikerjakan setelah F-05 dan F-07.
Fitur: R-01
Acceptance criteria:
- [ ] Given member sisa 7 hari dengan token terdaftar When job jalan Then satu push terkirim dan `notification_log` mencatat `expiry:<memberId>:<expires_on>`.
- [ ] Given job dijalankan dua kali pada hari yang sama When selesai Then push tidak terkirim dua kali.
- [ ] Given FCM menjawab `invalid-token` When mengirim Then token dihapus dan job lanjut ke member lain.
- [ ] Given member memperpanjang sebelum job When job jalan Then tidak ada push.
Edge cases:
- Member tanpa akun tertaut atau tanpa token dilewati.
- Kegagalan kirim non-token menghapus baris dedupe agar dicoba lagi pada run berikutnya.

### FR-13: Pengingat jadwal kelas
Push 60 menit sebelum kelas kepada member yang booking. Job `notifications.class-reminders` jalan tiap 5 menit dan memilih booking `booked` pada sesi `scheduled` yang mulai dalam ≤60 menit. Idempoten lewat `dedupe_key` `class:<bookingId>` (insert `ON CONFLICT DO NOTHING` sebelum kirim). Dikerjakan setelah F-10.
Fitur: R-03
Acceptance criteria:
- [ ] Given booking untuk sesi yang mulai dalam 58 menit When job jalan Then satu push dengan nama kelas dan jam lokal.
- [ ] Given job berjalan berulang When sesi yang sama Then push hanya terkirim sekali per booking.
- [ ] Given booking dibatalkan atau sesi `canceled` When job jalan Then tidak ada push.
- [ ] Given sesi sudah mulai When job jalan Then tidak ada push.
Edge cases:
- Booking dibuat kurang dari 60 menit sebelum kelas tetap diingatkan sekali pada run berikutnya.
- Dua worker berjalan bersamaan tetap aman karena UNIQUE `dedupe_key`.

## 7. Non-Functional Requirements

- NFR-01: Semua endpoint `/v1/*` mewajibkan token valid. `all-routes-require-auth.int.test.ts` lulus dan `PUBLIC_ROUTES` hanya berisi `/webhooks/payment-gateway` dan route publik bawaan template.
- NFR-02: Otorisasi ditegakkan di server. Integration test wajib: bukan anggota → `404`, member ke endpoint admin → `403`, member membaca data member lain → `404`.
- NFR-03: Akses Storage dari client ditolak penuh. Signed URL berlaku ≤5 menit dan hanya dibuat setelah otorisasi API.
- NFR-04: Kode undangan minimal 8 karakter acak (≥40 bit entropi), disimpan sebagai hash, berlaku 48 jam. Maksimal 10 percobaan redeem gagal per user per 15 menit, setelahnya `429`-setara `422 INVITATION_INVALID` dengan pesan terkunci sementara.
- NFR-05: Booking, pembayaran, dan pencabutan admin berjalan dalam transaksi. Test konkurensi (≥5 request paralel untuk booking, webhook ganda, cabut-silang admin) harus lolos tanpa overbooking, perpanjangan ganda, atau gym tanpa admin.
- NFR-06: P95 respons API untuk endpoint non-ekspor ≤500 ms dengan 10.000 member dan 100.000 check-in. Daftar memakai index dan pagination.
- NFR-07: Job idempoten. Semua job (`payments.reconcile`, `classes.generate-sessions`, dua job notifikasi) aman dijalankan ulang tanpa efek ganda. Shutdown mengikuti docs/conventions.md bagian Job (pg-boss).
- NFR-08: Cakupan test: unit test use case (`computeRenewalPeriod`, status masa aktif, validasi `startOn`) mencakup semua AC di FR-04 sampai FR-06. Integration test memakai adapter `fake` untuk payment, push, dan storage. Flutter diuji dengan bloc_test dan mocktail.
- NFR-09: Data pribadi (nama, telepon, email) hanya lewat HTTPS. Log tidak memuat token, kode undangan, atau tanda tangan webhook.
- NFR-10: Teks error untuk user di Flutter dipetakan dari `ErrorCode` (docs/conventions.md bagian Format error), termasuk kode baru dan status pembayaran `needs_review` ("Pembayaran sedang ditinjau admin").
- NFR-11: Waktu hari dihitung di server dengan zona gym. Setiap perhitungan tanggal punya unit test pada batas pergantian hari.
