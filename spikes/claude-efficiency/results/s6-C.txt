# Aplikasi Membership Gym

## 1. Context & Goal

**Masalah.** Pencatatan member dan masa aktif di sebuah gym masih manual atau berantakan. Admin sulit tahu siapa yang masih aktif, pembayaran dan perpanjangan tercecer, dan jadwal kelas dikelola di luar sistem.

**Pengguna.**
- **Admin** mengelola paket, member, pembayaran, jadwal kelas, dan memindai QR check-in lewat web.
- **Member** melihat status masa aktif, menampilkan QR check-in, membayar perpanjangan di aplikasi, dan memesan kelas. Member memakai Android, iOS, atau web.

**Tujuan.** Satu aplikasi (Flutter untuk web, Android, iOS) dengan API terpisah yang menjadi sumber kebenaran masa aktif, pembayaran, check-in, dan booking untuk **satu gym**. Semua data tetap membawa `gym_id` agar nanti bisa dikembangkan untuk banyak gym tanpa merombak skema.

**Aksi pertama pengguna:** admin menambahkan member baru beserta paketnya (FR-08).

**Indikator keberhasilan.**
- Admin menambahkan member dan memperpanjang masa aktif tanpa spreadsheet.
- Status masa aktif sama di semua layar dan saat check-in, karena selalu dihitung server dengan zona waktu gym.
- Tidak pernah ada overbooking (NFR-02).
- Pembayaran online yang lunas memperpanjang masa aktif tepat satu kali (NFR-06).

**Nilai bawaan dan aturan bisnis (sumber tunggal; FR merujuk tabel ini).** Nilai yang ditandai "pengaturan gym" disimpan di tabel `gyms` dan bisa diubah admin lewat `PATCH /v1/gyms/{gymId}` (RV-09).

| Aturan | Nilai |
| --- | --- |
| Zona waktu | `gyms.timezone` (IANA, bawaan `Asia/Jakarta`). Semua "hari" dan "tanggal" dihitung dengan zona ini. |
| Member aktif | `expires_on >= hari ini` (aktif sampai akhir hari `expires_on`). Tanpa masa tenggang (RV-07). |
| `daysLeft` | `expires_on` dikurangi hari ini (tanggal gym), dalam hari. |
| Status | `expired` jika `daysLeft < 0`; `expiring_soon` jika `0 <= daysLeft <= expiringSoonDays`; selain itu `active`. |
| Hampir habis | `expiringSoonDays` = **7** (pengaturan gym, RV-09). |
| Batas batal booking | `cancelCutoffMinutes` = **120** (paling lambat 2 jam sebelum kelas mulai, pengaturan gym, RV-09). |
| Pergantian QR | `qrRotationSeconds` = **30** (pengaturan gym, RV-09). Token QR berlaku `qrRotationSeconds + 10` detik (toleransi scan) dan hanya sekali pakai. |
| Perpanjangan | Basis = `expires_on` bila member masih aktif pada tanggal bayar; basis = tanggal bayar bila sudah lewat. Masa aktif baru = basis + durasi paket (RV-07). |
| Penambahan durasi | `day`: tambah N hari. `month`/`year`: tambah bulan/tahun kalender; bila tanggal tujuan tidak ada, dipakai hari terakhir bulan itu (31 Jan + 1 bulan = 28/29 Feb). |
| Awal masa aktif member baru | `startOn` dari hari ini sampai 30 hari ke belakang. Tidak boleh di masa depan (RV2-04). |
| Pembayaran online | Berlaku 60 menit sejak dibuat. Pembayaran yang lunas setelah itu tetap diproses. |
| Undangan | Kode sekali pakai, berlaku 48 jam. |
| URL foto | Signed URL berlaku 5 menit. |
| Horizon sesi seri | Sesi kelas berulang dibuat 28 hari ke depan. |
| Pengingat | Masa aktif: pukul 09:00 waktu gym pada hari `daysLeft = expiringSoonDays` dan `daysLeft = 1`. Kelas: 60 menit sebelum mulai. |

**Aturan bawaan lain.** Satu member punya satu paket dan satu masa aktif. Semua paket boleh mengikuti semua kelas. Booking kelas tidak otomatis menjadi check-in; member tetap memindai QR saat datang.

## 2. Scope

### In scope

Fitur dan urutan fase (F-11, F-12, F-13 berasal dari rekomendasi yang diterima, RV-01):

- **Fase 0, Fondasi**
  - **F-01 Akun dan login:** login, logout, pembuatan user otomatis tanpa peran, halaman profil singkat.
  - **F-02 Pengelolaan gym dan peran:** data dan pengaturan gym, peran admin dan member, pembatasan akses, admin pertama lewat CLI, daftar dan pencabutan admin.
- **Fase 1, Member dan paket**
  - **F-03 Paket membership.**
  - **F-04 Data member:** tambah dan ubah member, foto lewat signed URL, undangan sekali pakai dan penautan akun ke member (dipindah dari F-01, RV-03; RV-02), hapus akun (RV-10).
  - **F-05 Status masa aktif dan tanggal kedaluwarsa.**
- **Fase 2, Pembayaran dan perpanjangan**
  - **F-06 Pencatatan pembayaran manual dan perpanjangan.**
  - **F-07 Pembayaran online lewat payment gateway Midtrans.**
  - **F-11 Ekspor laporan member dan pembayaran (R-06):** setelah F-06.
- **Fase 3, Check-in QR**
  - **F-08 Check-in kehadiran dengan QR.**
- **Fase 4, Kelas dan booking**
  - **F-09 Jadwal kelas (termasuk berulang mingguan).**
  - **F-10 Booking kelas.**
- **Fase 5, Notifikasi** (FCM, job terjadwal pg-boss, token perangkat, APNs; RV-04)
  - **F-12 Pengingat masa aktif hampir habis (R-01):** setelah F-05 dan F-07.
  - **F-13 Pengingat jadwal kelas (R-03):** setelah F-10 dan F-12.

### Non-goals

- Dukungan banyak gym atau cabang dalam satu aplikasi. Skema sudah membawa `gym_id`, tetapi fiturnya belum dibuat.
- Mode offline: check-in, booking, dan pembayaran selalu butuh internet.
- Pembaruan data realtime. Data diambil saat halaman dibuka atau di-refresh.
- Instruktur atau personal trainer sebagai pengguna dengan login sendiri.
- Penjualan produk atau kasir (suplemen, minuman, merchandise).
- Absensi dan penggajian staf.
- Check-in mandiri lewat perangkat atau kios tanpa admin.
- Refund otomatis lewat payment gateway.
- Dashboard ringkasan untuk admin.
- Daftar tunggu kelas.
- Cuti atau bekukan membership.
- Kode promo dan diskon paket.
- Push notification di web. Push hanya untuk Android dan iOS.
- Impor data member lama dari spreadsheet.

## 3. Tech Constraints

**Monorepo (pnpm workspaces, tanpa Turborepo).** `apps/api` (Hono + TypeScript), `apps/app` (Flutter: web, Android, iOS), `packages/contract` (`openapi.json` + client Dart `api_client` hasil generate; jangan diedit manual). Struktur dan perintah mengikuti `docs/conventions.md`, yang menjadi sumber kebenaran bila bertentangan dengan ringkasan ini.

**Konvensi proyek yang wajib diikuti.**
- **Versi dan verifikasi.**
  - Versi library dipin pasti (tanpa `^`/`~`) dan dicatat di `docs/conventions.md`.
  - `pnpm check` adalah satu-satunya perintah verifikasi dan harus hijau sebelum task dicentang.
  - Setelah route atau skema Zod berubah, jalankan `pnpm contract:generate` dan commit hasilnya.
  - Lint dan format memakai Biome.
  - TypeScript `strict` dengan import relatif berakhiran `.js`.
- **API.**
  - Prefix `/v1`, resource jamak, JSON camelCase, timestamp ISO 8601 UTC berakhiran `Z`, tanggal `YYYY-MM-DD`.
  - Route dibuat dengan `createRoute` + `.openapi('Nama')` dan punya `operationId`.
  - Semua `/v1/*` lewat middleware `authenticate`.
  - Aturan bisnis ditegakkan di API (Zod, use case, constraint DB). Client tidak boleh lebih ketat dari API.
  - Teks wajib memakai `.trim()` sebelum `.min()`.
  - Format error `{ error: { code, message, details? } }`. Kode baru ditambahkan ke `error-codes.ts`, lalu dipetakan di `failureCodeOf` dan `failure_messages.dart`.
  - Pelanggaran keunikan lewat constraint bernama dan error domain, menjadi `409`.
  - Pagination kursor `?limit&cursor` dengan respons `{ items, nextCursor }`. Daftar yang dibatasi rentang tanggal memakai `{ items }` tanpa kursor.
  - Resource tidak ditemukan atau milik gym lain memberi `404`. Peran kurang memberi `403`.
- **Database.**
  - Drizzle + `pg` + drizzle-kit, PostgreSQL 17.
  - Tabel snake_case jamak. Timestamp `timestamptz(3)` lewat helper `schema/columns.ts`, diisi jam database (`now()`).
  - Kolom `date` memakai `mode: 'string'`.
  - Constraint dan index bernama `<tabel>_<kolom>_<jenis>`.
  - Foreign key lewat `foreignKey({ name, ... })`. Enum ditulis `text` + `check`.
  - Migrasi lewat `db:generate`; migrasi yang sudah di-commit tidak diedit.
- **Clean Architecture per fitur.**
  - API: `domain` → `usecases` → `infrastructure` (Drizzle) → `http` (route + Zod). Use case berupa fungsi pabrik, dependency lewat objek pertama.
  - Flutter: `domain` (entity, interface repository, use case), `data` (data source dari client OpenAPI, DTO + mapper, repository impl), `presentation` (Cubit sealed state, pages, widgets).
  - Flutter memakai go_router, get_it manual per fitur, `Result` sealed (`Ok`/`Err`), `Failure` + `logFailure` di batas data. Teks UI Bahasa Indonesia, dan teks kegagalan hanya dari `failure_messages.dart` (D-03).
- **Port dan adapter** (`core/ports`, pola `none` / `fake` / sungguhan; `fake` ditolak di produksi). Setiap env baru ditambahkan ke `env.ts`, `.env.example`, dan `test/setup/env.ts`.
  - `PushSender` (FCM) dan `FileStorage` sudah ada. `FileStorage` ditambah `createReadUrl(path, { expiresInSeconds })`, dengan adapter `firebase` memakai signed URL dan adapter `fake` mengembalikan URL palsu.
  - Port baru `PaymentGateway`: `createTransaction`, `getStatus`, `verifyNotification`. Adapter `none`, `fake`, `midtrans`; env `PAYMENT_ADAPTER`, `MIDTRANS_SERVER_KEY`, `MIDTRANS_IS_PRODUCTION` (RV-08).
  - Port baru `AuthAccountService` (`deleteUser(firebaseUid)`) dengan adapter `none`/`fake`/`firebase`, untuk hapus akun dan CLI (`getUserByEmail`).
  - Env baru lain: `QR_SIGNING_SECRET` (wajib, minimal 32 karakter), `APP_WEB_URL` (dasar link undangan).
- **Job terjadwal.** pg-boss di dalam container API (`RUN_WORKER=true`; RV-04). Job milik fitur di `features/<fitur>/jobs/*.job.ts`, nama `<area>.<aksi>`, cron UTC, semua idempoten:
  - `payments.reconcile` (`*/10 * * * *`)
  - `classes.generate-sessions` (harian)
  - `notifications.expiry-reminders` (`*/30 * * * *`, hanya bertindak bila waktu lokal gym ≥ 09:00)
  - `notifications.class-reminders` (`*/5 * * * *`)

  Satu container dengan satu worker; pg-boss menjamin satu eksekusi per jadwal.
- **Notifikasi (RV-04).**
  - FCM untuk push Android dan iOS.
  - Tabel `device_tokens` per user dan `notification_deliveries` dengan unique `(kind, dedupe_key)` untuk mencegah notifikasi ganda.
  - Kunci APNs (.p8) diunggah sekali ke konsol Firebase, dan iOS mengaktifkan capability Push Notifications. Di lokal `PUSH_ADAPTER=fake` dan config Flutter `PUSH_ENABLED=false`.
- **File (RV-05).**
  - Foto member di Cloud Storage for Firebase, lewat firebase-admin di API.
  - `storage.rules` tetap menolak semua akses client; client tidak pernah menyentuh Storage.
  - Upload lewat endpoint API dan baca lewat signed URL berumur 5 menit yang dibuat API.
  - PostgreSQL hanya menyimpan path dan metadata. Path `gyms/<gymId>/members/<memberId>/photo-<uuid>.<ext>`.
- **Autentikasi dan peran.**
  - Firebase Auth email/password di client. API memverifikasi ID token lewat `TokenVerifier`.
  - Tabel `users` tanpa password dibuat saat request pertama (`syncUser`) dan **tanpa peran** (RV-06). Peran ada di `gym_users`.
  - Admin pertama hanya lewat CLI `bootstrap-gym` (FR-05). Admin berikutnya dan penautan member hanya lewat kode undangan (RV-02).
  - Penautan tidak pernah memakai email.
- **Pembayaran.** Midtrans Snap (sandbox untuk dev dan test) dengan metode transfer bank/virtual account, QRIS, dan e-wallet (GoPay, ShopeePay). Kartu tidak didukung. Pembuatan transaksi dan status lewat REST Midtrans dengan `fetch`, tanpa SDK.
- **Library Flutter tambahan** (dipin saat dipasang): `firebase_messaging`, `qr_flutter` (tampilan QR), `mobile_scanner` (scan kamera di web), `image_picker`, `url_launcher`.
- **Deploy.** API sebagai container yang selalu hidup (`apps/api/Dockerfile`). Migrasi dijalankan terpisah dengan `node dist/db/migrate.js` sebelum server. Flutter web di hosting statis. Mobile lewat store. Server berjalan dengan `NODE_ENV=production`, jadi adapter `fake` dan host emulator ditolak.
- **Testing.**
  - API: Vitest. Unit test per use case dengan repository palsu; integration test dengan PostgreSQL, Auth Emulator, dan Storage Emulator.
  - App: flutter_test + bloc_test + mocktail.
  - Fitur tenant/peran memakai pola "bukan anggota → 404, peran kurang → 403".
  - Rute baru otomatis diperiksa `all-routes-require-auth.int.test.ts`. Pengecualian yang didaftarkan di `PUBLIC_ROUTES`: `/health` dan `POST /webhooks/midtrans` (pengecualian prefix `/v1`; dicatat di `docs/conventions.md`).
- **Fitur contoh `notes`** dihapus setelah fitur pertama proyek berdiri, sesuai bagian "Menghapus fitur contoh notes".

**Constraint dan index penting** (nama mengikuti pola `<tabel>_<kolom>_<jenis>`).

- **users**
  - `users_firebase_uid_unique`.
  - `users_email_lowercase_check`.
  - Tidak ada kolom peran: user baru tanpa peran (RV-06).
- **gyms**
  - `gyms_expiring_soon_days_check` (0–60).
  - `gyms_cancel_cutoff_minutes_check` (0–1440).
  - `gyms_qr_rotation_seconds_check` (10–300).
  - `timezone` divalidasi sebagai nama IANA di Zod.
- **gym_users**
  - `gym_users_gym_id_user_id_unique` (satu peran per user per gym).
  - `gym_users_role_check` (`admin`/`member`).
  - Index `(gym_id, role)`.
- **invitations**
  - `invitations_code_hash_unique` (SHA-256 dari kode).
  - `invitations_kind_check` (`member`/`admin`).
  - `invitations_member_id_kind_check`: `member_id` wajib untuk `member` dan harus `NULL` untuk `admin`.
  - Unique parsial `invitations_member_id_pending_unique` pada `member_id` di mana `used_at IS NULL AND revoked_at IS NULL` (satu undangan aktif per member).
  - Kode asli tidak pernah disimpan.
- **invitation_redeem_failures:** index `(user_id, attempted_at)`.
- **plans**
  - Unique `plans_gym_id_name_unique` pada `(gym_id, lower(name))`.
  - `plans_duration_value_check` (1–999).
  - `plans_duration_unit_check` (`day`/`month`/`year`).
  - `plans_price_amount_check` (1–100000000, rupiah bulat).
  - Paket tidak pernah dihapus, hanya `is_active=false`.
  - Pagination: index `(gym_id, created_at DESC, id DESC)`.
- **members**
  - `members_user_id_unique` (satu akun ke satu member, nullable).
  - `members_expires_on_check` (`expires_on >= started_on`).
  - FK `plan_id` RESTRICT; FK `user_id` ON DELETE SET NULL.
  - `phone` dan `email` nullable di database agar bisa dianonimkan; API tetap mewajibkan `phone` saat membuat.
  - Index `(gym_id, expires_on)`, index pagination `(gym_id, created_at DESC, id DESC)`, index `(gym_id, lower(full_name))`.
- **payments**
  - `payments_status_check` (`pending`, `paid`, `failed`, `expired`, `needs_review`; RV2-06).
  - `payments_source_check` (`manual`/`online`).
  - `payments_method_check` (`cash`/`transfer` untuk manual; `NULL` untuk online).
  - **Snapshot durasi (RV2-01):** `plan_duration_value` dan `plan_duration_unit` NOT NULL, dengan `payments_plan_duration_value_check` dan `payments_plan_duration_unit_check` identik dengan `plans`. Keduanya diisi saat pembayaran dibuat, bersama `plan_name` dan `amount`.
  - `payments_amount_check` (> 0).
  - `payments.id` dipakai sebagai `order_id` di Midtrans.
  - Perpanjangan hanya sekali: `applied_at` diisi dalam transaksi yang mengunci baris pembayaran dan baris member (`FOR UPDATE`).
  - FK `member_id` RESTRICT (riwayat pembukuan tetap ada setelah akun dihapus); `recorded_by_user_id` ON DELETE SET NULL.
  - Index `(gym_id, created_at DESC, id DESC)`, `(member_id, created_at DESC, id DESC)`, dan `(status, source)` untuk rekonsiliasi.
  - `needs_review` dikecualikan dari rekonsiliasi.
- **check_ins**
  - `check_ins_qr_jti_unique`: satu token QR hanya bisa menghasilkan satu check-in.
  - Index `(gym_id, checked_in_at DESC, id DESC)` dan `(member_id, checked_in_at DESC, id DESC)`.
  - Penolakan check-in tidak menulis baris.
- **class_series**
  - `class_series_weekday_check` (1–7, ISO, Senin=1).
  - `class_series_capacity_check` (≥ 1).
  - `class_series_duration_minutes_check` (5–480).
  - `class_series_start_time_check` (`HH:MM`).
- **class_sessions**
  - `class_sessions_series_id_local_date_unique`: unik parsial pada `(series_id, local_date)` di mana `series_id IS NOT NULL`. Ini membuat generator idempoten (RV2-03).
  - `class_sessions_booked_count_check` (`0 <= booked_count <= capacity`).
  - `class_sessions_status_check` (`scheduled`/`cancelled`).
  - Index `(gym_id, starts_at)` dan `(gym_id, local_date)`.
  - `local_date` selalu dihitung dari `starts_at` dengan zona gym, kecuali sesi seri yang `local_date`-nya menjadi kunci (digeser hanya di tanggal yang sama).
- **bookings**
  - Unique parsial `bookings_session_id_member_id_booked_unique` di mana `status='booked'`.
  - `bookings_status_check` (`booked`/`cancelled`), `bookings_cancelled_by_check` (`member`/`admin`).
  - Index `(member_id, created_at DESC, id DESC)` dan `(session_id, status)`.
  - Booking atomik lewat `UPDATE class_sessions SET booked_count = booked_count + 1 WHERE id=$1 AND status='scheduled' AND booked_count < capacity` dalam transaksi yang sama dengan insert booking.
- **device_tokens**
  - `device_tokens_token_unique`.
  - `device_tokens_platform_check` (`android`/`ios`).
  - FK `user_id` ON DELETE CASCADE.
- **notification_deliveries**
  - `notification_deliveries_kind_dedupe_key_unique` pada `(kind, dedupe_key)`.
  - `notification_deliveries_kind_check` (`expiry_soon`, `expiry_tomorrow`, `class_reminder`).
  - `notification_deliveries_status_check` (`pending`, `sent`, `failed`).
  - Kunci dedupe: `<memberId>:<expiresOn>` untuk pengingat masa aktif, `<bookingId>` untuk pengingat kelas.
- **Penghapusan akun (RV-10).**
  - Baris `members` tidak dihapus tetapi dianonimkan: nama menjadi "Anggota Terhapus", `phone`/`email`/`user_id`/foto dikosongkan, `anonymized_at` diisi.
  - Riwayat `payments`, `check_ins`, dan `bookings` tetap ada.
  - `users`, `gym_users`, `device_tokens`, dan `notification_deliveries` milik user dihapus.
- **Kunci baris `gyms` (RV2-02).** Operasi yang mengubah jumlah admin (cabut admin, hapus akun admin, redeem undangan admin) menjalankan `SELECT ... FROM gyms WHERE id=$1 FOR UPDATE` sebelum menghitung admin, dalam transaksi yang sama.
- Semua tabel utama membawa `gym_id`; `check_ins` dan `bookings` ikut membawanya agar query tetap dibatasi gym.

## 5. API Contract

**Konvensi umum.**
- Semua path berprefix `/v1`, kecuali `POST /webhooks/midtrans` dan `GET /health`.
- Semua endpoint `/v1` butuh `Authorization: Bearer <ID token>`. Tanpa token atau token salah memberi `401 UNAUTHENTICATED` (tidak diulang di tiap endpoint).
- Path `{gymId}`, `{memberId}`, dan sejenisnya divalidasi `z.uuid()` (bukan UUID → `422 details.<nama>`).
- Di bawah `/v1/gyms/{gymId}/*`, middleware membaca `gym_users`. User tanpa peran di gym itu menerima `404 NOT_FOUND`. Peran kurang menerima `403 FORBIDDEN` (diperiksa di use case). Resource milik gym lain atau member lain memberi `404`.
- "Admin" berarti peran `admin`; "Member" berarti peran `member`.
- Body tidak valid memberi `422 VALIDATION_ERROR` dengan `details` (tidak diulang di tiap endpoint).

**Kode error tambahan** (ditambahkan ke `error-codes.ts`, dipetakan di Flutter):

| ErrorCode | HTTP | Kapan |
| --- | --- | --- |
| `MEMBERSHIP_INACTIVE` | 409 | Member kedaluwarsa pada tanggal yang relevan (check-in atau booking) |
| `QR_INVALID` | 400 | Token QR rusak, tanda tangan salah, atau gym berbeda |
| `QR_EXPIRED` | 409 | Token QR sudah lewat masa berlaku |
| `QR_ALREADY_USED` | 409 | Token QR sudah pernah menghasilkan check-in |
| `INVITATION_INVALID` | 409 | Kode salah, kedaluwarsa, sudah dipakai, atau dicabut (satu pesan untuk semua) |
| `LAST_ADMIN` | 409 | Aksi akan membuat gym tanpa admin |
| `PLAN_INACTIVE` | 409 | Paket nonaktif dipakai untuk member atau pembayaran baru |
| `CLASS_FULL` | 409 | Kuota habis |
| `ALREADY_BOOKED` | 409 | Member sudah punya booking aktif di sesi itu |
| `SESSION_NOT_BOOKABLE` | 409 | Sesi dibatalkan atau sudah mulai |
| `CANCEL_WINDOW_CLOSED` | 409 | Lewat batas batal booking |
| `RATE_LIMITED` | 429 | Terlalu banyak percobaan |
| `PAYMENT_GATEWAY_ERROR` | 502 | Payment gateway gagal atau tidak bisa dihubungi |

**Skema bersama** (nama komponen OpenAPI = nama kelas Dart):
- `User {id, email|null, displayName|null}`
- `GymRole {gymId, gymName, role: admin|member, memberId|null}`
- `Me {user: User, roles: GymRole[]}`
- `Gym {id, name, address|null, timezone, expiringSoonDays, cancelCutoffMinutes, qrRotationSeconds}`
- `Admin {userId, displayName|null, email|null, since}`
- `Plan {id, name, durationValue, durationUnit: day|month|year, priceAmount, isActive, createdAt, updatedAt}`
- `Member {id, fullName, phone|null, email|null, plan: {id, name}|null, startedOn, expiresOn, status: active|expiring_soon|expired, daysLeft, hasPhoto, linked, createdAt, updatedAt}`
- `Invitation {id, kind: member|admin, memberId|null, expiresAt, usedAt|null, revokedAt|null, createdAt}`
- `InvitationCreated` = `Invitation` + `{code, link}`. `code` hanya muncul di respons pembuatan.
- `Payment {id, memberId, memberName, planId, planName, planDurationValue, planDurationUnit, amount, status: pending|paid|failed|expired|needs_review, source: manual|online, method: cash|transfer|null, paidAt|null, expiresAt|null, periodStart|null, periodEnd|null, note|null, createdAt}`
- `PaymentCheckout` = `Payment` + `{checkout: {redirectUrl, token}}`
- `CheckIn {id, memberId, memberName, checkedInAt}`
- `CheckInResult {id, checkedInAt, member: {id, fullName, photoUrl|null, photoUrlExpiresAt|null, status, expiresOn}}`
- `ClassSeries {id, name, instructorName, capacity, durationMinutes, weekday, startTime, startOn, endOn|null, cancelledAt|null}`
- `ClassSession {id, seriesId|null, name, instructorName, startsAt, localDate, durationMinutes, capacity, bookedCount, remaining, status: scheduled|cancelled, myBooking: {id, status}|null}`. `myBooking` hanya terisi untuk Member.
- `Booking {id, sessionId, memberId, memberName, status: booked|cancelled, cancelledBy|null, cancelledAt|null, createdAt, session?: ClassSession}`
- `DeviceToken {id, platform, updatedAt}`

## 6. Functional Requirements

Keterangan UI: rute Flutter terlindungi kecuali `/login` dan `/register`. Setelah login, `GET /v1/me` menentukan beranda. Tanpa peran → `/redeem`; admin → `/admin`; member → `/home`. Parameter `next` pada `/login?next=...` mengembalikan pengguna ke halaman tujuan setelah login.

### FR-01: Login, logout, dan pembuatan user otomatis

Pengguna mendaftar dan login dengan email/password lewat Firebase Auth. API membuat baris `users` pada request pertama dan tidak memberi peran apa pun (RV-06). Logout menghapus sesi.

Fitur: F-01

Acceptance criteria:
- [ ] Given token Firebase valid dan belum ada baris `users` When `GET /v1/me` Then `200` dengan `roles: []` dan satu baris `users` dibuat dengan email huruf kecil.
- [ ] Given user sudah ada When `GET /v1/me` dipanggil dua kali Then tetap satu baris (unique `firebase_uid`) dan `last_seen_at` diperbarui.
- [ ] Given user baru tanpa peran When memanggil endpoint apa pun di bawah `/v1/gyms/{gymId}` Then `404 NOT_FOUND`, dan tidak pernah otomatis menjadi admin atau member.
- [ ] Given request tanpa header `Authorization` When memanggil `/v1/me` Then `401`.
- [ ] Given pengguna login di aplikasi When menekan "Keluar" Then sesi Firebase dihapus dan pengguna diarahkan ke `/login`.

Edge cases:
- Dua request pertama bersamaan dengan token yang sama tidak menghasilkan duplikat atau error 500 (`ON CONFLICT`).
- Token kedaluwarsa atau untuk project lain memberi `401` tanpa mencatat token di log.
- Akun Firebase tanpa email: `users.email` bernilai `NULL`.

### FR-02: Halaman profil

Halaman profil menampilkan nama, email, dan peran pengguna, serta tombol "Keluar" dan "Hapus akun" (FR-13).

Fitur: F-01

Acceptance criteria:
- [ ] Given pengguna login When membuka `/profile` Then nama, email, dan peran tampil dari `GET /v1/me`.
- [ ] Given pengguna tanpa peran When membuka `/profile` Then peran tampil "Belum ada peran" dan tersedia tautan ke `/redeem`.
- [ ] Given kegagalan jaringan When memuat profil Then `FailureView` dengan tombol "Coba lagi".

Edge cases:
- `displayName` kosong: tampilkan email.

### FR-03: Profil gym dan pengaturan

Admin melihat dan mengubah data gym (nama, alamat, zona waktu) dan pengaturan (`expiringSoonDays`, `cancelCutoffMinutes`, `qrRotationSeconds`; RV-09).

Fitur: F-02

Acceptance criteria:
- [ ] Given admin When `PATCH /v1/gyms/{gymId}` dengan `expiringSoonDays: 10` Then `200` dan status member dihitung dengan ambang 10 hari.
- [ ] Given `timezone: "Bukan/Zona"` When PATCH Then `422 details.timezone`.
- [ ] Given `qrRotationSeconds: 5` When PATCH Then `422` (batas 10–300).
- [ ] Given member When PATCH gym Then `403`; dan `GET /v1/gyms/{gymId}` tetap `200`.
- [ ] Given body kosong When PATCH Then `422 details._root`.

Edge cases:
- Mengubah zona waktu tidak mengubah `expires_on` (tanggal murni), tetapi mengubah `localDate` sesi baru yang dibuat berikutnya. Sesi lama tidak dihitung ulang.

### FR-04: Otorisasi berdasarkan peran

Semua data dibatasi gym dan peran. Member hanya melihat datanya sendiri; admin mengelola semua data gym.

Fitur: F-02

Acceptance criteria:
- [ ] Given user tanpa peran di gym When memanggil `GET /v1/gyms/{gymId}` Then `404`.
- [ ] Given member When memanggil `GET /v1/gyms/{gymId}/members` Then `403`.
- [ ] Given member A When `GET /v1/gyms/{gymId}/members/{memberB}` Then `404`.
- [ ] Given admin When `GET /v1/gyms/{gymId}/members/{id}` Then `200`.
- [ ] Given semua route baru When `all-routes-require-auth.int.test.ts` berjalan Then hanya `/health` dan `POST /webhooks/midtrans` yang publik.

Edge cases:
- `gymId` bukan UUID memberi `422 details.gymId`.
- `gymId` UUID valid tapi gym lain memberi `404`.

### FR-05: Admin pertama lewat CLI

Admin pertama dibuat sekali saat deploy lewat skrip CLI. Tidak ada jalur lain untuk membuat admin tanpa undangan (RV-06).

Perintah: `node dist/cli/bootstrap-gym.js --gym-name "..." --timezone Asia/Jakarta --admin-email <email>`. Lokal: `pnpm --filter api bootstrap:gym -- <argumen>`. Akun Firebase untuk email itu harus sudah ada (didaftarkan lewat aplikasi atau konsol). CLI mencarinya lewat `AuthAccountService.getUserByEmail`.

Fitur: F-02

Acceptance criteria:
- [ ] Given belum ada gym dan akun Firebase untuk `a@x.id` ada When CLI dijalankan Then satu baris `gyms`, satu baris `users`, dan satu baris `gym_users` dengan peran `admin` dibuat dan exit code 0.
- [ ] Given gym sudah punya admin When CLI dijalankan lagi Then tidak ada perubahan data, pesan mengarahkan ke undangan admin, dan exit code 1.
- [ ] Given email tidak ada di Firebase When CLI dijalankan Then exit code 1 dan pesan menyebut email itu tanpa membuat baris apa pun.
- [ ] Given zona waktu tidak valid When CLI dijalankan Then exit code 1.

Edge cases:
- CLI hanya membutuhkan `DATABASE_URL` dan `FIREBASE_PROJECT_ID`, bukan seluruh env server.
- Dijalankan bersamaan dua kali: hanya satu gym dan satu admin yang terbentuk (transaksi + kunci).

### FR-06: Daftar dan pencabutan admin

Admin melihat daftar admin dan mencabut peran admin lain atau dirinya sendiri, selama gym tetap punya minimal satu admin. Penghitungan dijaga kunci baris `gyms` (RV2-02).

Fitur: F-02

Acceptance criteria:
- [ ] Given dua admin A dan B When A mencabut B Then `204` dan B tanpa peran; `GET .../admins` hanya memuat A.
- [ ] Given satu admin A When A mencabut dirinya Then `409 LAST_ADMIN` dan peran tetap.
- [ ] Given admin A dan B When A mencabut B bersamaan dengan B mencabut A Then tepat satu `204` dan satu `409 LAST_ADMIN`, dan gym tetap punya satu admin (integration test cabut-silang bersamaan).
- [ ] Given pencabutan Then use case menjalankan `SELECT ... FROM gyms WHERE id=$1 FOR UPDATE` sebelum menghitung admin, dalam transaksi yang sama.
- [ ] Given member When memanggil `DELETE .../admins/{userId}` Then `403`.

Edge cases:
- `userId` yang bukan admin gym ini memberi `404`.

### FR-07: Paket membership

- [ ] Given kode kedaluwarsa, salah, atau dicabut Then `409 INVITATION_INVALID` dengan pesan yang sama.

- [ ] Given orang lain mendaftar dengan email member tetapi tanpa kode When memanggil API gym Then `404` dan tidak melihat data member.

Edge cases:

### FR-13: Hapus akun dari halaman profil

Dari halaman profil, pengguna dapat menghapus akunnya (syarat App Store dan Google Play; RV-10). Pengguna mengetik "HAPUS" untuk konfirmasi.

Fitur: F-04

Acceptance criteria:
- [ ] Given member dengan booking mendatang When `POST /me/delete-account {confirmation:"HAPUS"}` Then `204`; baris `members` dianonimkan (nama "Anggota Terhapus", `phone`/`email`/`user_id`/foto kosong, `anonymized_at` terisi); booking mendatangnya `cancelled` dan `booked_count` berkurang.
- [ ] Given penghapusan Then `payments`, `check_ins`, dan booking lampau tetap ada dan menunjuk ke member yang dianonimkan; baris `users`, `gym_users`, dan `device_tokens` dihapus; file foto dihapus; akun Firebase dihapus lewat `AuthAccountService`.
- [ ] Given `confirmation:"hapus"` atau kosong When POST Then `422 details.confirmation`.
- [ ] Given admin terakhir When menghapus akun Then `409 LAST_ADMIN` dan tidak ada data berubah.
- [ ] Given dua admin terakhir menghapus akun bersamaan Then tepat satu `204` dan satu `409 LAST_ADMIN` (kunci `gyms FOR UPDATE`, RV2-02).

### FR-14: Perhitungan status masa aktif

Server menghitung status dari `expires_on` memakai zona waktu gym dan aturan di Bagian 1. Perhitungan memakai satu fungsi `membershipStatus(expiresOn, todayInGymTz, expiringSoonDays)` yang dipakai semua use case dan query filter.

Fitur: F-05

Acceptance criteria:
- [ ] Given hari ini 2026-11-05 dan `expiringSoonDays=7` When `expiresOn=2026-11-04` Then `expired`, `daysLeft=-1`.
- [ ] Given `expiresOn=2026-11-05` Then `expiring_soon`, `daysLeft=0` (masih aktif sampai akhir hari).
- [ ] Given `expiresOn=2026-11-12` Then `expiring_soon` (`daysLeft=7`); `2026-11-13` Then `active` (`daysLeft=8`).
- [ ] Given waktu server 2026-11-05 17:30 UTC dan zona `Asia/Jakarta` Then hari ini gym adalah 2026-11-06.
- [ ] Given `expiringSoonDays` diubah menjadi 3 Then `daysLeft=5` menjadi `active`.

Edge cases:
- Tes batas pukul 23:59 dan 00:00 di zona gym, serta zona lain (misalnya `Asia/Makassar`).
- Tidak ada masa tenggang: `expired` berarti check-in dan booking ditolak seketika.

### FR-15: Tampilan status dan daftar member bermasalah

### FR-16: Pembayaran manual dan perpanjangan masa aktif

Admin mencatat pembayaran tunai atau transfer. Pembayaran langsung berstatus `paid` dan memperpanjang masa aktif. Aturan perpanjangan (RV-07) dan snapshot durasi (RV2-01) diterapkan oleh fungsi murni `computeRenewalPeriod` yang membaca durasi dari kolom snapshot di `payments`, bukan dari `plans`.

Fitur: F-06

Acceptance criteria:
- [ ] Given member `expiresOn=2026-11-10` aktif dan bayar 2026-11-05 paket 1 bulan When admin `POST /payments` Then `periodStart=2026-11-10`, `periodEnd=2026-12-10`, `members.expires_on=2026-12-10`.
- [ ] Given pembayaran pada 2026-11-10 (hari terakhir, masih aktif) Then basis tetap `expires_on` (`2026-12-10`).
- [ ] Given member `expiresOn=2026-11-01` (sudah lewat) dan bayar 2026-11-05 Then `periodStart=2026-11-05`, `periodEnd=2026-12-05`.
- [ ] Given pembayaran dibuat Then `payments` menyimpan `plan_name`, `amount`, `plan_duration_value`, dan `plan_duration_unit` sesuai paket saat itu (RV2-01).
- [ ] Given pembayaran online 1 bulan dibuat lalu admin mengubah paket menjadi 3 bulan atau 1 minggu, kemudian pembayaran lunas Then perpanjangan tetap 1 bulan dari snapshot.
- [ ] Given pembayaran diterapkan Then `members.plan_id` menjadi paket yang dibayar.
- [ ] Given dua permintaan penerapan pembayaran yang sama bersamaan Then perpanjangan terjadi sekali (`applied_at`, kunci baris).
- [ ] Given paket nonaktif When admin mencatat pembayaran Then `409 PLAN_INACTIVE`.
- [ ] Given member When `POST /payments` Then `403`.

Edge cases:
- 31 Jan + 1 bulan menjadi 28 Feb (atau 29 Feb tahun kabisat).
- Tanggal bayar dihitung dari waktu server saat pembayaran diproses, dengan zona gym.
- Tidak ada masa tenggang: bayar sehari setelah kedaluwarsa dihitung dari tanggal bayar.

### FR-17: Riwayat pembayaran

### FR-18: Memulai pembayaran online

Member memilih paket dan membayar lewat Midtrans Snap. - [ ] Given gateway gagal When POST Then `502 PAYMENT_GATEWAY_ERROR` dan tidak ada baris `payments` baru.

### FR-19: Webhook Midtrans

`POST /webhooks/midtrans` memverifikasi tanda tangan, memetakan status, dan menerapkan perpanjangan tepat sekali. Pembayaran yang lunas setelah `expired` atau `failed` tetap diproses, karena uang sudah diterima (RV2-01).

Pemetaan status:

| `transaction_status` | Hasil |
| --- | --- |
| `settlement`, atau `capture` dengan `fraud_status=accept` | `paid` |
| `pending`, atau `capture` dengan `fraud_status=challenge` | tetap `pending` |
| `deny`, `cancel`, `failure` | `failed` |
| `expire` | `expired` |

Fitur: F-07

Acceptance criteria:
- [ ] Given tanda tangan salah When webhook diterima Then `401` dan tidak ada perubahan data.
- [ ] Given `settlement` dengan `gross_amount` sama dengan `amount` When webhook diterima Then status `paid`, `paid_at` terisi, perpanjangan diterapkan sesuai FR-16 dengan snapshot durasi, dan respons `200`.
- [ ] Given webhook `settlement` yang sama dikirim 10 kali (berurutan atau bersamaan) Then masa aktif bertambah sekali dan semua respons `200`.
- [ ] Given pembayaran berstatus `expired` When `settlement` datang kemudian Then status menjadi `paid` dan perpanjangan diterapkan.
- [ ] Given pembayaran sudah `paid` When `expire` atau `cancel` datang Then status tetap `paid` (tidak mundur).
- [ ] Given `gross_amount` tidak sama dengan `payments.amount` When `settlement` datang Then status menjadi `needs_review`, masa aktif tidak berubah, dan kejadian dicatat di log tingkat `warn` (RV2-06).
- [ ] Given pembayaran `needs_review` When webhook berikutnya datang Then tidak ada perubahan.
- [ ] Given `order_id` yang tidak dikenal Then `404`.
- [ ] Given `gross_amount` "350000.00" dan `amount` 350000 Then dianggap sama.

Edge cases:
- Webhook yang menunggu kunci baris diproses berurutan; yang kedua melihat `applied_at` terisi dan tidak melakukan apa pun.
- `needs_review` tampil di daftar pembayaran admin dengan filter status; admin menindaklanjuti dengan mencatat pembayaran manual (FR-16) bila perlu. Member melihat "Sedang ditinjau admin".

### FR-20: Rekonsiliasi pembayaran

Job `payments.reconcile` (tiap 10 menit) memeriksa pembayaran online `pending` ke gateway lewat `getStatus` dan menerapkan hasilnya dengan logika yang sama dengan webhook, sebagai jaring pengaman bila webhook hilang.

Fitur: F-07

Acceptance criteria:
- [ ] Given pembayaran `pending` yang sudah lunas di gateway tetapi webhook tidak datang When job berjalan Then status `paid` dan perpanjangan diterapkan sekali.
- [ ] Given pembayaran `pending` dengan `expiresAt` lewat dan gateway melaporkan `expire` atau tidak menemukan transaksi Then status menjadi `expired`.
- [ ] Given pembayaran `needs_review` Then tidak pernah diperiksa job (dikecualikan dari rekonsiliasi).
- [ ] Given job berjalan dua kali berturut-turut Then hasil sama dengan sekali jalan.
- [ ] Given gateway tidak bisa dihubungi untuk satu pembayaran Then pembayaran lain tetap diproses dan kegagalan dicatat di log.

Edge cases:
- Pembayaran yang sudah `expired` tidak diperiksa job; ia hanya bisa menjadi `paid` lewat webhook.
- Job memakai `FOR UPDATE SKIP LOCKED` agar tidak bertabrakan dengan webhook.

### FR-21: Pembuatan QR check-in oleh member

Aplikasi member menampilkan QR dinamis. Server menerbitkan token bertanda tangan HMAC-SHA256 (`QR_SIGNING_SECRET`) berisi `{v, g: gymId, m: memberId, jti, exp}`. QR berganti tiap `qrRotationSeconds` (30 detik, RV-09), dan Flutter mengambil token baru sebelum yang lama berganti.

- [ ] Given member `expired` Then `409 MEMBERSHIP_INACTIVE` dan tidak ada token.
- [ ] Given halaman QR terbuka Then token diganti otomatis tiap 30 detik dan hitung mundur tampil.
- [ ] Given admin When memanggil endpoint ini Then `404`.

Edge cases:
- Screenshot QR hanya berguna maksimal 40 detik dan hanya sekali pakai.

### FR-22: Scan QR dan check-in oleh admin

Admin memindai QR di halaman web (kamera lewat `mobile_scanner`) atau menempelkan teks token sebagai cadangan. Server memvalidasi tanda tangan, gym, masa berlaku, sekali pakai, dan status member, lalu menampilkan nama dan foto member untuk verifikasi visual admin.

- [ ] Given tanda tangan diubah atau token acak Then `400 QR_INVALID`.
- [ ] Given member kedaluwarsa pada hari scan (menurut tanggal gym) Then `409 MEMBERSHIP_INACTIVE` dan tidak ada baris `check_ins`.
- [ ] Given member `expiresOn` = hari ini Then check-in diterima.
- [ ] Given member menekan "Hapus akun" setelah QR dibuat dan sebelum scan Then `404`.

Edge cases:

### FR-23: Riwayat check-in

- [ ] Given member When `GET /check-ins` Then `403`.

Edge cases:
- `from`/`to` memakai tanggal gym, bukan UTC (check-in 00:30 WIB masuk hari WIB itu).

### FR-24: Membuat kelas dan jadwal berulang

Admin membuat kelas satu kali atau seri mingguan. Sesi seri dibuat 28 hari ke depan saat seri dibuat, lalu dilengkapi tiap hari oleh job `classes.generate-sessions`. Waktu mulai dihitung dari `local_date` + `start_time` di zona gym.

Fitur: F-09

Acceptance criteria:
- [ ] Given admin When `POST /class-sessions` dengan `startsAt` di masa depan Then `201`, `bookedCount=0`, `remaining=capacity`, `localDate` dihitung dari zona gym.
- [ ] Given `startsAt` di masa lalu atau `capacity=0` Then `422`.
- [ ] Given `POST /class-series {weekday:2, startTime:"18:00", startOn:<Selasa>}` Then seri dan sesi tiap Selasa 28 hari ke depan dibuat dengan `startsAt` 18:00 waktu gym (UTC 11:00 untuk Jakarta).
- [ ] Given job `classes.generate-sessions` dijalankan dua kali Then tidak ada sesi ganda (unique `(series_id, local_date)`).
- [ ] Given `endOn` terisi Then tidak ada sesi setelah tanggal itu.
- [ ] Given seri dibatalkan Then job tidak membuat sesi baru untuknya.
- [ ] Given member When `POST /class-series` Then `403`.

Edge cases:
- `weekday` tidak bisa diubah setelah dibuat; admin membuat seri baru.
- Job yang terlewat beberapa hari akan menutup kekurangan saat berjalan lagi (horizon dari hari ini).

### FR-25: Mengubah dan membatalkan sesi atau seri

Admin mengubah atau membatalkan sesi tunggal maupun seri. Sesi seri hanya boleh digeser di `local_date` yang sama (RV2-03). Sesi satu kali bebas digeser dan `local_date` dihitung ulang.

Fitur: F-09

Acceptance criteria:
- [ ] Given sesi seri pada 2026-11-10 18:00 WIB When `PATCH startsAt` ke 2026-11-10 19:30 WIB Then `200`, `localDate` tetap 2026-11-10.
- [ ] Given sesi seri When `PATCH startsAt` ke tanggal gym lain Then `422 details.startsAt` dan tidak ada perubahan; generator tidak pernah membuat sesi ganda di tanggal asli.
- [ ] Given kelas satu kali When `PATCH startsAt` ke tanggal lain Then `200` dan `localDate` dihitung ulang.
- [ ] Given `capacity` baru lebih kecil dari `bookedCount` When PATCH Then `409 CONFLICT`.
- [ ] Given sesi di masa depan When `POST /cancel` Then status `cancelled` dan semua booking aktifnya `cancelled` dengan `cancelledBy=admin`, `booked_count=0`.
- [ ] Given sesi sudah mulai atau sudah dibatalkan When PATCH atau cancel Then `409 CONFLICT`.
- [ ] Given `PATCH /class-series/{id}` mengubah `startTime` Then semua sesi mendatang berstatus `scheduled` dihitung ulang di `local_date` masing-masing.
- [ ] Given `POST /class-series/{id}/cancel` Then semua sesi mendatangnya dibatalkan beserta booking-nya dan `cancelled_at` seri terisi.
- [ ] Given form edit sesi atau seri dibuka lewat URL langsung atau di-refresh Then data diisi lewat `GET /class-sessions/{id}` atau `GET /class-series/{id}` (RV2-05).

Edge cases:
- Edit seri menimpa edit manual pada sesi mendatang berstatus `scheduled` dari seri itu.
- Pengingat yang sudah terkirim tidak dikirim ulang bila waktu sesi digeser.

### FR-26: Member melihat jadwal kelas

Member melihat jadwal kelas dalam rentang tanggal beserta sisa kuota dan status booking miliknya. Admin melihat semua sesi termasuk yang dibatalkan.

Fitur: F-09

Acceptance criteria:
- [ ] Given sesi `scheduled` dan `cancelled` When member `GET /class-sessions?from&to` Then hanya yang `scheduled` dengan `remaining = capacity - bookedCount`.
- [ ] Given admin Then kedua status tampil.
- [ ] Given rentang lebih dari 31 hari Then `422 details.to`.
- [ ] Given member sudah booking Then `myBooking` berisi `{id, status}`.
- [ ] Given member When `GET /class-sessions/{id}` untuk sesi `cancelled` Then `404`; admin `200`.
- [ ] Given jadwal tampil Then dikelompokkan per hari menurut tanggal gym, dan jam tampil dalam zona gym.

Edge cases:
- Kuota yang tampil adalah data saat halaman dimuat; angka final tetap dicek server saat booking.

### FR-27: Halaman detail sesi dan daftar peserta (admin)

Admin membuka detail sesi yang menampilkan nama, instruktur, waktu, status, "N / kapasitas", dan daftar peserta. Halaman dapat di-deep-link dan di-refresh (RV2-05).

Fitur: F-10

Acceptance criteria:
- [ ] Given sesi dengan 3 booking aktif dan kapasitas 10 When admin membuka `/admin/classes/sessions/:id` Then tampil "3 / 10" dan tiga peserta dari `GET .../bookings`.
- [ ] Given halaman dimuat ulang di web Then data tetap terisi lewat `GET /class-sessions/{id}` tanpa menebak rentang tanggal.
- [ ] Given peserta membatalkan Then tidak ada di daftar default (`status=booked`); dengan `status=cancelled` muncul.
- [ ] Given member When `GET /class-sessions/{id}/bookings` Then `403`.
- [ ] Given `sessionId` tidak ada Then `FailureView` "tidak ditemukan".

Edge cases:
- Peserta yang sudah menghapus akun tampil sebagai "Anggota Terhapus" bila ia dahulu punya booking `booked` yang sudah selesai; booking mendatangnya sudah dibatalkan (FR-13).

### FR-28: Booking kelas

Member yang masih aktif memesan slot. Pengecekan kuota dan pembuatan booking terjadi dalam satu transaksi dengan update bersyarat pada `class_sessions`, sehingga tidak terjadi overbooking. Keaktifan dicek terhadap `local_date` sesi, yaitu `members.expires_on >= session.local_date`.

Fitur: F-10

Acceptance criteria:
- [ ] Given sesi kapasitas 1 dan 5 member aktif memesan bersamaan When semua `POST .../bookings` berjalan Then tepat satu `201` dan empat `409 CLASS_FULL`, `booked_count=1` (integration test konkuren).
- [ ] Given member `expiresOn=2026-11-10` When booking sesi 2026-11-10 Then `201`; sesi 2026-11-11 Then `409 MEMBERSHIP_INACTIVE`.
- [ ] Given member kedaluwarsa kemarin When booking sesi hari ini Then `409 MEMBERSHIP_INACTIVE`.
- [ ] Given member sudah punya booking aktif di sesi itu When booking lagi (juga bersamaan) Then `409 ALREADY_BOOKED` dan `booked_count` tidak bertambah dua kali.
- [ ] Given member membatalkan lalu booking ulang sebelum batas Then `201` dengan baris booking baru.
- [ ] Given sesi `cancelled` atau sudah mulai Then `409 SESSION_NOT_BOOKABLE`.
- [ ] Given admin When `POST .../bookings` Then `404` (bukan member).
- [ ] Given booking berhasil Then kartu sesi menampilkan "Sudah dipesan" dan sisa kuota berkurang saat dimuat ulang.

Edge cases:
- Kegagalan insert booking membatalkan kenaikan `booked_count` (satu transaksi).
- Booking tidak otomatis check-in.

### FR-29: Pembatalan booking

Member membatalkan booking paling lambat `cancelCutoffMinutes` (120 menit) sebelum kelas mulai. Admin dapat membatalkan kapan saja.

Fitur: F-10

Acceptance criteria:
- [ ] Given kelas mulai 18:00 dan sekarang 15:59 When member `POST /bookings/{id}/cancel` Then `200`, status `cancelled`, `cancelledBy=member`, `booked_count` berkurang satu.
- [ ] Given sekarang 16:00 (tepat 120 menit) Then `200`; sekarang 16:01 Then `409 CANCEL_WINDOW_CLOSED` dan booking tetap `booked`.
- [ ] Given admin Then `200` kapan pun sebelum sesi mulai, dengan `cancelledBy=admin`.
- [ ] Given dua pembatalan bersamaan untuk booking yang sama Then `booked_count` hanya berkurang satu, yang kedua `409 CONFLICT`.
- [ ] Given booking milik member lain When member membatalkan Then `404`.
- [ ] Given `cancelCutoffMinutes` diubah menjadi 60 Then batas baru dipakai pada pembatalan berikutnya.

Edge cases:
- Tidak ada sanksi untuk tidak datang.
- Pembatalan setelah kelas mulai tidak diizinkan untuk member.

### FR-33: Registrasi token perangkat

Aplikasi mobile meminta izin notifikasi setelah login, mendaftarkan token FCM ke API, memperbarui saat token berganti, dan menghapusnya saat logout. Fondasi untuk FR-34 dan FR-35 (RV-04).

- [ ] Given token milik user A didaftarkan oleh user B pada perangkat yang sama Then token berpindah ke B.
- [ ] Given logout When aplikasi memanggil `DELETE /me/device-tokens/{id}` Then baris terhapus.
- [ ] Given `PUSH_ENABLED=false` (dev) Then aplikasi tidak meminta izin dan tidak memanggil endpoint.
- [ ] Given `PushSender` mengembalikan `invalid-token` Then token itu dihapus oleh pengirim.

### FR-34: Pengingat masa aktif hampir habis

Job `notifications.expiry-reminders` (tiap 30 menit) mengirim push ke member yang tertaut dan punya token pada pukul 09:00 waktu gym atau setelahnya di hari `daysLeft = expiringSoonDays` (`expiry_soon`) dan `daysLeft = 1` (`expiry_tomorrow`). Pengiriman idempoten lewat `notification_deliveries`.

Teks contoh: "Masa aktif membership kamu berakhir 12 Nov 2026. Perpanjang sekarang di aplikasi."

Fitur: F-12

Acceptance criteria:
- [ ] Given member `daysLeft=7`, punya token, dan waktu gym 09:30 When job berjalan Then satu push terkirim dan satu baris `notification_deliveries` `sent` dengan kunci `<memberId>:<expiresOn>`.
- [ ] Given job berjalan lagi 30 menit kemudian Then tidak ada push kedua (unique `(kind, dedupe_key)`).
- [ ] Given job berjalan dua kali bersamaan Then tepat satu push.
- [ ] Given waktu gym 08:30 Then tidak ada push.
- [ ] Given member memperpanjang sebelum job berjalan (`daysLeft` tidak lagi 7) Then tidak ada push.
- [ ] Given member belum punya token Then tidak ada baris `notification_deliveries` dan akan dicoba lagi pada run berikutnya.
- [ ] Given member punya dua perangkat Then keduanya menerima push dalam satu baris pengiriman.
- [ ] Given `PushSender` melempar error Then baris `failed`, API tidak terpengaruh, dan tidak dicoba ulang.
- [ ] Given pengguna mengetuk notifikasi Then aplikasi membuka halaman perpanjangan.

Edge cases:
- Pengiriman bersifat paling banyak sekali. Kegagalan sementara tidak dicoba ulang.
- Member yang sudah `expired` tidak menerima pengingat ini.

### FR-35: Pengingat jadwal kelas

Job `notifications.class-reminders` (tiap 5 menit) mengirim push ke member yang punya booking `booked` pada sesi `scheduled` yang mulai dalam 60 menit ke depan (R-03). Pengiriman idempoten per booking.

- [ ] Given booking pada sesi mulai dalam 55 menit When job berjalan Then satu push dan satu baris `class_reminder` dengan kunci `<bookingId>`.
- [ ] Given job berjalan lagi atau bersamaan Then tidak ada push kedua.
- [ ] Given booking dibatalkan sebelum job berjalan Then tidak ada push.
- [ ] Given sesi dibatalkan admin Then tidak ada push.
- [ ] Given sesi mulai dalam 90 menit Then belum ada push.
- [ ] Given member tanpa token Then tidak ada baris pengiriman dan dicoba lagi pada run berikutnya selama sesi belum mulai.
- [ ] Given sesi sudah mulai Then tidak ada push.

Edge cases:
- Booking yang dibuat kurang dari 60 menit sebelum kelas tetap menerima pengingat pada run berikutnya.
- Sesi yang digeser setelah pengingat terkirim tidak memicu pengingat kedua.

## 7. Non-Functional Requirements

- **NFR-01 Performa baca:** untuk satu gym dengan 5.000 member dan 50 pengguna bersamaan, p95 endpoint daftar dan detail kurang dari 300 ms (API di container dengan satu vCPU, diukur lewat skrip beban pada database uji). Index di Bagian 4 dipakai (diperiksa dengan `EXPLAIN` pada query paginasi member dan pembayaran).
- **NFR-02 Konkurensi booking:** 50 permintaan booking bersamaan pada sesi dengan 1 slot sisa menghasilkan tepat 1 booking; `booked_count` tidak pernah melebihi `capacity` (CHECK dan integration test). Pembatalan dan booking bersamaan tetap menjaga `booked_count` sama dengan jumlah booking `booked`.
- **NFR-03 Keamanan akses:** setiap route `/v1/*` menolak request tanpa token valid (`401`). Hanya `/health` dan `POST /webhooks/midtrans` publik, dijaga `all-routes-require-auth.int.test.ts`. Setiap endpoint gym punya test integrasi untuk: bukan anggota → `404`, peran kurang → `403`, member lain → `404`.
- **NFR-04 Privasi log:** log tidak pernah memuat token ID, token QR, kode undangan, `signature_key`, server key Midtrans, atau token FCM. Field `code`, `qrToken`, `signature_key`, `serverKey`, dan `token` ditambahkan ke `SENSITIVE_KEYS` (diredaksi sampai kedalaman 4), beserta test-nya. Nomor HP dan email tetap diredaksi.
- **NFR-05 Penyimpanan file:** `storage.rules` menolak 100% akses client; foto hanya diakses lewat signed URL berumur ≤ 5 menit dan upload ≤ 2 MB. Test integrasi dengan Storage Emulator memeriksa file tersimpan dan terhapus.
- **NFR-06 Idempoten:** 10 webhook duplikat untuk satu pembayaran, atau rekonsiliasi bersamaan dengan webhook, memperpanjang masa aktif tepat sekali. Job pengingat yang dijalankan dua kali (atau bersamaan) menghasilkan paling banyak satu push per `(kind, dedupe_key)`. Generator sesi yang dijalankan dua kali tidak menambah baris.
- **NFR-07 Ketepatan waktu dan tanggal:** semua perhitungan hari, status, perpanjangan, dan filter tanggal memakai zona gym lewat satu modul waktu bersama. Ada unit test untuk batas 23:59/00:00, tahun kabisat, penjumlahan bulan di akhir bulan, dan dua zona waktu berbeda. Timestamp yang ditulis server memakai `now()` database.
- **NFR-08 Ketahanan integrasi luar:** webhook Midtrans dijawab dalam kurang dari 3 detik pada kondisi normal. Kegagalan FCM atau Storage tidak menggagalkan request lain dan tidak menjatuhkan job. Pembayaran yang webhook-nya hilang terselesaikan oleh rekonsiliasi paling lambat 10 menit setelah lunas. Gagal ke gateway saat membuat transaksi memberi `502` tanpa data setengah jadi.
- **NFR-09 Integritas admin:** gym tidak pernah tanpa admin. Test integrasi konkuren (cabut-silang, hapus-akun dua admin terakhir) selalu menyisakan minimal satu admin, dan 100 kali pengulangan test tidak pernah menghasilkan nol admin (RV2-02).
- **NFR-10 Penghapusan akun:** selesai dalam satu request kurang dari 2 detik. Setelah itu tidak ada kolom data pribadi (nama asli, telepon, email, foto, `user_id`) tersisa pada member yang dianonimkan, sementara baris `payments` tidak berkurang (dicek di test integrasi).
- **NFR-11 Kualitas dan kontrak:** `pnpm check` hijau (Biome, typecheck, unit, integration, `contract:check`, `flutter analyze`, `flutter test`). Setiap use case punya unit test dengan repository palsu. Setiap kode error baru terpetakan di `failureCodeOf` (analyzer gagal bila ada yang terlewat). Tidak ada perubahan route tanpa `pnpm contract:generate`.
- **NFR-12 Pembatasan percobaan:** redeem undangan dibatasi 5 kegagalan per user per 15 menit (`429`), dan kode berentropi 60 bit. Kode undangan tidak bisa ditebak dengan lebih dari 5 percobaan per 15 menit per akun.
- **NFR-13 Bahasa dan format:** 100% teks UI Bahasa Indonesia. Nominal tampil "Rp 350.000", tanggal memakai locale `id` dan zona gym. Teks kegagalan hanya dari `failure_messages.dart`.
- **NFR-14 Deploy dan operasional:** `/health` menjawab 200 untuk healthcheck container. Migrasi berjalan sebagai perintah terpisah sebelum server. `SIGTERM` menunggu request dan job berjalan selesai (shutdown bertahap). Server menolak start bila `NODE_ENV=production` dengan adapter `fake`, host emulator, atau `QR_SIGNING_SECRET` kurang dari 32 karakter.
- **NFR-15 Platform:** build web (Chrome), Android (debug), dan iOS (simulator, diverifikasi lewat job CI macOS atau Mac sebelum rilis; dicatat di `docs/conventions.md`) berhasil. Halaman admin (termasuk scan QR) diuji pada web; aplikasi member diuji pada Android dan web.
