# Aplikasi Membership Gym

## 1. Context & Goal

Satu gym saat ini mencatat member dan masa aktif secara manual dan berantakan. Produk ini merapikan pengelolaan member di satu aplikasi Flutter (web, Android, iOS) dengan backend API terpisah. Admin dan member sama-sama memakainya.

- **Admin** (dipakai lewat web) mengelola paket, member, pembayaran, check-in lewat scan QR, dan jadwal kelas.
- **Member** (dipakai lewat HP atau web) melihat status masa aktif, membayar perpanjangan secara online, menampilkan QR check-in, memesan kelas, dan menerima pengingat.
- **Aksi pertama admin:** menambahkan member baru beserta paketnya.
- **Tujuan MVP:** status masa aktif selalu benar dan konsisten, perpanjangan pasti, check-in aman, dan booking kelas tidak pernah overbooking.

Aturan bisnis default yang berlaku di seluruh PRD (RV-07, RV-09, RV2-04). Nilai ambang disimpan sebagai pengaturan gym.

| Aturan | Nilai |
| --- | --- |
| Hari ini | Tanggal lokal di zona waktu gym (`gyms.timezone`) |
| `expires_on` | Hari terakhir aktif (inklusif); member aktif sampai akhir hari itu |
| Status | `expired` bila `expires_on < hari ini`; `expiring_soon` bila sisa hari 0 sampai `expiringSoonDays` (default 7); selain itu `active` |
| Masa tenggang | Tidak ada. Status `expired` langsung ditolak untuk check-in dan booking |
| Perpanjangan | Mulai `expires_on + 1 hari` bila `expires_on >= hari bayar`; bila sudah lewat, mulai dari tanggal bayar. Akhir periode = mulai + durasi − 1 hari |
| `startOn` member baru | Hari ini sampai 30 hari ke belakang. Tidak boleh di masa depan |
| Batas batal booking | Paling lambat 120 menit sebelum kelas mulai (`cancelCutoffMinutes`) |
| Pergantian QR | Tiap 30 detik (`qrRotationSeconds`) |
| Masa berlaku pembayaran online | 60 menit |
| Pengingat | Masa aktif: saat sisa hari = `expiringSoonDays` dan saat sisa 1 hari. Kelas: 60 menit sebelum mulai (`classReminderMinutes`) |

Batasan versi pertama: satu member punya satu paket aktif, semua paket boleh ikut semua kelas, booking tidak otomatis menjadi check-in, tidak ada sanksi tidak hadir, dan satu member hanya bisa check-in satu kali per hari lokal.

## 2. Scope

### In scope

Urutan fase mengikuti dependensi (RV-01, RV-03).

- **Fase 0, fondasi**
  - F-01 Akun dan login: login/logout, pembuatan user otomatis tanpa peran, halaman profil. Penautan akun ke member **tidak** termasuk di sini (RV-03).
  - F-02 Pengelolaan gym dan peran: profil dan pengaturan gym, peran admin/member, pembatasan akses, pembuatan admin pertama lewat CLI (RV-06), pencabutan admin dengan penjagaan race condition (RV2-02).
- **Fase 1, member dan paket**
  - F-03 Paket membership.
  - F-04 Data member: tambah/ubah/daftar/detail member, foto lewat signed URL (RV-05), **undangan sekali pakai dan penautan akun** untuk member dan admin tambahan (RV-02, RV-03), hapus akun dari halaman profil (RV-10).
  - F-05 Status masa aktif dan tanggal kedaluwarsa.
- **Fase 2, pembayaran dan perpanjangan**
  - F-06 Pencatatan pembayaran manual dan perpanjangan.
  - R-06 Ekspor laporan member dan pembayaran (CSV), setelah F-06.
  - F-07 Pembayaran online lewat Midtrans di balik interface `PaymentGateway` (RV-08), termasuk status `needs_review` (RV2-06).
  - R-01 Pengingat masa aktif hampir habis (push FCM, token perangkat, job pg-boss). Dikerjakan setelah F-05 dan F-07 (RV-04).
- **Fase 3, check-in QR**
  - F-08 Check-in kehadiran dengan QR dinamis.
- **Fase 4, kelas dan booking**
  - F-09 Jadwal kelas (satu kali dan berulang mingguan).
  - F-10 Booking kelas atomik.
- **Fase 5, notifikasi kelas**
  - R-03 Pengingat jadwal kelas, memakai infrastruktur notifikasi dari R-01, setelah F-10.

### Non-goals

- Banyak gym atau cabang. Skema sudah memakai `gym_id`, tetapi fiturnya belum dibuat.
- Mode offline. Check-in, booking, dan pembayaran selalu butuh koneksi.
- Pembaruan data realtime. Data diambil saat halaman dibuka atau di-refresh.
- Instruktur atau personal trainer sebagai pengguna dengan login sendiri.
- Penjualan produk atau kasir.
- Absensi dan penggajian staf.
- Check-in mandiri lewat perangkat atau kios tanpa admin.
- Refund otomatis lewat payment gateway.
- Dashboard ringkasan admin, daftar tunggu kelas, cuti/bekukan membership, kode promo dan diskon.
- Impor data member lama dari spreadsheet.
- Lebih dari satu paket aktif per member, batas jumlah kelas per paket, dan sanksi tidak hadir.
- Booking yang otomatis dihitung sebagai check-in.
- Pembatalan atau koreksi pembayaran yang sudah lunas.
- Push notification untuk web. Pengingat hanya untuk Android dan iOS.
- Antarmuka admin di aplikasi mobile. Admin memakai web.
- Verifikasi email oleh aplikasi dan penautan otomatis lewat email atau nomor HP (RV-02).

## 3. Tech Constraints

- Monorepo pnpm: `apps/app` (Flutter web/Android/iOS), `apps/api` (Hono + TypeScript, Zod OpenAPI), `packages/contract` (OpenAPI + client Dart hasil generate).
- PostgreSQL + Drizzle + drizzle-kit. Lokal lewat Docker Compose.
- Firebase Auth di client; API memverifikasi ID token. Peran disimpan di PostgreSQL. Firebase Auth Emulator dipakai lokal.
- Cloud Storage for Firebase lewat port `FileStorage`. FCM lewat port `PushSender`. Job terjadwal lewat pg-boss di container API (`RUN_WORKER=true`).
- Deploy: API sebagai container yang selalu hidup, Flutter web di hosting statis, mobile lewat store.
- Testing: Vitest (API), flutter_test + bloc_test + mocktail (app).

Detail konvensi ada di `docs/conventions.md`. Bagian yang berlaku: Struktur repo, Job (pg-boss), Autentikasi, Port push dan storage, Pagination, Database, Format error, Clean Architecture API, dan Organisasi dan tenancy. Keputusan khusus produk ini:

- **Tenancy (konvensi: Organisasi dan tenancy).** Gym berperan sebagai organisasi. Tabelnya `gyms` dan `gym_users` (peran `admin`/`member`), dan path-nya `/v1/gyms/{gymId}/...`. Fitur contoh `notes` dihapus. User tanpa baris `gym_users` mendapat `404` pada path gym mana pun.
- **Peran default dan admin pertama (RV-06).** User baru dibuat tanpa peran. Admin pertama dibuat lewat skrip CLI (FR-03). Tidak ada endpoint publik yang menaikkan peran.
- **Kode error tambahan.** Ditambahkan ke `error-codes.ts`, lalu `pnpm contract:generate`, lalu dipetakan di `failureCodeOf` dan `failure_messages.dart`:

| Kode | HTTP | Kapan |
| --- | --- | --- |
| `MEMBERSHIP_INACTIVE` | 409 | Check-in atau booking oleh member kedaluwarsa |
| `CLASS_FULL` | 409 | Kuota sesi penuh |
| `SESSION_NOT_BOOKABLE` | 409 | Sesi dibatalkan atau sudah mulai |
| `CANCEL_WINDOW_CLOSED` | 409 | Lewat batas pembatalan booking |
| `LAST_ADMIN` | 409 | Aksi membuat gym tanpa admin |
| `INVITATION_INVALID` | 409 | Kode undangan salah, kedaluwarsa, terpakai, atau dicabut |
| `QR_INVALID` | 409 | QR salah tanda tangan, kedaluwarsa, atau sudah dipakai |
| `PLAN_INACTIVE` | 409 | Paket nonaktif dipakai untuk pembayaran atau member baru |
| `RATE_LIMITED` | 429 | Terlalu banyak percobaan kode undangan |
| `PAYMENT_GATEWAY_ERROR` | 502 | Payment gateway gagal merespons |

- **Pembayaran (RV-08).** Gateway: **Midtrans Snap**. Metode: **QRIS dan Virtual Account (BCA, BNI, BRI, Mandiri)**. Masa berlaku transaksi 60 menit. Dibungkus port `PaymentGateway` di `core/ports/` dengan adapter `none`, `fake`, `midtrans`, dan env `PAYMENT_ADAPTER`, mengikuti pola layanan luar baru di konvensi. Port punya `createTransaction`, `verifyNotification(rawBody)`, dan `getStatus(orderId)`. Hasilnya dinormalisasi ke `paid|pending|failed|expired`. Env: `MIDTRANS_SERVER_KEY`, `MIDTRANS_ENV`. Sandbox Midtrans dipakai untuk uji end-to-end.
- **Notifikasi (RV-04).** `PUSH_ADAPTER=fcm` di produksi. Butuh tabel `device_tokens`, kunci APNs di-upload ke Firebase untuk iOS, dan job pg-boss yang idempoten (lihat FR-31 dan FR-40).
- **Foto (RV-05).** `storage.rules` menolak semua baca/tulis dari client. Upload dan baca lewat API: `FileStorage.save` untuk upload, dan metode baru `createReadUrl(path, { expiresInSeconds })` di port `FileStorage` untuk signed URL berumur **300 detik**. Adapter `fake` mengembalikan URL palsu. Adapter `firebase-storage` butuh izin penandatanganan pada service account runtime.
- **Job (konvensi: Job pg-boss):**
  - `payments.reconcile` (`*/10 * * * *`)
  - `classes.generate-sessions` (`0 20 * * *`)
  - `notifications.membership-expiry` (`0 * * * *`)
  - `notifications.class-reminder` (`*/5 * * * *`)
- **Waktu.** Semua perhitungan "hari ini", `local_date`, dan batas hari memakai zona waktu gym lewat satu helper domain (`gymLocalDate(instant, tz)`).
- **Penyimpangan konvensi yang disengaja:**
  - `GET .../class-sessions` mengembalikan `{ items }` tanpa cursor, diurutkan `starts_at ASC`, dengan rentang maksimal 31 hari.
  - Webhook `POST /webhooks/midtrans` berada di luar `/v1`, didaftarkan di `PUBLIC_ROUTES`, dan diamankan dengan verifikasi signature.
  - Endpoint ekspor mengembalikan `text/csv`.
- **Rate limit kode undangan.** Disimpan in-memory di proses API, karena hanya ada satu container.

Constraint dan aturan integritas (nama mengikuti konvensi `<tabel>_<kolom>_<jenis>`):

- **Umum.** Semua timestamp `timestamptz(3)` lewat helper. Kolom `date` memakai `mode: 'string'`. Semua FK `gym_id` ke `gyms` memakai `ON DELETE CASCADE`. FK `user_id` ke `users` pada `gym_users`, `device_tokens`, dan `notification_logs` memakai `CASCADE`. FK aktor (`created_by_user_id`, `used_by_user_id`, `recorded_by_user_id`) memakai `SET NULL`. FK `member_id` dan `plan_id` pada `payments`, `check_ins`, `bookings`, dan `members.plan_id` memakai `RESTRICT` (paket tidak pernah dihapus, hanya dinonaktifkan).
- **`users`.** `users_firebase_uid_unique`, `users_email_lowercase_check`. Tanpa `gym_id`.
- **`gyms`.** CHECK `expiring_soon_days` 1–60, `cancel_cutoff_minutes` 0–1440, `qr_rotation_seconds` 10–120, `class_reminder_minutes` 15–720. `timezone` divalidasi sebagai nama IANA di Zod.
- **`gym_users`.** `gym_users_gym_id_user_id_unique`, `gym_users_role_check` (`admin`,`member`), index `user_id`. User tanpa baris = tanpa peran.
- **`plans`.** `plans_gym_id_name_unique` pada `(gym_id, lower(name))`. `plans_duration_check` (`duration_value` 1–120 dan `duration_unit` in `day,week,month,year`). `plans_price_amount_check` (`> 0`, rupiah bulat). `plans_name_length_check` (1–100).
- **`members`.**
  - `members_gym_id_phone_unique` (unik bila `phone` tidak null).
  - `members_user_id_unique`: satu akun hanya tertaut ke satu member.
  - `members_anonymized_check`: `phone IS NOT NULL OR anonymized_at IS NOT NULL`.
  - Index `(gym_id, expires_on)` dan index pagination `(gym_id, created_at DESC, id DESC)`.
  - FK `user_id` memakai `SET NULL`.
- **`invitations`.**
  - `invitations_code_hash_unique`: kode disimpan sebagai SHA-256, kode asli hanya ditampilkan sekali.
  - `invitations_kind_check` (`member`,`admin`).
  - `invitations_kind_member_check`: `kind='member'` wajib `member_id`, `kind='admin'` wajib `member_id` null.
  - Index `member_id`.
  - Umur kode 48 jam (`expires_at`).
- **`payments`.**
  - `payments_method_check` (`cash`,`transfer`,`online`).
  - `payments_status_check` (`pending`,`paid`,`failed`,`expired`,`needs_review`).
  - `payments_amount_check` (`> 0`).
  - `payments_plan_duration_check`: aturan yang sama dengan `plans_duration_check` (RV2-01). Kolom `plan_duration_value`/`plan_duration_unit` NOT NULL dan diisi saat pembayaran dibuat.
  - `payments_gateway_order_id_unique` (NULL boleh banyak).
  - `payments_member_id_pending_online_unique`: unik parsial `(member_id)` where `method='online' AND status='pending'`.
  - `payments_paid_check`: `status <> 'paid'` atau (`paid_at`, `period_start`, `period_end` semuanya terisi).
  - Index pagination `(gym_id, created_at DESC, id DESC)` dan `(member_id, created_at DESC, id DESC)`, serta index `(status, expires_at)` untuk rekonsiliasi.
- **`check_ins`.** `check_ins_member_id_local_date_unique`, `check_ins_qr_jti_unique` (QR sekali pakai). Index pagination per gym dan per member.
- **`class_series`.** CHECK `weekday` 1–7 (ISO, 1 = Senin), `capacity` 1–200, `duration_minutes` 15–300, `ends_on >= starts_on`.
- **`class_sessions`.**
  - `class_sessions_series_id_local_date_unique`: generator idempoten, NULL `series_id` boleh banyak.
  - `class_sessions_booked_count_check`: `0 <= booked_count <= capacity`.
  - CHECK `status` (`scheduled`,`cancelled`), `capacity` 1–200, `duration_minutes` 15–300.
  - Index `(gym_id, local_date, starts_at)`.
  - `local_date` selalu dihitung dari `starts_at` dengan zona gym.
- **`bookings`.**
  - `bookings_session_id_member_id_booked_unique`: unik parsial where `status='booked'`.
  - CHECK `status` (`booked`,`cancelled`), `cancel_source` (`member`,`admin`,`session_cancelled`,`account_deleted`).
  - Index pagination `(member_id, created_at DESC, id DESC)` dan index `session_id`.
- **`device_tokens`.** `device_tokens_token_unique` (token yang dipakai akun lain dipindahkan ke akun yang mendaftar), `device_tokens_platform_check` (`android`,`ios`), index `user_id`.
- **`notification_logs`.** `notification_logs_user_id_kind_dedupe_key_unique`, `notification_logs_kind_check` (`membership_expiry`,`class_reminder`).
- **Perhitungan.** Fungsi murni di domain: `computeMemberStatus(expiresOn, today, expiringSoonDays)`, `addDuration(date, value, unit)` (bulan dan tahun dijepit ke akhir bulan), dan `computeRenewalPeriod(expiresOn, paidLocalDate, durationValue, durationUnit)`. Durasi perpanjangan **selalu** dibaca dari snapshot `payments.plan_duration_*`, bukan dari `plans` (RV2-01).

## 5. API Contract

**Aturan umum.**
- Semua route di bawah `/v1` (konvensi: Autentikasi). Format error mengikuti konvensi bagian Format error, ditambah kode error di bagian 3.
- Setiap `/v1/gyms/{gymId}/*` mengembalikan `401` tanpa token valid, `422` bila `gymId` bukan UUID atau validasi gagal, dan `404` bila user bukan anggota gym. Peran yang tidak cukup menghasilkan `403` dari use case. Hal ini tidak diulang di tiap endpoint.
- Daftar berpaginasi memakai `?limit&cursor` dan respons `{ items, nextCursor }`. Nama skema: `PlanPage`, `MemberPage`, `PaymentPage`, `CheckInPage`, `BookingPage`, `ClassSeriesPage`.
- Tanggal `date` berformat `YYYY-MM-DD`. Timestamp berformat ISO-8601 UTC.
- **Skema bersama:**
  - `Gym` `{ id, name, address, timezone, expiringSoonDays, cancelCutoffMinutes, qrRotationSeconds, classReminderMinutes }`
  - `Plan` `{ id, name, durationValue, durationUnit, priceAmount, isActive }`
  - `Member` `{ id, fullName, phone, email, hasPhoto, planId, planName, startOn, expiresOn, status, daysLeft, linked, createdAt, updatedAt }`. `status` ∈ `active|expiring_soon|expired`. `daysLeft` negatif bila lewat. Anggota anonim memakai `fullName: "Member Terhapus"` dan `phone: null`.
  - `Payment` `{ id, memberId, memberName, planId, planName, planDurationValue, planDurationUnit, amount, method, status, paymentUrl, expiresAt, paidAt, periodStart, periodEnd, note, createdAt }`. `paymentUrl` hanya terisi saat `pending`.
  - `CheckIn` `{ id, memberId, memberName, localDate, checkedInAt }`
  - `ClassSession` `{ id, seriesId, name, instructorName, startsAt, localDate, durationMinutes, capacity, bookedCount, remainingSlots, status, myBookingId }`. `myBookingId` hanya untuk member, null bagi admin.
  - `ClassSeries` `{ id, name, instructorName, weekday, startTime, durationMinutes, capacity, startsOn, endsOn, cancelledAt }`
  - `Booking` `{ id, sessionId, sessionName, sessionStartsAt, memberId, memberName, status, cancelSource, cancelledAt, createdAt }`

### GET /v1/me
- Akses: user terautentikasi (peran apa pun atau tanpa peran).
- Response `200` `{ user: { id, email, displayName }, gyms: [{ gymId, gymName, role, memberId|null }] }`. `gyms` kosong berarti belum punya peran.

### DELETE /v1/me
- Akses: user terautentikasi. Menghapus akun sesuai FR-13.
- Response `204`.
- Error: `409 LAST_ADMIN`.

### POST /v1/invitations/redeem
- Akses: user terautentikasi, boleh tanpa peran.
- Request `{ code }` (trim, 8–32 karakter).
- Response `200` `{ gymId, role, memberId|null }`.
- Error: `409 INVITATION_INVALID`; `409 CONFLICT` (user sudah punya peran di gym itu, atau member sudah tertaut); `429 RATE_LIMITED`.

### POST /v1/me/device-tokens
- Akses: user terautentikasi.
- Request `{ token, platform }` (`android|ios`). Upsert, memperbarui `last_seen_at`.
- Response `204`. Error: `422`.

### POST /v1/me/device-tokens/unregister
- Akses: user terautentikasi. Request `{ token }`.
- Response `204` (idempoten, tidak error bila token tidak ada).

### GET /v1/gyms/{gymId}
- Akses: admin, member.
- Response `200` `Gym`.

### PATCH /v1/gyms/{gymId}
- Akses: admin.
- Request: semua opsional, minimal satu (`name`, `address`, `timezone`, `expiringSoonDays`, `cancelCutoffMinutes`, `qrRotationSeconds`, `classReminderMinutes`).
- Response `200` `Gym`.
- Error: `422` (termasuk `details._root` bila body kosong dan `details.timezone` bila bukan zona IANA).

### GET /v1/gyms/{gymId}/admins
- Akses: admin.
- Response `200` `{ items: [{ userId, email, displayName, createdAt }] }`.

### DELETE /v1/gyms/{gymId}/admins/{userId}
- Akses: admin. Mencabut peran admin user lain atau diri sendiri.
- Response `204`.
- Error: `404` (user itu bukan admin gym ini), `409 LAST_ADMIN`.

### POST /v1/gyms/{gymId}/admin-invitations
- Akses: admin.
- Request: tanpa body.
- Response `201` `{ id, code, expiresAt }`. `code` hanya muncul di respons ini.

### GET /v1/gyms/{gymId}/plans
- Akses: admin (semua paket), member (hanya `isActive=true`).

## 6. Functional Requirements

### FR-01: Login dan logout
Admin dan member masuk dengan akun Firebase (email dan kata sandi). Aplikasi menyimpan sesi Firebase dan mengirim ID token di setiap request. Setelah login, aplikasi memanggil `GET /v1/me` untuk menentukan layar awal: admin ke area admin (web), member ke beranda member, user tanpa peran ke layar "Masukkan kode undangan".

Fitur: F-01

Acceptance criteria:
- [ ] Given pengguna belum login, When membuka rute mana pun selain login, Then go_router mengarahkan ke halaman login.
- [ ] Given kredensial benar, When login, Then aplikasi memanggil `GET /v1/me` dan membuka layar sesuai peran.
- [ ] Given pengguna login, When menekan Logout, Then sesi Firebase dihapus dan aplikasi kembali ke halaman login.
- [ ] Given token tidak ada atau kedaluwarsa, When memanggil `/v1/*`, Then respons `401` dan client kembali ke login.

Edge cases:
- Token kedaluwarsa saat aplikasi terbuka: client me-refresh token sekali, lalu logout bila tetap `401`.
- Admin membuka aplikasi mobile: layar menyatakan area admin tersedia di web.

### FR-02: Pembuatan user otomatis tanpa peran
Pada request terautentikasi pertama, API membuat baris `users` dari `firebase_uid` (konvensi: Autentikasi, `syncUser`). User baru **tidak** mendapat peran apa pun (RV-06).

Fitur: F-01

Acceptance criteria:
- [ ] Given `firebase_uid` baru, When `GET /v1/me` dipanggil, Then baris `users` terbuat dan `gyms` di respons kosong.
- [ ] Given user yang sama memanggil dua kali, When request kedua tiba, Then tidak ada baris ganda dan `last_seen_at` diperbarui.
- [ ] Given user tanpa peran, When memanggil `/v1/gyms/{gymId}/plans`, Then `404`.
- [ ] Given email di token berubah huruf besar-kecil, When disinkronkan, Then email tersimpan lowercase.

Edge cases:
- Dua request pertama bersamaan: `ON CONFLICT (firebase_uid)` mencegah duplikasi.
- Tidak ada jalur API yang memberi peran tanpa kode undangan atau CLI.

### FR-03: Pembuatan admin pertama lewat CLI
Skrip `pnpm --filter api admin:bootstrap --email <email> [--gym-name <nama> --timezone <zona>]` dijalankan sekali saat deploy. Skrip membuat baris gym bila belum ada (nama dan zona wajib saat gym dibuat). Skrip juga memberi peran `admin` pada user dengan email itu (RV-06). User harus sudah pernah login satu kali agar baris `users`-nya ada.

Fitur: F-02

Acceptance criteria:
- [ ] Given belum ada gym, When skrip dijalankan dengan `--gym-name` dan `--timezone`, Then satu baris `gyms` dengan nilai default pengaturan terbuat.
- [ ] Given user dengan email itu sudah ada, When skrip dijalankan, Then terbuat baris `gym_users` role `admin`.
- [ ] Given skrip dijalankan dua kali dengan argumen sama, When kali kedua jalan, Then tidak ada baris ganda dan exit code 0.
- [ ] Given email tidak ada di `users`, When skrip dijalankan, Then exit code 1 dengan pesan yang meminta user login dahulu.
- [ ] Given `--timezone` bukan zona IANA, When skrip dijalankan, Then exit code 1 tanpa mengubah data.

Edge cases:
- Gym sudah ada dan `--gym-name` diberikan: diabaikan dengan peringatan.
- Skrip hanya butuh `DATABASE_URL`.

### FR-04: Halaman profil
Halaman profil menampilkan nama, email, peran, dan (untuk member) member terkait. Ada tombol Logout dan tombol "Hapus akun" (FR-13).

Fitur: F-01

Acceptance criteria:
- [ ] Given user login, When membuka profil, Then nama, email, dan peran dari `GET /v1/me` tampil.
- [ ] Given user tanpa peran, When membuka profil, Then email tampil, peran bertuliskan "Belum terhubung ke gym", dan tombol "Masukkan kode undangan" tersedia.

Edge cases:
- Nama kosong di token: tampilkan email.

### FR-05: Profil dan pengaturan gym
Admin melihat dan mengubah data gym: nama, alamat, zona waktu, ambang hampir habis, batas batal booking, interval QR, dan menit pengingat kelas. Semua member bisa membaca profil gym.

Fitur: F-02

Acceptance criteria:
- [ ] Given admin, When `PATCH` dengan `expiringSoonDays: 14`, Then respons `200` dan status member dihitung dengan ambang 14 hari sejak saat itu.
- [ ] Given member, When `PATCH /gyms/{gymId}`, Then `403`.
- [ ] Given `timezone: "Asia/Nowhere"`, When `PATCH`, Then `422` dengan `details.timezone`.
- [ ] Given body kosong, When `PATCH`, Then `422` dengan `details._root`.

Edge cases:
- Mengubah zona waktu tidak mengubah `expires_on` yang tersimpan, tetapi status dihitung ulang memakai zona baru.

### FR-06: Peran dan pembatasan akses
Hak akses ditentukan baris `gym_users`. Middleware keanggotaan di `/v1/gyms/:gymId/*` menaruh `c.var.membership`. Pemeriksaan peran ada di use case (konvensi: Organisasi dan tenancy).

Fitur: F-02

Acceptance criteria:
- [ ] Given user bukan anggota gym, When memanggil endpoint gym mana pun, Then `404`.
- [ ] Given member, When memanggil endpoint khusus admin (misalnya `GET /members`), Then `403`.
- [ ] Given member A, When `GET /members/{idMemberB}`, Then `404`.
- [ ] Given `gymId` bukan UUID, When dipanggil, Then `422` dengan `details.gymId`.
- [ ] Given route baru ditambahkan, When `all-routes-require-auth.int.test.ts` dijalankan, Then semua route `/v1` menolak request tanpa token dan hanya `/webhooks/midtrans` di `PUBLIC_ROUTES`.

Edge cases:
- Integration test minimal: bukan anggota `404`, peran kurang `403`, member tidak melihat data member lain.

### FR-07: Cabut admin dan penjagaan "gym selalu punya admin"
Admin dapat mencabut peran admin lain atau dirinya sendiri. Gym tidak boleh kehabisan admin. Transaksi mengunci baris gym (`SELECT ... FROM gyms WHERE id=$1 FOR UPDATE`) sebelum menghitung jumlah admin, sehingga pencabutan bersamaan tidak lolos bersama-sama (RV2-02).

Fitur: F-02

Acceptance criteria:
- [ ] Given dua admin A dan B, When A mencabut B, Then `204` dan B kehilangan akses admin.
- [ ] Given admin tunggal, When mencabut dirinya, Then `409 LAST_ADMIN` dan peran tetap.
- [ ] Given dua admin A dan B, When A mencabut B dan B mencabut A secara bersamaan, Then tepat satu request `204`, yang lain `409 LAST_ADMIN`, dan gym tetap punya satu admin (integration test).
- [ ] Given dua admin, When keduanya menghapus akun (FR-13) bersamaan, Then tepat satu berhasil.
- [ ] Given `userId` bukan admin gym, When dicabut, Then `404`.

Edge cases:
- Kunci baris gym juga dipakai oleh penghapusan akun admin (FR-13).
- User yang dicabut tetap ada sebagai user tanpa peran.

### FR-08: Kelola paket membership
Admin menambah, mengubah, dan menonaktifkan paket (nama, durasi, harga). Paket aktif muncul sebagai pilihan saat mendaftarkan member, mencatat pembayaran, atau membayar online. Paket tidak dihapus.

Fitur: F-03

Acceptance criteria:
- [ ] Given admin, When `POST /plans` dengan nama, durasi, dan harga valid, Then `201` dan paket muncul di daftar.
- [ ] Given paket "Bulanan" ada, When menambah "bulanan", Then `409 CONFLICT`.
- [ ] Given `durationValue: 0` atau `priceAmount: 0`, When `POST`, Then `422` dengan `details.durationValue` atau `details.priceAmount`.
- [ ] Given paket dinonaktifkan, When member melihat daftar paket, Then paket itu tidak tampil dan admin tetap melihatnya.
- [ ] Given paket nonaktif, When dipakai membuat member atau pembayaran, Then `409 PLAN_INACTIVE`.

Edge cases:
- Mengubah durasi atau harga paket tidak mengubah pembayaran lama (snapshot) dan tidak mengubah `expires_on` member.
- Paket yang sudah dipakai tidak bisa dihapus (tidak ada endpoint hapus).

### FR-09: Tambah member baru beserta paket
Aksi pertama admin. Admin mengisi nama, nomor HP, email (opsional), paket, dan `startOn`. `expires_on` dihitung: `addDuration(startOn, durasi) − 1 hari`. `startOn` hanya boleh hari ini sampai 30 hari ke belakang (RV2-04). Untuk mulai di masa depan, admin menambahkan member di hari mulainya.

Fitur: F-04

Acceptance criteria:
- [ ] Given paket 1 bulan dan `startOn` 2026-01-15, When member dibuat, Then `expiresOn` 2026-02-14.
- [ ] Given paket 1 tahun dan `startOn` 2026-03-01, When member dibuat, Then `expiresOn` 2027-02-28.
- [ ] Given `startOn` besok, When `POST /members`, Then `422` dengan `details.startOn`.
- [ ] Given `startOn` 31 hari lalu, When `POST /members`, Then `422` dengan `details.startOn`.
- [ ] Given nomor HP sudah dipakai member lain di gym, When `POST`, Then `409 CONFLICT`.
- [ ] Given member baru, Then `linked` bernilai `false` dan `status` dihitung sesuai FR-14.

Edge cases:
- Paket awal tidak membuat baris `payments`. Pembayaran awal di luar aplikasi tidak dicatat, dan admin hanya mencatat perpanjangan berikutnya (FR-16).
- Nomor HP dinormalisasi (spasi dan tanda hubung dibuang) sebelum cek unik.

### FR-10: Daftar, pencarian, detail, dan ubah member
Admin melihat daftar member dengan pencarian nama atau nomor HP dan filter status. Halaman detail menampilkan data, status, paket, riwayat pembayaran (`GET /payments?memberId=`), dan riwayat check-in. Admin dapat mengubah nama, nomor HP, dan email.

Fitur: F-04

Acceptance criteria:
- [ ] Given 30 member, When `GET /members?limit=20`, Then 20 item dan `nextCursor` terisi; halaman kedua berisi 10 item tanpa duplikat.
- [ ] Given `q=budi`, When daftar diminta, Then hanya member yang nama atau nomornya mengandung "budi" (tanpa membedakan huruf besar-kecil).
- [ ] Given `status=expired`, When daftar diminta, Then hanya member dengan `expires_on` sebelum hari ini menurut zona gym.
- [ ] Given admin mengubah nomor HP ke nomor member lain, When `PATCH`, Then `409 CONFLICT`.
- [ ] Given member A, When `GET /members` atau mengubah member, Then `403`.

Edge cases:
- Halaman detail dibuka lewat URL langsung atau refresh tetap terisi (`GET /members/{memberId}`).
- `q` kosong atau spasi saja diperlakukan tanpa filter.

### FR-11: Foto member dengan signed URL
Admin mengunggah foto member lewat API. API menyimpan lewat port `FileStorage` dan hanya menyimpan path dan metadata di database. Foto dibaca lewat signed URL berumur 300 detik yang dibuat API setelah otorisasi (RV-05). `storage.rules` menolak semua akses langsung dari client.

Fitur: F-04

Acceptance criteria:
- [ ] Given file JPEG 1 MB, When admin `PUT .../photo`, Then `200`, `hasPhoto: true`, dan file tersimpan di path `gyms/<gymId>/members/<memberId>/photo`.
- [ ] Given file lebih dari 2 MB atau bukan JPEG/PNG/WebP, When diunggah, Then `422` dengan `details.file`.
- [ ] Given member A, When `GET /members/{idB}/photo-url`, Then `404`.
- [ ] Given admin atau pemilik foto, When `GET .../photo-url`, Then respons memuat `url` dan `expiresAt` 300 detik dari sekarang.
- [ ] Given `storage.rules`, When client langsung membaca atau menulis ke Storage, Then ditolak.

Edge cases:
- Upload kedua menimpa foto lama.
- Member tanpa foto: `photo-url` mengembalikan `404` dan UI menampilkan inisial.

### FR-12: Undangan sekali pakai dan penautan akun
Akun login ditautkan ke data member hanya lewat kode undangan sekali pakai dari admin (RV-02, RV-03). Admin menerbitkan kode untuk member. Admin juga bisa menerbitkan kode undangan admin. Kode berumur 48 jam, acak, dan disimpan sebagai hash. Member login lalu memasukkan kode di `POST /v1/invitations/redeem`. Penukaran kode terjadi dalam satu transaksi: periksa kode, tandai `used_at`, buat `gym_users`, dan (untuk member) isi `members.user_id`. Email tidak pernah dipakai untuk penautan otomatis.

Fitur: F-04

Acceptance criteria:
- [ ] Given admin menerbitkan kode untuk member M, When user U login dan menukar kode, Then `members.user_id = U`, `gym_users` role `member` terbuat, dan `GET /members/me` mengembalikan M.
- [ ] Given kode sudah dipakai, When ditukar lagi, Then `409 INVITATION_INVALID`.
- [ ] Given kode melewati `expires_at`, When ditukar, Then `409 INVITATION_INVALID`.
- [ ] Given admin menerbitkan kode baru untuk member yang sama, When kode lama ditukar, Then `409 INVITATION_INVALID`.
- [ ] Given user yang sudah punya peran di gym, When menukar kode member, Then `409 CONFLICT`.
- [ ] Given kode admin valid, When ditukar, Then user mendapat `gym_users` role `admin`.
- [ ] Given 5 percobaan salah dalam 15 menit oleh user yang sama, When percobaan ke-6, Then `429 RATE_LIMITED`.
- [ ] Given dua user menukar kode yang sama bersamaan, Then tepat satu berhasil.

Edge cases:
- Orang lain mendaftar dengan email member: tidak mendapat akses apa pun tanpa kode.
- Kode ditampilkan sekali di layar admin dengan tombol salin. Setelah ditutup, admin harus menerbitkan kode baru.
- Member yang sudah tertaut tidak bisa menerima undangan baru (`409 CONFLICT`).

### FR-13: Hapus akun dari halaman profil
Halaman profil menyediakan "Hapus akun" (syarat store, RV-10). Alurnya: konfirmasi, login ulang (re-auth Firebase), `DELETE /v1/me`, lalu client menghapus akun Firebase. API tidak punya service account, jadi penghapusan di Firebase dilakukan client.

Yang dihapus: baris `users`, `gym_users`, dan `device_tokens` milik user.

Yang tetap disimpan:
- Data member diperlakukan sebagai berikut: `user_id` dilepas, `full_name` diganti "Member Terhapus", `phone` dan `email` dikosongkan, foto dihapus dari Storage, dan `anonymized_at` diisi.
- Riwayat pembayaran dan check-in tetap tersimpan untuk pembukuan dan kehadiran.
- Booking sesi mendatang berstatus `booked` dibatalkan dengan `cancel_source='account_deleted'`.

Edge cases:

### FR-20: Webhook pembayaran dan perpanjangan otomatis
`POST /webhooks/midtrans` memverifikasi signature (SHA-512 dari `order_id + status_code + gross_amount + server key`, dibandingkan dengan waktu konstan). Pemrosesan berjalan dalam transaksi yang mengunci baris `payments`, lalu baris member (`FOR UPDATE`). Hasil gateway dinormalisasi:
- `pending` ke `pending`.
- `paid` memperpanjang masa aktif.
- `failed` ke `failed`.
- `expired` ke `expired`.

Pembayaran yang `pending` atau `expired` dapat menjadi `paid` (RV2-01). `computeRenewalPeriod` memakai snapshot durasi di `payments`. Bila `gross_amount` tidak sama dengan `payments.amount`, status menjadi `needs_review`, masa aktif tidak berubah, dan kejadian dicatat di log (RV2-06).

Fitur: F-07

Acceptance criteria:
- [ ] Given notifikasi `settlement` dengan signature benar dan jumlah sama, When webhook diterima, Then `status='paid'`, `paid_at` terisi, dan `members.expires_on` = `periodEnd` hasil `computeRenewalPeriod`.
- [ ] Given notifikasi yang sama dikirim dua kali (atau bersamaan), Then masa aktif hanya bertambah sekali dan kedua respons `200`.
- [ ] Given signature salah, When webhook diterima, Then `403` dan tidak ada perubahan data.
- [ ] Given pembayaran sudah `expired` lalu `settlement` tiba, Then status menjadi `paid` dan masa aktif diperpanjang.
- [ ] Given paket dua bulan dibuat lalu admin mengubah paket menjadi 1 minggu sebelum bayar, When `settlement` tiba, Then perpanjangan tetap dua bulan (snapshot).
- [ ] Given `gross_amount` berbeda dari `amount`, When webhook diterima, Then `status='needs_review'`, `members.expires_on` tidak berubah, dan log berisi `paymentId`, jumlah gateway, dan jumlah seharusnya.
- [ ] Given `deny`, `cancel`, atau `failure`, Then `status='failed'` tanpa perubahan masa aktif.
- [ ] Given `order_id` tidak dikenal dengan signature benar, Then `200` dan dicatat di log.

Edge cases:
- Pembayaran berstatus `paid`, `failed`, atau `needs_review` tidak diubah oleh notifikasi berikutnya (kecuali duplikat `paid`, yang menjadi no-op).
- Body webhook rusak: `400`.

### FR-21: Rekonsiliasi dan kedaluwarsa pembayaran

- [ ] Given pembayaran `pending` lewat `expires_at` dan gateway menjawab `expire`, When job berjalan, Then `expired`.
- [ ] Given pembayaran `needs_review`, When job berjalan, Then tidak ada panggilan `getStatus` dan status tidak berubah.
- [ ] Given job dijalankan dua kali berturut-turut, Then hasil tidak berubah pada eksekusi kedua.
- [ ] Given pembayaran `pending` yang gagal diperiksa karena gateway error, Then dicatat di log dan dicoba lagi pada eksekusi berikutnya, tanpa menghentikan pembayaran lain.

Edge cases:

- [ ] Given member, When `GET /class-sessions/{id}` untuk sesi `cancelled`, Then `404`.

Edge cases:
- Daftar urut `startsAt` naik. Filter `from` dan `to` memakai `local_date`.

### FR-32: Booking kelas atomik
Member `active` atau `expiring_soon` memesan slot. Booking diterima bila `expires_on >= local_date` sesi (masa aktif mencakup tanggal kelas). Dalam satu transaksi: `UPDATE class_sessions SET booked_count = booked_count + 1 WHERE id=$1 AND status='scheduled' AND starts_at > now() AND booked_count < capacity RETURNING ...`, lalu `INSERT` booking. Bila update tidak mengenai baris, API menentukan `CLASS_FULL` atau `SESSION_NOT_BOOKABLE`.

Fitur: F-10

Acceptance criteria:
- [ ] Given sesi kapasitas 10 dan 50 member memesan bersamaan, Then tepat 10 `201`, 40 `409 CLASS_FULL`, dan `booked_count = 10` (integration test konkuren).
- [ ] Given member sudah punya booking `booked` di sesi itu, When memesan lagi, Then `409 CONFLICT` dan `booked_count` tidak bertambah.
- [ ] Given member `expired`, When memesan, Then `409 MEMBERSHIP_INACTIVE`.
- [ ] Given `expires_on` 2026-03-10 dan sesi pada 2026-03-12, When memesan pada 2026-03-09, Then `409 MEMBERSHIP_INACTIVE`; untuk sesi 2026-03-10, Then `201`.
- [ ] Given sesi `cancelled` atau sudah mulai, Then `409 SESSION_NOT_BOOKABLE`.
- [ ] Given admin, When memesan, Then `403`.

Edge cases:
- Kegagalan insert (duplikat) membatalkan transaksi sehingga `booked_count` tidak bocor.
- Booking tidak otomatis menjadi check-in.

### FR-33: Batalkan booking
Member membatalkan booking paling lambat `cancelCutoffMinutes` (default 120) sebelum kelas mulai. Admin dapat membatalkan booking kapan pun sebelum kelas mulai. Pembatalan menandai `cancelled` dan mengurangi `booked_count` dalam satu transaksi.

Fitur: F-10

Acceptance criteria:
- [ ] Given kelas mulai 3 jam lagi, When member membatalkan, Then `200`, booking `cancelled` (`cancel_source='member'`), dan `booked_count` berkurang 1.
- [ ] Given kelas mulai tepat 120 menit lagi, When member membatalkan, Then `200`.
- [ ] Given kelas mulai 119 menit lagi, When member membatalkan, Then `409 CANCEL_WINDOW_CLOSED`.
- [ ] Given kelas mulai 30 menit lagi, When admin membatalkan, Then `200`.
- [ ] Given booking sudah `cancelled`, When dibatalkan lagi, Then `200` tanpa mengurangi `booked_count` lagi.
- [ ] Given booking milik member lain, When member membatalkan, Then `404`.
- [ ] Given sesi sudah mulai, Then `409 SESSION_NOT_BOOKABLE`.

Edge cases:
- Setelah dibatalkan, member dapat memesan ulang sesi yang sama bila masih ada kuota (unik parsial hanya untuk `booked`).

### FR-34: Daftar booking dan peserta
Member melihat daftar booking miliknya (mendatang dan riwayat). Admin melihat daftar peserta tiap sesi di halaman detail sesi.

Fitur: F-10

Acceptance criteria:
- [ ] Given member punya 3 booking aktif, When `GET /bookings?status=booked&upcoming=true`, Then hanya booking mendatang miliknya, urut terbaru dahulu.
- [ ] Given sesi dengan 4 booking aktif dan 1 batal, When admin `GET .../bookings`, Then 4 item peserta.
- [ ] Given member, When `GET /class-sessions/{id}/bookings`, Then `403`.

Edge cases:
- Peserta anonim ditampilkan sebagai "Member Terhapus".

### FR-35: Pengingat jadwal kelas
Job `notifications.class-reminder` berjalan tiap 5 menit. Job mengirim push ke member dengan booking `booked` pada sesi `scheduled` yang `starts_at`-nya dalam `classReminderMinutes` ke depan (default 60). Idempotensi memakai `notification_logs` dengan kunci `<bookingId>`. Bila kirim melempar error, baris log dihapus.

Fitur: R-03

Acceptance criteria:
- [ ] Given booking untuk sesi yang mulai 55 menit lagi, When job berjalan, Then satu push terkirim.
- [ ] Given job dijalankan berulang sampai kelas mulai, Then hanya satu push untuk booking itu.
- [ ] Given booking dibatalkan atau sesi dibatalkan, Then tidak ada push.
- [ ] Given sesi mulai 3 jam lagi, Then belum ada push.
- [ ] Given member tanpa token, Then tidak ada push dan tidak ada log.

Edge cases:
- Booking yang dibuat kurang dari `classReminderMinutes` sebelum kelas mendapat pengingat pada eksekusi job berikutnya.
- Token tidak valid dihapus (FR-23).

## 7. Non-Functional Requirements

- **NFR-01 (Keamanan akses):** Seluruh route `/v1/*` menolak request tanpa token valid dengan `401`. `all-routes-require-auth.int.test.ts` hijau dan hanya `/webhooks/midtrans` terdaftar sebagai publik.
- **NFR-02 (Isolasi data):** Tidak ada endpoint yang mengembalikan data member lain kepada member. Setiap query repository memfilter `gym_id` (dan `member_id` untuk data milik member) di query yang sama. Integration test memeriksa 100% endpoint member terhadap data member lain (hasil `404`).
- **NFR-03 (Konkurensi booking):** 50 request booking bersamaan pada sesi berkapasitas 10 menghasilkan tepat 10 sukses dan `booked_count = 10`, dalam 20 kali pengulangan test tanpa kegagalan.
- **NFR-04 (Konkurensi admin):** Test cabut-silang dan hapus-akun bersamaan pada dua admin selalu menyisakan tepat 1 admin. Test diulang 20 kali tanpa kegagalan.
- **NFR-05 (Idempotensi pembayaran):** Webhook yang sama dikirim 10 kali (sebagian bersamaan) memperpanjang masa aktif tepat sekali. `members.expires_on` sama dengan hasil satu kali pemrosesan.
- **NFR-06 (Idempotensi job):** Setiap job (`payments.reconcile`, `classes.generate-sessions`, `notifications.*`) yang dijalankan dua kali berturut-turut tidak membuat perubahan atau notifikasi tambahan pada eksekusi kedua. Job yang gagal di tengah tidak menghentikan item lain.
- **NFR-07 (Webhook):** Verifikasi signature memakai perbandingan waktu konstan. Request dengan signature salah tidak mengubah data (diuji).
- **NFR-08 (Performa):** Dengan 5.000 member dan 20.000 pembayaran, p95 `GET /members` (dengan `q` dan `status`) dan `GET /payments` kurang dari 300 ms. `POST .../check-ins` dan `POST .../bookings` p95 kurang dari 500 ms, diukur pada lingkungan Docker Compose lokal.
- **NFR-09 (Ketepatan waktu):** Test unit `computeMemberStatus` dan `computeRenewalPeriod` mencakup batas tengah malam zona gym, akhir bulan, dan tahun kabisat. Semua kasus di FR-14, FR-16, dan FR-20 lulus dengan jam yang disuntikkan.
- **NFR-10 (QR):** Token QR berumur `qrRotationSeconds` (default 30 detik, toleransi pemindaian 5 detik) dan sekali pakai. Kunci penandatangan hanya di env server dan tidak pernah masuk log atau respons.
- **NFR-11 (Foto):** Signed URL berumur 300 detik. Bucket tidak bisa diakses langsung dari client (`storage.rules` menolak semua). Ukuran maksimal 2 MB dan tipe terbatas JPEG/PNG/WebP.
- **NFR-12 (Privasi dan log):** Log tidak memuat token ID, token QR, token FCM, kode undangan, nomor HP, atau email. Kode undangan hanya tersimpan sebagai hash. Seluruh lalu lintas lewat HTTPS.
- **NFR-13 (Kode undangan):** Kode minimal 40 bit entropi, berumur 48 jam, dan sekali pakai. Lebih dari 5 percobaan gagal per user per 15 menit menghasilkan `429`.
- **NFR-14 (Kontrak):** `pnpm contract:check` lulus di CI. Client Dart di-generate dari OpenAPI, dan setiap `ErrorCode` baru punya teks pesan Indonesia di `failure_messages.dart`.
- **NFR-15 (Pengujian):** Use case API punya unit test dengan repository palsu. Repository dan job punya integration test (PostgreSQL sungguhan, adapter `fake` untuk push, storage, dan payment). Setiap Bloc/Cubit Flutter punya `bloc_test`. `pnpm check` hijau di CI.
- **NFR-16 (Penghapusan akun):** Menghapus akun member menghapus 100% baris `users` dan `device_tokens` miliknya dan menganonimkan data pribadi member. Baris `payments` dan `check_ins` tetap ada. Tombol "Hapus akun" terjangkau dalam maksimal 3 ketukan dari beranda.
- **NFR-17 (Ketersediaan dan shutdown):** API dan worker berjalan di satu container. Shutdown mengikuti urutan konvensi (Job pg-boss: Shutdown) tanpa kehilangan job yang sedang berjalan. Gagal start worker membuat proses keluar dengan exit code 1.
- **NFR-18 (Konsistensi data):** Semua timestamp berpresisi milidetik dan diisi jam database. `pnpm --filter api db:generate` tanpa perubahan skema mencetak `No schema changes`.
- **NFR-19 (Notifikasi):** Pengingat masa aktif dikirim paling banyak satu kali per `(member, expires_on, tahap)`. Pengingat kelas paling banyak satu kali per booking. Token tidak valid dihapus pada upaya kirim pertama yang menolaknya.
- **NFR-20 (Bahasa dan UX):** Seluruh teks antarmuka berbahasa Indonesia. Error validasi API (`details`) ditampilkan per field. Layar daftar menyediakan tarik-untuk-segarkan dan menampilkan status memuat, kosong, dan gagal.
